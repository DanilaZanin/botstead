# Bot Hub: контракты модулей (v1, 2026-09-24)

Единственный источник правды для параллельной разработки. Меняешь контракт: сначала правка здесь отдельным коммитом, потом код. Всё, чего здесь нет, модуль решает сам внутри себя.

## 1. База данных (Postgres 16, схема `bothub`)

Миграция `core/bothub/migrations/001_init.sql` (владелец: core). Остальные модули читают только через API.

## 2. HTTP API ядра (префикс `/api`, JSON)

Авторизация: заголовок `Authorization: Bearer <token>`.
- Токен владельца `OWNER_TOKEN` (PWA; перед ядром ещё SSO-прокси).
- Токен бота `bot:<bot_id>:<hmac>` где hmac = HMAC-SHA256(`BOT_TOKEN_SECRET`, bot_id) в hex. Выдаётся контейнеру бота через env `BOTHUB_TOKEN`. Боту доступны только помеченные [bot] эндпоинты и только в своих тредах.
- Mac-агент: `MAC_AGENT_TOKEN`, только WebSocket из раздела 5.

Тело запроса больше 1 МиБ (кроме `multipart/form-data` файлов и `/gateway/…`): 413 `{"error": "invalid", "detail": "request body exceeds 1 MiB"}`; `/hooks/{id}` держит свой предел 64 КБ (тоже 413).

**Сводка расхода (`GET /api/usage/summary`).** Принимает query-параметр `days`: целое десятичное число от 1 до 90, по умолчанию 7 (пробелы по краям игнорируются; `0`, `91`, `abc`, `7.5`, `+7`, `07` и пустое значение недопустимы). Недопустимое значение возвращает 422 `{"error": "invalid", "detail": "days"}`. Каждая из четырёх выборок (боты, модели, дни, провайдеры) явно ограничена ботами текущего пользователя (`bots.owner_id`): расход чужих ботов не попадает ни в одно поле ответа.
Период считается целыми сутками: он начинается в полночь суток `days - 1` дней назад и идёт по текущий момент, то есть включает сегодняшние сутки и `days - 1` предыдущих. Запись ровно на начале периода (полночь первых суток) входит, запись на микросекунду раньше не входит. Запись «ровно `days` суток назад» (`now() - days * 24 ч`) лежит в сутках перед первыми сутками периода: при этом `days` она не входит, при `days + 1` входит. Границы суток берёт база: часовой пояс её сессии (по умолчанию UTC).
Ответ содержит:
- `days`: запрошенный период в днях (целое число).
- `total_tokens`: сумма `total_tokens` из `daily`, то есть расход всех ботов пользователя за период.
- `bots`: все боты пользователя (даже без расхода) по возрасту создания, затем по `id`; поля `bot_id`, `tokens_today` (расход с начала текущих суток), `tokens_period` (расход за период), `budget` (`bots.budget_daily_tokens`, по умолчанию 200 000), `last_activity` (время самой поздней записи расхода бота за всё время, ISO 8601, или `null`, если расхода не было).
- `models`: расход за период, сгруппированный по паре `(provider, model)`, по убыванию `total_tokens`, затем по `provider` и `model`; поля `provider`, `model`, `tokens_in`, `tokens_out`, `tokens_cache_read`, `tokens_cache_write`, `total_tokens` (сумма четырёх), `turns` (число различных `turn_id` в записях группы; запись без `turn_id` считается отдельным ходом). Модель без расхода за период в список не попадает.
- `daily`: ровно `days` элементов от старых суток к сегодняшним, `date` (`YYYY-MM-DD`) и `total_tokens`. Сутки без расхода присутствуют в ряду со значением `0`, в том числе посередине периода.
- `providers`: различные `provider` ботов пользователя по алфавиту, `pct_week` и `reset_at` пока `null` (трекинга квот подписок нет).

Поля `guard` в ответе нет: маршрут его не отдаёт ни сейчас, ни раньше. Остановка бота предохранителем видна как событие `guard` в треде (раздел 3).

## 4. Правила auto_allow и подтверждения

`bots.auto_allow` = список объектов `{"tool": "<имя или префикс*>", "match"?: {"<ключ args>": "<значение>"}, "op_hash"?: "<SHA256>"}`. Значения `match` сравниваются с аргументом точно (строка как есть, остальные типы через канонический JSON), без glob; отсутствующий ключ = не совпало; метасимволы `* ? [` в значении буквальные. Glob допустим только в имени инструмента. Если задан `op_hash`, дополнительно требуется совпадение хэша инструмента и всего объекта `args`: лишний аргумент меняет операцию. Правило с непустым `match` без `op_hash` не действует (так выглядело старое «запомнить»); миграция 006 удаляет такие правила, а заодно правила без `match` для `Bash`, `WebFetch` и `mcp__bothub__mac_delegate`, и складывает их в `auto_allow_removed(bot_id, rule, removed_at)`.

Действие разрешено без спроса, если совпало правило и инструмент классифицирован безопасным (fail-closed, `bothub/risk.py`):
- читающие инструменты: `Read`, `Glob`, `Grep`, `TodoWrite`, `WebSearch`, `mcp__bothub__{attach_file,remember,mac_find_files,mac_read_file,mac_preview,mac_screenshot,mac_upload_file}`: подходит любое правило. Исключение: `Read`, `mcp__bothub__attach_file` и `Grep` с `path` не читают без подтверждения `.claude/`, `.codex/`, `.gemini/`, `.auth/`, `.ssh/`, `.aws/` (на любой глубине), `.netrc`, `.env*`, `/proc/*/environ`, `/run/secrets/`; путь нормализуется (`..`, `~`, относительный путь от `/home/bot`, регистр), путь с glob не проверить, поэтому он тоже идёт на подтверждение и не запоминается;
- `Write`/`Edit`: только абсолютный путь внутри `/home/bot` без выхода за его пределы; скрытые компоненты (`.bashrc`, `.claude`, `.git/config`, `.auth`) и инструкционные файлы требуют подтверждения (регистр не учитывается): `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `GEMINI.md`, `Makefile`, `GNUmakefile`, `package.json`, `conftest.py`, `pytest.ini`, `pyproject.toml`, `setup.py`, `setup.cfg`, `sitecustomize.py`, `usercustomize.py`, `*.pth`, всё внутри `node_modules/` и `bin/` (в том числе `.local/bin/`);
- любой другой инструмент: только правило с точным именем (без glob) и непустым `match`;
- `mcp__bothub__browser`: `snapshot` и `screenshot` разрешены без правила; `navigate`, `click`, `fill` спрашивают и запоминаются по паре (действие, origin) правилом `{"tool": "mcp__bothub__browser", "scope": "browser_origin", "match": {"action": "...", "origin": "https://host"}}` (без `op_hash`: правило про действие и origin, а не про точные аргументы); адреса вне политики отклоняются сразу, без вопроса (раздел 13);
- `Bash` и `WebFetch` в базовый набор не входят. Для `Bash` правило может разрешить только одиночную читающую команду `ls`, `cat`, `grep`, `pwd`, `head`, `tail`, `wc`, `find` (без `-exec`, `-delete`, `-ok`, `-fprint`), `du`, `sort`, `uniq`, `which`, `echo`, `stat`, `file`, `tree`, `diff`, без перенаправлений, конвейера, разделителей команд и подстановок; аргументы не указывают на пути с учётными данными, glob допустим только как шаблон поиска (`find -name`, первый операнд `grep`). `git` в контейнере всегда требует подтверждения и не запоминается. Слова в аргументах такой команды (`cat pay.txt`, `grep -r auth .`) метку риска не ставят.

Никогда не проходят ни по правилам, ни по `mac_full_control`, ни по «запомнить»: риски `pay`, `delete`, `login`; установка ПО и запуск интерпретаторов или скриптов с возможностью записи (в том числе `python3 file.py`, `npm run`, `perl -e`, `python -W ... -c`, `sed -i`, `find -exec`, `awk system()`, `docker -v /`); отправка данных наружу из Bash (`curl`, `wget`, `dig`, `nc`, `scp`, `ssh`, `rsync`); команды, которые не удалось классифицировать (обфускация, `$(...)`, backticks, base64, eval, heredoc, незакрытые кавычки); не-словарные аргументы; `mac_delegate` и его alias; для Mac всё, кроме читающих инструментов и shell-команды, целиком состоящей из читающих программ (`git` в этом списке отсутствует). `mac_shell` с относительным, скрытым или непроверяемым `cwd` и чтением секретов требует подтверждения.

`remember=true` при approve добавляет правило `{"tool": tool, "match": {все аргументы, точно}, "op_hash": "<SHA256>"}` и не добавляет ничего для действий из списка выше (в ответе `remember: false`).

`bots.mcp_allow` (2026-10-06) = список разрешённых чужих MCP-инструментов; пусто = у бота только сервер `bothub`. Чужой инструмент (`mcp__<сервер>__<инструмент>`, сервер не `bothub`; у codex в событиях `<сервер>.<инструмент>`, имя приводится к тому же виду) проходит, только если подходит под элемент списка: точное имя, glob (`mcp__github__*`), `<сервер>.<инструмент>` или голое имя сервера (`github` = `mcp__github__*`). Список не авто-одобряет: разрешённый инструмент идёт по обычным правилам этого раздела (неизвестному нужно точное правило с непустым `match`), а `auto_allow` инструмент вне списка не открывает. Свои инструменты (`mcp__bothub__*`) и встроенные инструменты CLI (`Bash`, `Read`) списку не подчиняются. Свой сервер только ровно `bothub`: `bothub_`, `bothub_x`, `Bothub` и `mcp__bothub___x` (лишний `_` отходит серверу, это сервер `bothub_`) чужие. Сервер и инструмент сравниваются с маской по отдельности: `mcp__github__*` не открывает сервер `github_`. Имя, похожее на MCP-инструмент, но не разобравшееся (`mcp__github`, `mcp_tool_call`, имя с точкой и пробелом), считается чужим и не открывается никаким списком, в том числе `*`. Три слоя (`bothub/mcp_policy.py`):
- ядро, `POST /api/approvals`: инструмент вне списка сразу получает `rejected`, в ответе поле `reason: "mcp_not_allowed"`, в тред пишется `approval_dec` от `system` с тем же `reason`; владельцу вопрос не приходит, одобрить такой вызов нельзя (как запрещённый адрес, раздел 13). Это единственный слой, который решает; остальные его дублируют;
- `approve` в `mcp_server.py` (Claude): ответ ядра `rejected` с `reason: "mcp_not_allowed"` превращается в `{"behavior":"deny","message":"mcp_not_allowed"}`, ход продолжается. Раннер Claude при пустом списке добавляет `--strict-mcp-config`: серверы из настроек CLI в контейнере не поднимаются, работает только `bothub`; при непустом списке флага нет, инструменты чужих серверов режет `approve`;
- раннеры codex и agy не спрашивают подтверждение: `SubprocessRunner.guard` видит `tool_call` чужого инструмента вне списка в потоке событий, останавливает процесс (`stop_exec` в контейнере) и бросает `McpNotAllowed`; ядро закрывает ход как `error` с событием `guard` `{"reason":"mcp_not_allowed","detail":"<инструмент>"}`. Вызов к этому моменту уже начат, поэтому это остановка, а не предотвращение. Сервер `bothub` codex получает флагами `-c mcp_servers.bothub.*` (адрес и токен берутся из окружения через `env_vars`, не из argv), а не из `~/.codex/config.toml`. Сам `-c` сливается с `config.toml`, а не заменяет его (проверено `codex mcp get` на 0.159), поэтому чужие серверы из `config.toml` остаются и их вызовы ловит `guard`. Флаг `--ignore-user-config` есть в 0.159, но не проверен в закреплённом в образе 0.156.1, поэтому не используется. Ход сжатия (раздел 15) в эту проверку не входит: его останавливает ядро первым же `tool_call`.
- agy список не применяет: парсер не отдаёт `tool_call` (формат шагов инструментов не снят живьём). Ход с непустым `mcp_allow` не запускается: `GeminiRunner.command` бросает `McpAllowUnsupported`, ядро закрывает ход как `error` с событием `guard` `{"reason":"mcp_allow_unsupported","detail":"gemini"}` до запуска процесса. Пустой список для agy не гарантия: серверы из настроек agy не отключаются. Ход сжатия отказом не затрагивается.
- Проверка тела (`POST`/`PATCH /api/bots`): до 200 элементов, 1–200 символов после обрезки краёв, без пробелов и непечатных символов внутри (иначе 422); пробелы по краям обрезаются, повторы убираются, порядок сохраняется.

Для Claude: `--permission-prompt-tool mcp__bothub__approve`. Инструмент `approve` MCP-сервера получает `{"tool_name","input"}` и возвращает `{"behavior":"allow","updatedInput":input}` или `{"behavior":"deny","message":"..."}`. Риск определяется по таблице в `bothub/risk.py` (владелец: runner): имя инструмента и аргументы → risk. Чтение, поиск, скриншот = `other` и разрешены при `mac_full_control` или по правилам.

## 5. Mac-агент ↔ ядро (WebSocket `/agent/mac`)

Подключение: `wss://<host>/agent/mac?token=MAC_AGENT_TOKEN`. Агент держит соединение, переподключается с экспоненциальной паузой 1–30 с.

Несколько адресов ядра: `BOTHUB_URLS` содержит список через запятую по приоритету (например, публичный адрес, затем SSH-туннель); `BOTHUB_URL` остаётся поддержанным как список из одного. Каждая попытка подключения пробует адреса по порядку, основной первым, с таймаутом 10 с на адрес. Если основной не отвечает, агент подключается к следующему. Сидя на запасном адресе, раз в 5 минут проверяет доступность основного отдельным HTTP GET `<url>/api/health` с таймаутом 5 с (2xx/3xx считается «доступен»: за SSO-прокси приходит 302, следовать за редиректом не нужно) и, если основной жив, переключается обратно, не рвя рабочее соединение раньше времени. `upload_file` шлёт файл на тот адрес, к которому агент подключён прямо сейчас.

Сообщения JSON:
- агент → ядро `{"type":"hello","host","os","agent_version","permissions":{"files":bool,"screen":bool,"automation":bool,"accessibility":bool}}`
- агент → ядро `{"type":"heartbeat","locked":bool,"battery":int|null}` каждые 30 с
- ядро → агент `{"type":"call","id","tool","args","timeout"}`
- агент → ядро `{"type":"result","id","ok":bool,"data"?,"error"?}`

Инструменты Mac (`tool`, `args` → `data`):
| tool | args | data |
| --- | --- | --- |
| find_files | `{"query","kind"?:"pdf|image|doc|any","since"?:"YYYY-MM-DD","limit"?:20,"content"?:bool}` | `[{"path","name","size","modified","kind"}]` через mdfind |
| read_file | `{"path","max_bytes"?:1048576}` | `{"path","size","mime","content_b64"}` |
| upload_file | `{"path","thread_id"}` | `{"file_id"}` (агент шлёт файл в POST /api/files с MAC_AGENT_TOKEN) |
| preview | `{"path","max_side"?:800,"format"?:"jpeg"}` | `{"jpeg_b64"\|"png_b64","width","height","bytes"}` через `qlmanage -t`, ужато `sips -Z <max_side>` |
| screenshot | `{"max_side"?:1440,"format"?:"jpeg"}` | `{"jpeg_b64"\|"png_b64","width","height","bytes"}` через `screencapture -x`, ужато `sips -Z <max_side>` |
| open | `{"target"}` | `{}` (`open` файла, URL или `-a` приложения) |
| applescript | `{"script"}` | `{"stdout"}` |
| shortcut | `{"name","input"?}` | `{"stdout"}` |
| shell | `{"cmd","cwd"?,"timeout"?:60}` | `{"code","stdout","stderr"}` (обрезка 64 КБ) |
| delegate | `{"engine":"gemini\|codex\|claude","prompt","cwd"?:"~/BotHub/work","timeout"?:900}` | `{"engine","output","seconds","exit_code"}`: субагент на Mac, максимум 2 параллельно, timeout максимум 1800 с, обрезка вывода 200 КБ, stderr в конце при ошибке, таймаут убивает всю группу процессов. `engine="gemini"` → `agy`. `engine="claude"` → второе мнение, Claude Sonnet без `--permission-mode` (правок не делает). `engine="codex"` → решение владельца 2026-09-25 (у Codex закончился лимит): по умолчанию тоже Claude Sonnet, но с `--permission-mode acceptEdits` (кодовая задача, правки в cwd разрешены); настоящий Codex CLI используется только если в окружении агента `BOTHUB_CODE_ENGINE=codex` |

Статус Mac в `mac_status`: `online` при живом WS и `locked=false`; `locked`; `offline` если нет heartbeat 90 с. `POST /api/mac/call` при не-online: если `MAC_WOL_CMD` задан, ядро выполняет его и ждёт до 30 с появления агента, иначе 409 `mac_unavailable`; turn переходит в `waiting_mac` и продолжается, когда агент подключится (до дедлайна turn).

## 6. Runner (владелец: runner) и MCP-сервер bothub

Интерфейс в `core/bothub/runner/base.py`:

```python
class Runner(Protocol):
    provider: str
    async def run(self, turn: TurnContext) -> AsyncIterator[RunnerEvent]: ...
    async def stop(self, turn_id: str) -> None: ...

@dataclass
class TurnContext:
    turn_id: str; thread_id: str; bot: dict; prompt: str
    cli_session_id: str | None; dry_run: bool; memory_md: str
    exec_prefix: list[str]      # например ["docker","exec","-i","bot-scout"] или [] для локального запуска

@dataclass
class RunnerEvent:
    kind: str                    # как в разделе 3 (assistant_msg, plan, tool_call, tool_result, usage)
    payload: dict
    cli_session_id: str | None = None
```

- `claude`: `claude -p --output-format stream-json --verbose --resume <sid> --model <model> --mcp-config <json> --permission-prompt-tool mcp__bothub__approve --append-system-prompt <instructions+memory>`; dry_run: `--permission-mode plan`.
- `codex`: `codex exec --json -s workspace-write -m <model>` / `codex exec resume <sid>`; парсить последнее сообщение, эхо промпта игнорировать; dry_run: `-s read-only`.
- `gemini`: `agy -p --output-format stream-json --model <model>`, промпт через stdin; dry_run без `--dangerously-skip-permissions`.
- `fake`: детерминированный раннер для тестов: план из 2 шагов, ответ «ok: <prompt>», usage 10/20.
- Ядро выбирает раннер по `bots.provider`, пишет RunnerEvent в events, сохраняет cli_session_id, считает шаги и повторы ошибок (guard).

MCP-сервер `bothub` (stdio, `python -m bothub.mcp_server`, env `BOTHUB_URL`, `BOTHUB_TOKEN`, `BOTHUB_THREAD_ID`, `BOTHUB_TURN_ID`) даёт инструменты:
`approve` (раздел 4), `mac_<tool>` для каждого инструмента Mac (через POST /api/mac/call), `attach_file` (путь в контейнере → POST /api/files), `remember` (POST /api/memory, статус proposed), `schedule_wakeup` (POST /api/bots/wakeups, раздел 17), `delegate_to_bot` и `delegation_result` (POST и GET /api/bots/delegations, раздел 19).

`mac_delegate` требует подтверждения операции. При 409 он сразу отдаёт модели ошибку «Mac не в сети, выполни сам» без повтора. Таймаут вызова `/api/mac/call` = `args.timeout` (по умолчанию 900, максимум 1800) + запас 60 с, чтобы ядро дождалось ответа агента или таймаута.

## 8. Уточнения (после контрактных тестов, 2026-09-24)

- Нет токена или он неверный: 401 `unauthorized`. Токен верный, но прав нет (бот лезет в чужой тред или в эндпоинт владельца): 403 `forbidden`. Неверный hook token: 403.
- `auto_allow`: `tool` сравнивается с именем инструмента через `fnmatch` (`mac_find_*`); каждое значение `match` сравнивается точно, без glob (раздел 4); отсутствующий ключ = не совпало.
- `POST /hooks/{id}`: prompt turn = `schedule.prompt + "\n\nДанные события:\n```json\n" + тело + "\n```"`.
- `PATCH /api/threads/{id}` принимает также `title`.
- `user_msg` пишет ядро при `POST /api/threads/{id}/turns` (actor `owner`, client из тела), до постановки turn в очередь.
- Бот видит в `GET /api/memory` только `status=active` с `bot_id is null` или своим `bot_id`.
- `/api/mac/call` при не-online без `MAC_WOL_CMD` или после неудачного пробуждения: 409 `mac_unavailable`, ядро переводит turn в `waiting_mac` и пишет событие `system` «Mac недоступен: <state>». Раннер сам решает, ждать ли (MCP-инструмент `mac_*` повторяет вызов раз в 15 с до таймаута инструмента).
- Решение владельца 2026-09-25: мозг ботов только Claude. `POST /api/bots` и `PATCH /api/bots/{id}` отклоняют `provider` `codex`/`gemini` с 400 `invalid`, detail «provider не поддерживается: мозг ботов только claude». `fake` остаётся (тесты), раннеры codex/gemini в коде не удалены.
- `decide_permission(bot, tool, args, turn)` (`bothub/main.py`, логика в `bothub.risk.decide`): единая точка риска и авто-разрешения, используется и `/api/approvals`, и `/api/mac/call`: `risk = bothub.risk.classify(tool, args)` считается на сервере (тело `/api/approvals` может присылать `risk`, но он игнорируется); запреты и условия авто-разрешения описаны в разделе 4; `mac_full_control` авто-разрешает только читающие `mac_*`-инструменты (и `mac_shell` с чисто читающей командой), остальное через `auto_allow` по правилам раздела 4.
- `POST /api/mac/call`: требует `executor='mac'` или `mac_full_control` у бота, кроме `delegate`, который доступен любому боту после подтверждения. Turn должен существовать, принадлежать треду и иметь статус `running` или `waiting_mac` (иначе 403 `forbidden`). Для `shell`/`applescript`/`shortcut`/`open`/`click`/`type_text`/`move_to_trash`/`delegate` требуется approved `Approval` с тем же `op_hash` (SHA256 от `tool` и канонического JSON `args`) на этот `turn_id`, либо разрешение `decide_permission`. Одобрение расходуется одним вызовом (`approvals.used_at`): повтор требует нового одобрения, кроме одобрения с `remember`; если вызов до Mac не дошёл (агент офлайн, нет слота), одобрение возвращается; для `delegate` авто-разрешение всегда отключено. Для чтения (`find_files`/`read_file`/`preview`/`screenshot`/`upload_file`) достаточно `mac_full_control` или подходящего правила `auto_allow`. Имя инструмента для risk/auto_allow в обоих случаях: `mcp__bothub__mac_<tool>`. Неизвестный `tool`: 400 `invalid`.
- `claim_turn()` не подхватывает turn, если у его бота уже есть другой `running`/`waiting_approval`/`waiting_mac` turn (тред принадлежит одному боту, поэтому turns одного треда и одного бота идут строго по очереди), и не берёт новый `queued`, пока `running` turn'ов на ядре не меньше `BOTHUB_MAX_PARALLEL_TURNS`. Занятый бот и лимит не отклоняют turn: он остаётся `queued` и стартует, когда освободится слот; занятый бот не блокирует очередь других ботов. Возврат turn'а из `waiting_approval`/`waiting_mac` в `running` проходит ту же проверку лимита под той же блокировкой (`resume_turn`). Слота нет: turn остаётся в `waiting_*` (статус не становится `queued`: раннер жив, и `claim_turn` запустил бы второй `execute_turn`), `GET /api/approvals/{id}/wait` отвечает `status: pending` с `queued: true`, а `POST /api/mac/call` отвечает 409 `queued`; раннер повторяет запрос, пока слот не освободится.
- Надёжность (этап 1Б). Статус `failed` из плана = существующий `error` (CHECK миграции 001 не меняется). Любое закрытие turn идёт через `fail_turn`: останавливает раннер, закрывает висящие approval turn'а (`expired`), пишет событие причины, `status` и outbox. Причины: исключение раннера (в том числе в `waiting_approval`/`waiting_mac`), раннер завершился во время ожидания (`guard` `runner_exited`), раннер не пинговал `BOTHUB_RUNNER_TIMEOUT` минут (`guard` `runner_lost`), истёкший approval (`approval_expired`), дневной бюджет (`budget_exceeded`).
- «Пинг» раннера (`turns.runner_ping_at`): событие раннера, `GET /api/approvals/{id}/wait`, `POST /api/approvals`, `POST /api/usage`, `POST /api/mac/call` по этому turn. Проверка staleness идёт в `claim_turn` (`reap_turns`) для `waiting_approval`/`waiting_mac`.
- Истёкший approval (по `expires_at` или старше `APPROVAL_TIMEOUT`) больше не возвращает turn в `running`: turn закрывается событием `approval_expired`, поэтому `claim_turn` не может запустить его повторно после истечения lease. Рестарт ядра: `recover_stale_turns` закрывает turn'ы с просроченным lease и в той же транзакции переводит их pending-approval в `expired` с событием `approval_dec` (вид тот же, что у истечения по сроку: `client: "system"`), раньше события `status`; иначе карточка остаётся `pending` до `expires_at`.
- Бюджет проверяется на каждом `usage` (событие раннера и `POST /api/usage`), а не только на старте turn: при `spent >= budget_daily_tokens` turn закрывается событием `budget_exceeded`. Проверка на старте осталась (status `stopped`, `guard` `budget`).
- Outbox: доставка push по каждой подписке отдельно (`outbox_deliveries`: `sent|failed|gone`), сбой одной подписки не повторяет отправку остальным, ответ 404/410 удаляет подписку, повтор с экспоненциальной паузой (`next_attempt_at`, потолок 1 час), после `BOTHUB_OUTBOX_MAX_ATTEMPTS` запись получает `failed_at`. Запись о попытке (`outbox_deliveries.status='sending'`) создаётся до сетевой отправки, соединение из пула на время отправки не удерживается. Параллельные проходы захватывают запись арендой (`next_attempt_at` сдвигается на `BOTHUB_OUTBOX_LEASE`, по умолчанию 120 с). Сетевой вызов push ограничен 10 секундами. Сбой БД после отправки повтор не вызывает: endpoint остаётся в `sending` и повторно не шлётся (при падении процесса до отправки такое уведомление теряется). `dedup_key` остаётся идемпотентным ключом записи.
- Фоновые циклы `worker`, `scheduler`, `outbox_sender` работают под `supervise`: исключение в проходе логируется (`loop_error`) и цикл продолжается. Логи: JSON-строка в stdout (`ts`, `level`, `logger`, `msg`, поля extra, `exc`).
- Одобрение и правило «запомнить» привязаны к операции: `approvals.op_hash` и `op_hash` в правиле `auto_allow` (SHA256 от `tool` и канонического JSON всех `args`). Правило с `op_hash` не срабатывает при лишних или других аргументах; правило с `match` без `op_hash` не срабатывает совсем.
- `lease_until` обновляется на `now()+60s` при каждом возврате turn'а в `running` (claim_turn, approval decide, `waiting_mac`→`running`) и в фоновом `renew()` каждые 30 с (он продлевает также `waiting_approval`/`waiting_mac`). Истёкший lease может дать `claim_turn()` запустить второй `execute_turn` поверх ещё живого.
- При старте ядра turn'ы `running`/`waiting_approval`/`waiting_mac` с истёкшим (или отсутствующим) `lease_until` помечаются `error` («прервано рестартом ядра») + событие `status`; в `BOTHUB_RUNNER_EXEC=docker` дополнительно шлётся `docker exec bot-<id> pkill -f <turn_id>` (TERM, затем KILL).
- В режиме `docker` `stop()`/timeout/guard убивают не только клиента `docker exec`, но и CLI внутри контейнера: команда оборачивается так, что её `argv[0]` внутри контейнера содержит `turn_id` (`bothub-turn-<turn_id>`), и `stop()` шлёт туда `docker exec <container> pkill -TERM -f <turn_id>`, через 5 с `-KILL`.

## 9. Конструктор ботов (2026-09-25)

Владелец создаёт бота одним описанием на естественном языке. Существующие боты не меняются.

`POST /api/bots/draft` (owner), тело `{"description": str (10–4000 символов)}` → 200 BotDraft:
```json
{"id": "tax-helper", "name": "Налоговик", "role": "одна фраза", "avatar": "owl",
 "provider": "claude", "model": "claude-sonnet-5", "executor": "container", "mac_full_control": false,
 "auto_allow": [{"tool": "mcp__bothub__mac_find_files"}], "instructions": "…",
 "schedule": {"name": "…", "cron": "0 9 * * 1-5", "timezone": "Europe/Moscow", "prompt": "…"} | null,
 "rationale": "2–3 предложения, почему такие настройки"}
```
- Черновик собирает Claude: ядро выполняет `docker exec -i <BOTHUB_BUILDER_CONTAINER или любой запущенный bot-*> claude -p --model claude-sonnet-5 --output-format json --tools ""` с системной инструкцией конструктора и описанием владельца; ответ модели обязан быть одним JSON-объектом BotDraft. В тестах и dev вместо этого вызывается `drafter` из `create_app(runner_factory=None, drafter=None)`.
- Ядро валидирует черновик: id по `^[a-z0-9-]{1,32}$` и уникален (при занятости добавляет `-2`, `-3`), avatar из 8 персонажей, provider только claude, model из {claude-haiku-4-5-20251001, claude-sonnet-5, claude-opus-5-5}, auto_allow только из инструментов `mcp__bothub__*` с риском other, cron валиден по croniter. Невалидное поле ядро заменяет безопасным значением и пишет об этом в `rationale`. 502 `builder_failed`, если модель не вернула JSON.
- Инструкции черновика всегда заканчиваются общим блоком: делегирование через `mac_delegate` при Mac в сети, иначе сам; необратимое через approve; результат подтверждать фактом; писать по-русски.

`POST /api/bots` (owner) дополнительно принимает `"schedule"` как в BotDraft и `"start_container": true` (по умолчанию true в режиме docker): ядро создаёт бота, расписание (если есть) и контейнер `bot-<id>` так же, как `deploy/bot-create.sh` (сеть `bothub_default`, env BOTHUB_URL=http://core:8080, BOTHUB_TOKEN, CLAUDE_CODE_OAUTH_TOKEN из своего окружения, том `bot-<id>-home`, логины `/data/bots/logins` read-only, образ `bothub-bot`). Ответ Bot + `"container": "starting"|"skipped"`; запуск контейнера идёт фоном, см. «Запуск бота после ответа» ниже.

PWA: экран «Новый бот» = поле описания + «Собрать» → карточка черновика (персонаж, имя, роль, модель, где работает, правила, расписание, rationale), поля редактируются → «Создать» → открыть тред нового бота.

### Запуск бота после ответа (2026-10-06)

Первый бот пользователя создавал сеть `bothub-u-<owner>` и подключал к ней ядро (`docker network connect`) прямо внутри `POST /api/bots`. Docker перестраивает правила и рвёт соединения: бот и контейнер появлялись, а клиент не получал ответ (обрыв около 0,6 с). Теперь запрос не ждёт лаунчер.

- `POST /api/bots` в режиме docker при `start_container=true` и `skip_container=false`: бот пишется в базу со `status='starting'`, ответ уходит сразу: **201** с телом Bot (итоговый `id`, `status: "starting"`, `container: "starting"`, `recreate_url: null`). Сеть, контейнер и браузер создаёт фоновая задача `start_new_bot` не раньше чем через `BOT_START_DELAY` (0,3 с) после ответа: ответ успевает уйти в сокет до первого вызова лаунчера. Без контейнера (`skip_container`, `start_container=false`, режим local) ответ прежний: 200, `container: "skipped"`, статус `idle`.
- Итог фона: `idle` (контейнер и браузер есть) или `error_starting` (отказ лаунчера; `recreate_url` как раньше). Статус пишется условно (`where status='starting'`): удаление или пересоздание за это время не затираются. Если бота удалили, пока контейнер создавался, контейнер убирается. События: записи журнала `bot_started` и `bot_start_failed` (с `bot_id`; текст ошибки обрезан до 300 символов). Клиент видит итог перечитыванием `GET /api/bots` (поле `status`).
- Повтор: `POST /api/bots` с `id` своего бота в статусе `starting` возвращает этого бота (200, `container: "starting"`), дубль и второй запуск не создаются. Чужой `id` и `id` бота не в `starting` игнорируются (id выдаёт ядро, как раньше; в режиме тестовых id `BOTHUB_TEST_LEGACY_IDS` занятый id остаётся 409). Один бот не запускается параллельно дважды.
- Старт ядра (`recover_after_start`) находит боты в `starting` (ядро остановилось до конца запуска) и доводит их до `idle` или `error_starting` тем же `start_new_bot`; `create_bot` лаунчера идемпотентен, готовый контейнер не пересоздаётся. Пока лаунчер не отвечает, `starting` остаётся в базе.
- Пока бот в `starting`, ввод принимается: сообщение встаёт в очередь (`queued`), `claim_turn` не берёт turn бота в `starting` (как `error_starting` и `no_model`), он выполняется после перехода в `idle`. Расписание и hook создают turn так же.
- Сеть пользователя: при создании пользователя (`POST /api/setup`, `POST /api/invites/accept`) ядро после ответа вызывает `ensure_network(owner_id)` лаунчера фоном (`POST /v1/networks/{owner_id}`, только режим docker). Отказ только пишется в журнал (`user_network_prepare_failed`): `ensure_network` внутри запуска бота остаётся подстраховкой.
- PWA: на сетевую ошибку, 502 и 504 при создании бота экран не показывает ошибку, а перечитывает список ботов и ищет бота по имени и времени создания (не раньше начала запроса); найден: открывает его; нет: ошибка с кнопкой «Повторить». Бот в `starting` показан как «Запускается» (ввод доступен, под полем пояснение: сообщение подождёт запуска); список ботов перечитывается, пока есть бот в `starting`.

Расписание и запуск процедуры (раздел 14): расписание `cron` бота, у которого есть неконечный запуск процедуры (`queued`, `running`, `waiting_approval`, `waiting_model`, `waiting_human`), планировщик пропускает. `next_run_at` не сдвигается, расписание срабатывает одним turn'ом на первом проходе после освобождения бота; сроки, пропущенные за время запуска, не копятся. Ожидание человека ограничено `BOTHUB_PROCEDURE_WAIT_HOURS` (по умолчанию 24 ч), так что откладывание не бесконечно.

### Шаблон бота: экспорт и импорт файлом (2026-10-06, этап 11)

Файл шаблона нужен, чтобы перенести бота на другую установку или поделиться настройками без истории. Формат задаёт ядро, клиент отдаёт его как есть.

`GET /api/bots/{id}/export` (owner бота, чужой бот 404) — JSON-документ:
```json
{"format": "botstead-bot", "version": 1, "name": "Скаут", "role": "…", "instructions": "…",
 "avatar": "scout", "executor": "container", "auto_allow": [{"tool": "…"}], "mcp_allow": ["…"],
 "budget_daily_tokens": 200000, "auto_compact_percent": 80,
 "schedules": [{"cron": "0 9 * * 1-5", "timezone": "Europe/Moscow", "prompt": "…", "enabled": true, "name": "…"}],
 "procedures": [{"format": "bothub-procedure/1", "name": "Вход", "description": "…", "params": […], "steps": […]}]}
```

В экспорте нет: `id`, `owner_id`, `provider_id`/`model_id`, провайдера и модели строками, секретов, памяти, тредов, токенов, расхода, статуса, времени создания, контейнера. `auto_allow` и `mcp_allow` валидируются как обычные правила. Процедуры проходят через `procedures.export_document` (раздел 14), расписания — через `SELECT cron, timezone, prompt, enabled, name FROM bothub.schedules WHERE bot_id=$1 AND kind='cron'` (только cron, без hook и mac_folder).

`POST /api/bots/import` (owner) — тело: тот же документ + опциональные `provider_id` и `model_id` (оба вместе или ни одного, UUID-строкой). Тело ≤ 256 КиБ (`Content-Length` больше — 413). Поля документа: только перечисленные выше; лишний ключ отдаёт 422 `{"error":"invalid","detail":"body: unknown_field: unknown field"}` (значение ключа в ответ не попадает). Каждое поле проверяет тот же валидатор, что у `BotIn`/`ScheduleIn`/`procedures.parse_import` (`name`, `role`, `instructions`, `avatar`, `executor`, `auto_allow`, `mcp_allow`, `budget_daily_tokens`, `auto_compact_percent`); `procedures` — `procedures.parse_import` для каждого, расписания — `check_timezone` и `croniter`. `provider_id`/`model_id` валидируются как UUID-строки; в БД ядро проверяет связку «провайдер владельца и включённая модель» тем же запросом, что в `POST /api/bots`.

Импорт создаёт нового бота, его расписания и процедуры в одной транзакции: ошибка на любом шаге не оставляет полубота. Имя бота и имена процедур (у процедур `unique (owner_id, name)`) при коллизии получают ` (2)`, ` (3)` и так далее, база укорачивается под предел длины. `executor` только `container` или `mac` (иначе 422 `executor: unsupported`). Бот создаётся общей функцией `insert_bot`, той же, что у `POST /api/bots`: связка `provider_id`/`model_id` проверяется тем же запросом (`runner_provider`/`binding.name`). Без `provider_id` раннер получается `fake`, как у `provider: "fake"` в `POST /api/bots`: PWA всегда передаёт выбранную модель, прямой вызов без неё создаёт бота без рабочей модели. Процедуры привязываются к новому боту (`bot_id` ставится при вставке), источник `'import'`. `mac_full_control` всегда `false`. Контейнер стартует так же, как после `POST /api/bots` (`BOTHUB_RUNNER_EXEC=docker`: ответ `"container": "starting"`, запуск фоном после коммита); без docker ответ `"container": "skipped"`. Ответ: запись бота + `recreate_url: null`, статус 201.

PWA: в настройках бота карточка «Экспорт шаблона» (файл `<name>.botstead.json`); на экране `#/bots/new` рядом с «Собрать» кнопка «Создать из файла» (`.botstead.json` или `.json`, до 1 МБ; при разборе показывает имя, роль, число расписаний и процедур, дальше тот же шаг выбора модели и кнопка «Создать»).

## 10. Пользователи, инвайты, сессии (2026-10-04, миграция `004_users_providers.sql`)

Владелец: core. Решение владельца 2026-10-04: админ плюс приглашённые, регистрации с улицы нет. Разделы 10–14 описывают то, что кладёт миграция 004 и что на ней строят этапы 1–7 из `.ai/plan.md`. С этапа 4 `principal()` разделяет пользователей по `user_id`; прежний вход через `OWNER_TOKEN` остаётся временной совместимостью.

```sql
users    (id uuid pk, email text unique check (email = lower(email)), password_hash text,   -- argon2id, PHC-строка
          role 'admin'|'member', status 'active'|'disabled', created_at)
invites  (token_hash text pk, created_by → users, role, expires_at, used_by → users, used_at)
sessions (id_hash text pk, user_id → users on delete cascade, created_at, expires_at, revoked_at, user_agent)
mac_tokens (token_hash text pk, user_id → users unique, created_at, revoked_at) -- миграция 008
```

`invites.token_hash`, `sessions.id_hash` и `mac_tokens.token_hash` проверяются в БД: `check (… ~ '^[0-9a-f]{64}$')`, то есть `sha256(...).hexdigest()` в нижнем регистре. Сырой токен, значение cookie, короткая строка или hex в верхнем регистре дают CHECK-ошибку. Миграция 008 добавляет `sessions.last_extended_at` для ограничения скользящего продления.

- Email хранится в нижнем регистре; ядро приводит его к нему до вставки, CHECK ловит пропуск. Пользователя выключают переводом в `disabled`: на `users.id` ссылаются данные без каскада, `DELETE` пользователя с данными даёт FK-ошибку.
- Пароль длиной от 10 символов хэшируется Argon2id (`argon2-cffi`). В БД хранится только PHC-строка. Жёсткий лимит входа действует для пары email и IP. Для email отдельно растёт задержка до 2 секунд без блокировки. Отсутствие пользователя и неверный пароль дают одинаковый ответ и одинаковую проверку хэша.
- Инвайт: `POST /api/invites` (admin) возвращает токен один раз (32 случайных байта, base64url); в БД только `sha256(token)`. `GET /api/invites` и `DELETE /api/invites/{id}` доступны админу. Публичный `GET /api/invites/check?token=` раскрывает email пригласившего только по действующему токену; причину отказа и данные приглашённого не раскрывает. Погашение (`POST /api/invites/accept`) идёт в одной транзакции: `select … for update` строки инвайта, проверка `used_at is null and expires_at > now()`, создание пользователя с ролью инвайта, запись `used_by`/`used_at`. Срок задаёт админ, по умолчанию 7 суток. Повторное погашение не создаёт второго пользователя.
- Сессия: `POST /api/auth/login` выдаёт cookie `bothub_session` (`HttpOnly; Secure; SameSite=Lax; Path=/bots/` по умолчанию, путь задаёт `BOTHUB_BASE_PATH`), значение 32 случайных байта; в БД `sha256(value)`. Срок 30 суток со скользящим продлением не чаще раза в сутки. `GET /api/auth/me` возвращает текущего пользователя и CSRF-токен. `POST /api/auth/logout`, `POST /api/auth/password`, `GET /api/sessions` и `DELETE /api/sessions/{id}` управляют своими сессиями. Отзыв сессии, смена пароля и `status='disabled'` закрывают соответствующие WS кодом 4401. При записи через cookie (`POST`, `PATCH`, `DELETE`) обязательны `X-CSRF` и проверенный `Origin` или `Referer`; для Bearer CSRF не нужен. WebSocket проверяет `Origin` и сессию при подключении.
- `principal()` возвращает `{kind: 'user'|'bot'|'mac', user_id, role, bot_id?}`. Токен бота (`bot:<id>:<hmac>`) разрешается в `bots.owner_id`. Старые `OWNER_TOKEN`, `MAC_AGENT_TOKEN` и доверенный SSO-прокси-прокси привязаны только к `settings.setup_user_id`. Если настройка отсутствует, пользователь отключён или больше не админ, старый вход получает 401, WebSocket получает 4401. Поиск другого админа запрещён. `settings.legacy_auth_enabled` зависит от способа setup: `true` для `OWNER_TOKEN`, `false` для одноразового кода. `BOTHUB_LEGACY_AUTH=0` принудительно отключает старый вход. `GET /api/auth/me` показывает `legacy_auth` первому админу для предупреждения в UI. Новые Mac-токены выдаются владельцу через `POST /api/mac/token` и отзываются через `DELETE /api/mac/token`.
- Если пользователей нет, `POST /api/setup` создаёт первого админа по `OWNER_TOKEN` или одноразовому коду из лога старта. Повторный вызов возвращает 409. В той же транзакции `settings.setup_user_id` получает ID админа, а все существующие строки с `owner_id is null` в `bots`, `threads`, `memory`, `schedules`, `files`, `push_subscriptions`, `outbox` и `mac_status` переходят ему. Перед запуском воркеров setup помечает зависшие turn как ошибку с причиной `прервано рестартом ядра`.
- Пределы полей публичных маршрутов (`setup`, `login`, `invites/accept`, смена пароля): `email` до 254 символов после `strip` и приведения к нижнему регистру, ровно один `@` с непустыми частями, без пробелов и управляющих символов (одна проверка `parse_email` на все три маршрута); `password`, `old_password`, `new_password` до 512 символов и кодируются в UTF-8 (непарный суррогат и NUL отклоняются); `token` приглашения до 512 символов (длиннее, с NUL или непарным суррогатом: `invite_invalid` 410, у `GET /api/invites/check` `{"valid": false}`); `User-Agent` в сессии обрезается до 512. Превышение или неверный формат: 422 `{"error":"invalid","detail":"<поле>"}`, поле не строка: 400. Тело `/hooks/{id}` в кодировке не UTF-8: 400. Маршрута смены пароля по коду в ядре нет: пароль меняет `POST /api/auth/password` с `old_password`.
- Публичный `GET /api/setup/status` возвращает `{"needs_setup": true}` до создания первого пользователя и `{"needs_setup": false}` после него.
- У действующего инвайта `GET /api/invites/check?token=` возвращает `valid`, `role`, `expires_at` и `invited_by` (email пригласившего). Недействующий токен даёт только `{"valid": false}`. `GET /api/users` дополняет каждого пользователя полями `bots_count` и `last_seen_at`; последнее равно `null`, если сессий ещё не было. `GET /api/sessions` помечает текущую cookie-сессию полем `current: true`.
- Отключение пользователя отзывает его сессии, закрывает Mac-сокет, останавливает активные turn и ставит его расписания на паузу. При повторном включении возобновляются только расписания, которые работали до отключения. Воркеры и вебхуки проверяют `users.status='active'` перед созданием или запуском turn.

### Доступ без SSO-прокси

Для входа по Bot Hub сессии внешний прокси должен пропускать `/bots/` без обязательной сессии SSO-прокси. Это включает PWA статику, `GET /api/setup/status`, `POST /api/setup`, `POST /api/auth/login`, `GET /api/invites/check` и `POST /api/invites/accept`. Пути записаны без префикса `/bots`, который добавляет прокси. Остальные `/api/*` остаются доступны через тот же маршрут: ядро проверяет сессию, CSRF и владельца ресурса. Если закрыть их SSO-прокси, приглашённый пользователь войдёт, но не сможет работать в PWA. `POST /api/setup` принимает только `OWNER_TOKEN` или одноразовый код и после создания первого пользователя возвращает 409. `GET /api/health` можно оставить доступным для проверки состояния. Внешние `/hooks/{id}` проверяют собственный токен. Для WebSocket `/api/ws` и `/agent/mac` токен передаётся в `Authorization: Bearer <token>` или как `Sec-WebSocket-Protocol: bearer, <token>`; query-параметр сохранён для старых клиентов и пишет предупреждение в лог. Вебхук принимает `X-Hook-Token`, query-параметр также временно работает. Если задан `BOTHUB_PUBLIC_ORIGIN`, CSRF и WebSocket сравнивают `Origin` с ним.

### Обновление действующей установки

1. Остановить ядро, сохранить дамп PostgreSQL и проверить, какой активный админ был исходным владельцем данных.
2. Запустить новую версию ядра с закрытым внешним маршрутом. При старте ядро применит миграцию `009_instance_settings.sql`. Если админ уже создан, записать его проверенный ID в `settings.setup_user_id` как JSON-строку, а `settings.legacy_auth_enabled` установить в `true`. Не выбирать ID запросом «первый активный админ» после запуска: результат может измениться при смене роли. Если пользователей ещё нет, настройки заполнит `POST /api/setup`.
3. Проверить `/api/auth/me` со старым `OWNER_TOKEN`, затем вход по паролю и доступ к своим ботам. Пока `setup_user_id` пуст, старые токены и прокси-вход возвращают 401. Проверить миграцию и настройки до открытия внешнего маршрута.
4. Открыть описанные выше пути в прокси. После перехода клиентов на сессии и новые Mac-токены установить `settings.legacy_auth_enabled=false` или `BOTHUB_LEGACY_AUTH=0`, затем проверить, что старые токены получают 401.
- `GET /api/users` и `PATCH /api/users/{id}` доступны админу: он меняет роль и статус, но не выключает и не понижает последнего активного админа. Админ видит данные ботов только своего `user_id`.

**`owner_id`.** Миграция 004 добавляет nullable `owner_id uuid references users(id)` в `bots`, `threads`, `memory`, `schedules`, `files`, `push_subscriptions`, `outbox`, `mac_status` и индекс по нему. Если админ уже существует, миграция 008 передаёт ему строки без владельца и ставит `NOT NULL` для этих восьми таблиц. Если пользователей ещё нет, поля остаются nullable до `/api/setup`: в одной транзакции он передаёт старые строки первому админу и ставит `NOT NULL`. `turns`, `events`, `approvals`, `usage` отдельного `owner_id` не получают: владелец определяется через `thread_id` или `bot_id`, чтобы не хранить противоречащие значения. Согласованность `threads.owner_id = bots.owner_id` проверяет ядро при вставке. Строка с `owner_id is null` не видна пользователю до переноса. Все запросы к пользовательским ресурсам фильтруются по владельцу; чужой идентификатор даёт 404, список пуст. Фоновые задачи, вебхуки и WS-публикация сохраняют того же владельца. В новых таблицах (`providers`, `procedures`) `owner_id` обязателен.

**`mac_status`.** CHECK `id = 1` снят. `id` теперь `default nextval('mac_status_id_seq')`, последовательность стартует со 2, поэтому строка `id=1` сохраняется. Этап 4 хранит состояние Mac по `owner_id`; `mac_socket` и `pending_mac` также разделены по пользователю. Уникальности по `owner_id` в миграции 004 нет: несколько Mac на пользователя планируются в этапе 10.

**Боты и реестр.** `bots.provider_id` и `bots.model_id` nullable. Выбор защищён двумя составными FK: `foreign key (provider_id, owner_id) references providers (id, owner_id) on delete set null (provider_id)` и `foreign key (model_id, provider_id) references models (id, provider_id) on delete set null (model_id)`. Для них у `providers` есть `unique (id, owner_id)`, у `models` `unique (id, provider_id)`. Итог: бот владельца A не может сослаться на провайдера владельца B, а модель обязана принадлежать провайдеру этого же бота; оба отказа ловит БД (`foreign_key_violation`). Составной FK с `on delete set null (колонка)` (PG 15+) работает: список колонок обнуляет только указанную, поэтому удаление провайдера обнуляет `provider_id` и оставляет `owner_id`, а каскад на `models` обнуляет `model_id`; удаление одной модели обнуляет только `model_id`, провайдер остаётся. Бот в обоих случаях живёт, его текстовые `provider`/`model` не меняются. FK с null в паре не проверяется (MATCH SIMPLE), поэтому два CHECK закрывают дыры: `provider_id` требует `owner_id`, `model_id` требует `provider_id`. Ядро по-прежнему отклоняет заведомо неверные запросы раньше БД (400 `invalid`), но защита от чужого провайдера и чужой модели больше не держится на коде ядра. Миграция 013 добавляет `registry_bound boolean not null default false` и помечает `true` ранее привязанных ботов. Бот с `registry_bound=false` и пустым `provider_id` выполняет turn и schedule по текстовым `provider`/`model`, если статус не `no_model` и не `error_starting`. Привязка ставит `registry_bound=true` навсегда. Удаление провайдера сохраняет этот флаг, и бот получает `no_model`. При смене провайдера у бота `provider_id` и `model_id` меняются одним `UPDATE`. Бот без `provider_id` создаётся только в режиме совместимости и только пока реестр владельца пуст; иначе `POST /api/bots` отвечает 400 `provider_id required` (исключение: тестовый раннер `fake`). Режим совместимости определяет `legacy_enabled()`: значение `BOTHUB_LEGACY_AUTH` из `0`, `false`, `off` выключает его всегда; в остальных случаях решает настройка `legacy_auth_enabled` в `bothub.settings` (её ставит первичная настройка: true при setup по `OWNER_TOKEN`, false при setup по одноразовому коду). Бот, который ни разу не был привязан к реестру (`registry_bound=false`), работает через текстовые `provider` и `model` на подписочных логинах своего владельца (том `bothub-login-<владелец>`), его turn и расписания выполняются, recreate не меняет статус. Бот, привязка которого снята удалением провайдера, получает `no_model` и не запускает turn до выбора модели.

**`bots.tool_modes`.** `jsonb not null default '{}'`, в БД проверяется только `jsonb_typeof = 'object'`. Режим разрешения по инструменту (пункт 7 плана): ключ это имя инструмента, значение одно из `allow` (без вопроса), `ask` (спросить через approvals), `command` (только по прямой команде владельца), `deny` (запрещено). Нет записи или `{}`: поведение прежнее (`auto_allow` и approvals, раздел 4). Допустимые значения и имена проверяет ядро; неотключаемый список рисков (раздел 4) режимом `allow` не снимается.

**Идентификатор и имя бота.** Новый бот получает `id = <slug>-<4 случайных символа [a-z0-9]>`: slug из названия (`[a-z0-9-]`, не длиннее 27 символов), затем `-` и четыре случайных символа, итого укладывается в прежние `[a-z0-9-]{1,32}` (раздел 9). Видимое имя хранится отдельно в `bots.name` (любой язык и символы), по `id` оно не восстанавливается. Коллизию `id` ловит PK, ядро повторяет с новым суффиксом (правило `-2`, `-3` из раздела 9 для новых ботов отменяется). Одинаковые видимые имена у разных ботов допустимы. Существующие боты (`scout`, `mac`, `sre` и созданные раньше) сохраняют `id` как есть; формат на них не распространяется, БД его не проверяет.

`DELETE /api/bots/{id}` удаляет бота без связанных тредов, одобрений, памяти, расхода и расписаний; при наличии таких записей возвращает 409. `POST /api/bots/{id}/recreate` пересоздаёт контейнер своего бота. Если лаунчер отказал при создании, бот сохраняется со статусом `error_starting`, а ответ содержит `recreate_url` для повторной попытки.

## 11. Реестр провайдеров, моделей и шлюз

Таблицы `providers`, `models` и новые поля `bots.provider_id`, `bots.model_id`, `usage.provider_id`, `usage.model_id`, `usage.tokens_cache_read`, `usage.tokens_cache_write` создаёт миграция `004_users_providers.sql`. Составные FK удерживают привязку бота в пределах владельца и выбранного провайдера. Старый бот без `provider_id` работает через текстовые `provider` и `model`.

Миграция `012_usage_bigint.sql` переводит `bots.budget_daily_tokens` и четыре счётчика токенов в `usage` на `bigint`. Сумма дневного расхода также вычисляется в `bigint`.

`GET/POST /api/providers`, `PATCH/DELETE /api/providers/{id}`, `POST /api/providers/{id}/check`, `GET /api/models`, `POST /api/models/refresh` и `PATCH /api/models/{id}` доступны только владельцу. Секрет принимается при создании или изменении API провайдера. Ответы возвращают `has_secret`, но не значение секрета. `BOTHUB_SECRET_KEYS` содержит `key_id:base64key`; `encrypt_secret` и `decrypt_secret` из `bothub.secrets` связывают AES-GCM шифртекст с UUID строки через AAD. При запуске ядро проверяет возможность расшифровать все сохранённые секреты. Новые модели включаются, исчезнувшие помечаются `enabled=false`.

Колонка `models.enabled` уже создана миграцией 004. Миграция `010_model_manual_disable.sql` добавляет только `models.manually_disabled` со значением `false` по умолчанию. Для существующих строк с `enabled=false` она ставит `manually_disabled=true`, не меняя `enabled` и остальные поля. Так повторное обнаружение модели сохраняет прежнее отключение, пока владелец явно не включит её.

Создание и `/check` запрашивают список моделей у API провайдера через закреплённый проверенный IP, с таймаутом 15 с и лимитом ответа 1 МиБ. Проверка подписки запускает фиксированную команду `<cli>_status` в login-контейнере. Код выхода команды входа не служит проверкой авторизации. Для `cli_subscription` модели берутся из локальной таблицы CLI, у `agy` из вывода `agy models` (раздел 12). `PATCH /api/bots/{id}` обновляет `provider_id` и `model_id` вместе и очищает `threads.cli_session_id` при смене привязки.
`google_api` пока можно зарегистрировать и проверить, но нельзя привязать к боту: установленный agy не имеет подтверждённого способа выбрать Gemini API backend для одного turn без изменения общего профиля. Попытка привязки получает 400.

**Проверка ключа до сохранения (миграция `015_provider_verification.sql`).** `POST /api/providers` и `PATCH /api/providers/{id}` с полем `secret` сначала проверяют адрес, затем делают ровно один пробный запрос списка моделей с ключом-кандидатом, и только при успехе пишут в БД (ключ, `secret_tail`, `base_url`, модели одной транзакцией). Старый ключ при отказе остаётся нетронутым, бот продолжает получать прежний. После записи повторной проверки нет. Отказ: 422 `{error, detail}`, где `error`: `key_rejected` (401/403 от провайдера), `unreachable` (DNS, сеть, таймаут, 408/429/5xx), `incompatible` (редирект, другой 4xx, ответ не похож на список моделей, список пуст, больше 1 МиБ), `invalid_base_url` (схема, учётные данные в URL, запрещённый адрес; приватный адрес без одобрения сюда не относится, он даёт `pending_admin`). `detail` и `last_error` секрета и кандидата не содержат. `force: true` (только вместе с `secret`) сохраняет без пробного запроса, статус `unchecked`, модели не меняются; правила адреса `force` не обходит. Смена `base_url` требует `secret` в том же запросе. Отключённый (`disabled`) провайдер остаётся отключённым после замены ключа.

`secret_tail`: последние 4 символа ключа, если его длина не меньше 12, иначе `null`. Для строк до миграции `null` до первой замены ключа (шифртекст в SQL не читается). Ответы провайдера возвращают `secret_tail`, `allow_private` и `has_secret`; значения секрета нет нигде.

**Проверил ли сервер ключ (`key_verified`, миграция `024_provider_key_verified.sql`).** У OpenRouter `GET /v1/models` публичный и ключ не смотрит, поэтому «ok» после пробы ничего не говорит о ключе. `openai_compatible` и `openai_api` после успешной пробы (список моделей разобран) делают второй запрос тем же путём и через тот же закреплённый IP с заведомо неверным ключом `Bearer invalid-` и 16 случайными символами. Ответ 401 или 403: `key_verified: true`. Ответ 2xx: `false`, статус остаётся `ok`, но в ответе проверки и в `providers.key_verified` стоит `false`, а PWA показывает предупреждение «Сервер принял запрос без ключа: ключ не проверен». Сеть, таймаут, 5xx и остальные коды: `null`, на статус это не влияет. Второй запрос делит с первым один `PROVIDER_CHECK_TIMEOUT`: ему отдаётся остаток за вычетом секунды запаса, нет остатка, запроса нет. `anthropic_api` и `google_api`: `true` при 200 (неверный ключ они отвергают сами), второго запроса нет. `cli_subscription` и строки до миграции: `null`. Значение пишут `POST` (без `force`), `PATCH` с ключом и `/check`; `force` и неудачная проверка ставят `null`. Второй запрос не считается отдельной пробой в лимите `provider_probe`.

Формы. `POST /api/providers` `{kind, name, secret, base_url?, cli?, force?: bool, allow_private?: bool}` → 201 с провайдером; `PATCH /api/providers/{id}` `{name?, secret?, base_url?, status?: "disabled", force?: bool, allow_private?: bool}` → 200 с провайдером; `allow_private` принимает только admin. Провайдер: `{id, owner_id, kind, cli, name, base_url, status, last_check_at, last_error, created_at, has_secret, secret_tail, allow_private, key_verified}`; `status` один из `new`, `ok`, `error`, `disabled`, `unchecked`, `pending_admin`. Отказ проверки: 422 `{"error": "key_rejected|unreachable|incompatible|invalid_base_url", "detail": "..."}`. Если провайдера успели изменить во время пробного запроса, PATCH отвечает 409. Бот, шлюз и turn работают только с `status=ok`: `unchecked` и `pending_admin` не запускаются, пока `POST /api/providers/{id}/check` (или одобрение админа) не переведёт провайдера в `ok`.

**Приватные адреса через администратора (миграции `015`, `016_provider_approved_ips.sql`).** Поля `providers.allow_private boolean not null default false` и `providers.allow_private_ips text[] not null default '{}'`, статус `pending_admin`. Что открывает одобрение: приватные адреса RFC1918, ULA `fc00::/7` и CGNAT `100.64.0.0/10` (в него входят адреса Tailscale), и только те IP, в которые имя разрешалось в момент одобрения. HTTP допустим только для таких адресов. Любой запрещённый или неодобренный ответ DNS отказывает весь адрес.

Всегда запрещено, одобрение и `PROVIDER_PRIVATE_ALLOW` этого не снимают:
- loopback, link-local (`169.254/16`, `fe80::/10`), multicast, `0.0.0.0`, метаданные облаков (`fd00:ec2::/32`, `100.100.100.200`), NAT64 `64:ff9b::/96`, IPv4-compatible `::/96` (включает `::` и `::1`). IPv4-mapped `::ffff:0:0/96` сводится к IPv4 и проверяется по его правилам.
- подсети собственных сетевых интерфейсов ядра (сети Docker с Postgres и ботами). Ядро читает их при каждой проверке адреса и кэширует на 30 с (`OWN_NETWORKS_TTL`): сеть бота `bothub-u-*`, к которой лаунчер подключил ядро после старта, закрывается не позднее чем через 30 с. Сбой чтения оставляет прошлое значение. Источник: `/proc/net/route` (подсети без шлюза у поднятого интерфейса, с настоящими масками) и `/proc/net/if_inet6`; без `/proc` берутся адреса машины как одиночные хосты. Берутся только подсети интерфейсов, не широкие маршруты: IPv4-префикс короче /8 и IPv6-префикс короче /16 отбрасываются, поэтому маршрут по умолчанию без шлюза (`default dev wg0`) и VPN-пара `0.0.0.0/1` + `128.0.0.0/1` в запрет не попадают. Публичные подсети в список не входят. Если ядро запущено с `network_mode: host`, в запрет попадает и сеть самого хоста.
- сети из `PROVIDER_FORBIDDEN_CIDRS` (список через запятую, см. `deploy/.env.example`). Опечатка в списке останавливает запуск ядра.

Одобрение и DNS rebinding. Участник создаёт `https://llm.lan` (`192.168.1.20`), админ одобряет, затем DNS отдаёт другой приватный адрес, например `172.18.0.2`. Одобрение привязано к набору IP, а не к имени, поэтому такой адрес отклоняется:
- При одобрении (`allow: true` в маршруте ниже) админ передаёт `ips`, то есть `resolved_ips` из списка заявок. Ядро один раз разрешает имя и сверяет множество приватных IP из ответа с `ips` (IPv4-mapped в `ips` сводится к IPv4); при совпадении пишет его в `allow_private_ips`. Без `ips` одобрения нет, одобряется набор, который видел админ, а не то, во что имя разрешится в момент запроса. Имя без ответа DNS одобрить нельзя: 422 `unreachable`. У публичного имени нет приватных IP, одобрять нечего. Для `allow_private: true` в `POST` или `PATCH /api/providers/{id}` админа (его собственный провайдер) набор берётся из того же ответа DNS, на котором идёт проверка.
- `/check`, `POST` и `PATCH /api/providers/{id}` с ключом, шлюз пропускают приватный IP только из `allow_private_ips`. Флаг без набора (пустой `allow_private_ips`, в том числе у строк, одобренных до миграции 016) не одобряет ничего. На устаревший `PROVIDER_PRIVATE_ALLOW` набор не действует.
- Смена адреса в DNS не снимает флаг и набор. Провайдер получает статус `pending_admin`, `last_error` = «адрес изменился, нужно повторное одобрение» и показывается админу как заявка с `reapproval: true`. Статус выставляет первый из трёх: `/check`, отчёт шлюза при отказе по адресу (`app.state.provider_address_changed`), миграция 016 для уже одобренных строк.
- `/check`, `POST` и `PATCH` с ключом при таком расхождении отвечают 422 `{"error": "invalid_base_url", "detail": "адрес изменился, нужно повторное одобрение"}`. `PATCH` не меняет ключ, пробный запрос не уходит. `POST /api/models/refresh` отвечает 200 со статусом `pending_admin`. Шлюз отвечает 502 `invalid provider address` (как для любого запрещённого адреса), и turn завершается ошибкой.
- Повторное одобрение: тот же маршрут `allow-private` с актуальными `ips` из `resolved_ips`; ядро заново разрешает имя и заменяет набор, затем одна проверка возвращает провайдера в `ok` или `error`. Если слоты проб владельца заняты (429), одобрение остаётся записанным, провайдер получает статус `new` и проверяется следующим `/check`.

Права и маршруты:
- Участник (не admin) с адресом, которому нужно одобрение: провайдер создаётся или обновляется со статусом `pending_admin`, пробный запрос не уходит, `/check` и `/api/models/refresh` его не опрашивают, шлюз не находит провайдера (turn отклоняется, модели не запрашиваются). Заявок не больше 5 в час на пользователя (`rate_limit` с ключом `(user_id, provider_admin_request)`), дальше 429 `rate_limited`. Имя, которое не разрешается (422 `unreachable`), и имя с приватным адресом для участника различаются ответом: объединять их нельзя без потери подсказки об опечатке. Перебор ограничен тем же лимитом на заявки.
- Админ в `POST` и `PATCH /api/providers/{id}` может передать `allow_private: true` сразу: набор берётся из того же ответа DNS, на котором идёт проверка и пробный запрос. Участник с этим полем (любое значение) в `POST`, `PATCH /api/providers/{id}` и в маршруте ниже получает 403.
- `PATCH /api/providers/{id}/allow-private` `{allow: bool, base_url?, ips?: [string]}` только admin. `allow: true`: `base_url` и `ips` обязательны (иначе 400 `{"error": "invalid", "detail": "..."}`); `ips` непустой список до 64 строк с IP-адресами, иначе 400. `base_url` сверяется с текущим адресом провайдера (несовпадение: 409). `ips` (после сведения IPv4-mapped к IPv4) должен совпасть с множеством приватных IP, в которое имя разрешается сейчас (несовпадение: 409): админ одобряет именно то, что видел, и смена DNS между списком и PATCH одобрения не даёт. Затем набор сохраняется, одна проверка выставляет статус (`ok` или `error`). `ips` вместе с `allow: false` даёт 400. `allow: false`: флаг и набор сняты, провайдер с приватным адресом становится `pending_admin`; `base_url` не нужен. Ответ: `{id, name, base_url, created_at, email, status, allow_private, allow_private_ips}`.
- `GET /api/admin/provider-requests` только admin: список `pending_admin` по всем пользователям, поля `id`, `name`, `base_url`, `email`, `created_at`, `allow_private`, `approved_ips` (уже одобренные), `resolved_ips` (приватные IP, в которые имя разрешается сейчас, один вопрос DNS с таймаутом 5 с на строку), `reapproval` (флаг уже стоял, адрес сменился), `resolve_error` только при сбое DNS. Секрета, моделей и `secret_tail` нет. Провайдеры, которые участник видит сам (`GET /api/providers` и ответы `POST`, `PATCH`, `/check`), `allow_private_ips` не содержат.
- Смена `base_url` сбрасывает `allow_private` и набор. Шлюз и `provider_lookup` читают флаг и набор при каждом запросе и заново проверяют DNS.
- `PATCH /api/providers/{id}` с пустым или состоящим из пробелов `base_url`: 400 `invalid_base_url` для любого вида провайдера, провайдер не меняется (как до миграции 015; вернуть вид к адресу по умолчанию этим полем нельзя).
- Адрес с путём. `base_url` может нести префикс пути: `https://host/api`. `split_base` (`core/bothub/gateway.py`) режет адрес на origin и `base_path`: хвостовые слэши и хвостовые сегменты `v1` и `v1beta` отбрасываются, потому что шлюз и проба сами дописывают `v1/...`. Поэтому `https://host/api/v1` и `https://host/api` равны и сохраняются как `https://host/api` (`Target.origin`, `Target.base_path`). Сегменты пути состоят из `A-Za-z0-9._~:@+-`, без `.` и `..`, пустых сегментов, `%`, `;` и пробелов: иначе 422 `invalid_base_url` (`invalid provider path`), пробный запрос не уходит. Проба и шлюз ходят на `<проверенный IP>/<base_path>/v1/...`. Повторный ввод того же адреса с `/v1` или слэшем на конце не считается сменой адреса: `allow_private` не сбрасывается. Уже сохранённые адреса с `/v1` нормализуются при использовании, миграции нет.
- Переменная `PROVIDER_PRIVATE_ALLOW` (список хостов) остаётся рабочим глобальным разрешением, но считается устаревшим способом; запрет подсетей ядра и `PROVIDER_FORBIDDEN_CIDRS` действуют и на неё.

Пробные запросы. Каждый запрос к API провайдера идёт через общий лимит по ключу `(user_id, provider_probe)`: не больше 10 в минуту и не больше 2 одновременно на пользователя, лишние получают 429 `{"error": "rate_limited", "detail": "..."}` (`user_id` владельца провайдера). Под лимит попадают `POST` и `PATCH` с ключом (без `force`, с адресом, прошедшим проверку), `POST /api/providers/{id}/check` и `POST /api/models/refresh` для провайдеров с API ключом, проверка после одобрения админом. Подписки (`cli_subscription`) не считаются: запроса к API нет. 429 в `/check` ничего не записывает: статус, `last_error` и `last_check_at` провайдера прежние. `POST /api/models/refresh` при занятых слотах отвечает 200 и отдаёт такие провайдеры без новой проверки. Сверх лимита у `/check` остаются кэш 30 с на провайдера и общая задача: параллельные `/check` одного провайдера делят одну пробу и один слот. Так `force` (создание без пробы) не обходит лимит через `/check`. Проверка адреса (DNS) и пробный запрос одного запроса укладываются в один `PROVIDER_CHECK_TIMEOUT` (30 с, при превышении 422 `unreachable`) и используют один ответ DNS.

Шлюз смонтирован на `/gateway/{provider_id}/`. Маршруты и фильтрация указаны в `docs/gateway.md`. Бот с API провайдером получает на каждый turn токен `gw:<bot_id>:<provider_id>:<turn_id>:<expires>:<hmac>` через env CLI. Ключ подписи `BOTHUB_GATEWAY_TOKEN_SECRET` отделён от `BOTHUB_SECRET_KEYS`. При каждом запросе шлюз проверяет подпись, активный turn, принадлежность провайдера и статус владельца. Настоящий API ключ остаётся в ядре. Запись `usage` создаётся один раз на ответ провайдера с конкретным `turn_id` и четырьмя счётчиками токенов. Дневной бюджет учитывает расход шлюза; usage самого CLI для API привязки повторно не пишется.

## 12. Вход по подписке

- Контейнер входа пользователя живёт между сессиями, но после пересборки образа ботов (другой sha256 у `image`) лаунчер пересоздаёт его при следующем входе: открытые терминалы закрываются, том с логинами остаётся. Так новые CLI в образе появляются и в терминале входа.

`WS /api/providers/{id}/login` принимает только cookie-сессию владельца и проверенный `Origin`. Лаунчер создаёт login-контейнер и открывает PTY командой из своего фиксированного списка. Бинарные кадры несут байты PTY; клиентский JSON допускает `resize` (`cols` 20–300, `rows` 5–100) и `close`. Время простоя ограничено 10 минутами, вся сессия 30 минутами, вывод 1 МиБ/с. Отзыв cookie или отключение пользователя закрывает сокет. Второй вход в тот же провайдер отклоняется кодом 4409. Ядро закрывает PTY после обрыва и не пишет его вывод в события или логи. После выхода выполняется отдельная проверка `<cli>_status`, которая обновляет `providers.status` и список моделей. Если проверка успешна, ядро автоматически пересоздаёт привязанные к провайдеру боты без активного turn. Боты с активным turn получают `need_restart=true` в `GET /api/bots` и пересоздаются после завершения turn. Флаг хранится в БД; пока он установлен, новый turn бота не запускается. Перед следующим turn подписочного бота ядро копирует обновлённые credentials из доступного только владельцу тома в уже работающий контейнер.

Команды входа лаунчера (`login_commands`): `claude` = `claude auth login` (голый `claude` открывает интерактивный сеанс, а не вход), `codex` = `codex login --device-auth`, `agy` = `agy`; статусы: `claude auth status` и аналоги. PWA (`pwa/cli-login.js`) ведёт один из двух сценариев (`loginFlow` в `pwa/terminal.js`):

- `site-code` (claude, agy): терминал печатает ссылку входа, владелец открывает её кнопкой, входит в аккаунт, сайт показывает код, его вставляют в поле «Код из браузера» и он уходит в терминал. CLI завершается сам после приёма кода.
- `screen-code` (codex): терминал печатает ссылку и одноразовый код устройства вида `ABCD-12345`. PWA показывает код крупно, владелец вводит его на странице входа. Поля для кода нет, CLI завершается сам, когда вход подтверждён.

Разбор вывода терминала на клиенте. Ссылка: последняя гиперссылка OSC 8 (`ESC ] 8 ; ; URL` и BEL или `ESC \`; Claude Code печатает так длинный адрес, который в тексте переносится по строкам), иначе последняя законченная ссылка `https` в тексте без управляющих последовательностей. Недописанная ссылка на границе фрагмента не берётся. Берутся только `https` и точные хосты провайдера (без поддоменов, логина, пароля и порта): claude: `claude.ai`, `claude.com`, `platform.claude.com`, `console.anthropic.com`; codex: `auth.openai.com`, `chatgpt.com`; agy: `accounts.google.com`. Код устройства: ровно `XXXX-XXXXX` (A–Z, 0–9) после строки «one-time code», неполный код не берётся. Если за 60 секунд после соединения нет ссылки (у codex ещё и кода), PWA закрывает сессию и предлагает начать заново.

### Сценарии входа (2026-10-06)

Ядро передаёт лаунчеру имя команды `claude`, `codex` или `agy` (поле `cli` провайдера), лаунчер подставляет фиксированную команду из `login_commands`: `claude` → `claude auth login`, `codex` → `codex login --device-auth`, `agy` → `agy`. Оба сценария идут по одному WebSocket и одинаковым кадрам; сценарий выбирает клиент по `provider.cli` (`loginFlow` в `pwa/terminal.js`), ядро и лаунчер их не различают.

- **Код с сайта (`claude`, `agy`).** CLI печатает ссылку входа и ждёт ввода (`Paste code here if prompted >`). Владелец открывает ссылку, входит в аккаунт, сайт показывает код. Клиент отправляет код в PTY как ввод `<код>\r` из поля «Код из браузера». Верный код: CLI выходит с кодом 0. Неверный или просроченный: ненулевой выход, клиент предлагает получить новый код (вход откроется заново, ссылка будет другой).
- **Код с экрана (`codex`).** CLI печатает ссылку `https://auth.openai.com/codex/device` и одноразовый код устройства `XXXX-XXXXX` после строки `Enter this one-time code (expires in 15 minutes)`. Владелец открывает ссылку и вводит этот код на сайте. Ввода в PTY нет: CLI сам опрашивает сервер и выходит с кодом 0 после подтверждения, с ненулевым кодом при просроченном коде. Клиент показывает код отдельной карточкой с кнопкой копирования, поле «Код из браузера» скрыто, после выхода код с экрана убирается.

В обоих сценариях после выхода с кодом 0 действует общий порядок выше: проверка `<cli>_status`, затем пересоздание ботов. Выход с ненулевым кодом клиент показывает как неудачный вход с кнопкой «Получить новый код» или «Начать заново».

### Проверка входа при открытии экрана (2026-10-06)

Экран входа (`pwa/cli-login.js`) сначала проверяет подписку и только потом открывает терминал.

- **Порядок.** Фаза `precheck` («Проверяю вход», спиннер, терминала нет): `POST /api/providers/{id}/check`. Статус `ok`: фаза `done` с заголовком «Вход уже выполнен», списком включённых моделей провайдера и кнопками «Готово» (к карточке провайдера) и «Войти заново». Любой другой исход (статус не `ok`, сеть, 429, 5xx): терминал открывается как раньше. 401 обрабатывает общий обработчик сессии. Ответа ждёт фоновая задача, не сам `view`: экран не остаётся `inert`.
- **«Войти заново».** Пропускает проверку и открывает терминал сразу (`data-act="relogin"`); повторной проверки при этом нет. Дальше всё как в сценариях выше: после выхода с кодом 0 фаза `checking` (опрос `last_check_at`), затем `done` с текстом «Вход выполнен» и «Выбрать модели».
- **`?force=1`.** `POST /api/providers/{id}/check?force=1` обходит кэш проверки (30 с, у agy 10 мин, после ошибки 30 с), но не чаще одного запуска на провайдера за `PROVIDER_FORCE_COOLDOWN` = 5 с. Остальное не меняется: общая задача на провайдера, лимит проб API. Экран входа просит `force=1`, если последний известный статус провайдера не `ok`: свежий вход в другой вкладке не должен висеть за кэшем ошибки.
- **Модели подписки.** Проверка `<cli>_status` собирает stdout из кадров `ExecChunk` (stream `stdout`, до 1 МиБ, декодирование UTF-8 с заменой). Для `claude` и `codex` вывод не разбирается, модели берутся из `SUBSCRIPTION_MODELS`: claude `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-4-5-20251001`; codex `gpt-6-sol`, `gpt-6-luna`, `gpt-6-astra`.
- **Разбор `agy models`.** Команда `agy_status` = `agy models`. Строка вывода `id<TAB>название` (после удаления управляющих последовательностей ANSI): `id` по `[a-z0-9][a-z0-9.-]{1,63}` целиком, название непустое, до 80 символов; прочие строки (заголовки, подсказки, строки без таба) пропускаются, повторы `id` убираются, максимум 50. Если разобралась хотя бы одна строка, список моделей провайдера равен списку `id` (остальные модели отключаются как обычно). Если ни одной, берётся запасной список `SUBSCRIPTION_MODELS['agy']`: `gemini-3.8-flash-high`, `gemini-3.8-flash-medium`, `gemini-3.8-flash-low`, `gemini-3.1-pro-high`. Код выхода не 0 остаётся ошибкой «subscription not authenticated», модели не меняются.

Вывод разбирает только клиент (`pwa/terminal.js`), в памяти страницы; ядро и лаунчер его не разбирают и не хранят.

- **Ссылка.** Приоритет у последней гиперссылки OSC 8 (`ESC ] 8 ; <параметры> ; <URI>`, терминатор `ESC \` или BEL): Claude Code печатает длинный адрес с жёстким переносом по строкам терминала, и целый адрес есть только в OSC 8. Если OSC 8 нет, берётся последняя законченная ссылка `https://` из текста без управляющих последовательностей (за ней пробел или перевод строки), без хвостовой пунктуации. Ссылка, не дописанная до конца на границе кадра, не берётся. Схемы кроме `https` отклоняются.
- **Код устройства.** Ровно `[A-Z0-9]{4}-[A-Z0-9]{5}` не дальше 120 символов после `one-time code`. Неполный код на границе кадра не берётся; при повторном выводе действует последний.
- **Допустимые хосты.** Точное совпадение имени хоста, `https`, без логина, пароля и нестандартного порта. `claude`: `claude.ai`, `claude.com`, `platform.claude.com`, `console.anthropic.com`. `codex`: `auth.openai.com`, `chatgpt.com`. `agy`: `accounts.google.com`. Ссылка с другого хоста кнопкой не становится; если в выводе есть и чужая, и подходящая, берётся подходящая.
- **Ожидание.** Если через 60 секунд после открытия сокета ссылки нет (у codex нет ссылки или кода), клиент закрывает сессию кадром `close` и показывает «Ссылка для входа не появилась» или «Код для входа не появился» с кнопкой «Начать заново». Дальше действуют общие сроки сессии выше (10 минут без ввода, 30 минут всего); код устройства codex живёт 15 минут.

Интерфейс экрана входа переведён на русский и английский: русские строки лежат в `pwa/cli-login.js`, английские в `pwa/i18n/en-extra.js`.

## 13. Браузер бота: состояния управления и noVNC

Владелец: core, bot-image, PWA. У контейнерного бота один headed Chromium на Xvfb. Для Claude ядро выдаёт инструмент `mcp__bothub__browser`; он проверяет состояние в ядре перед вызовом Playwright MCP по CDP и пишет событие с результатом вызова. Прямой Playwright MCP в конфигурацию Claude не включён. Для раннеров Codex и Gemini, а также ботов с `executor='mac'`, браузерные инструменты недоступны.

Состояние `browser_control` бота:

| Состояние | Смысл | Кто действует |
|---|---|---|
| `bot` | по умолчанию, управляет бот | бот; экран у человека только для просмотра |
| `human` | человек перехватил управление | человек в чистом Chromium без порта отладки; инструменты браузера бота отключены |
| `returning` | человек вернул управление (или ядро перезапустилось для контейнерного Claude-бота), бот ещё не перечитал страницу | никто, переходное |

Переходы (остальные запрещены, 409 `invalid_transition`):

- `bot → human`: `POST /api/bots/{id}/browser/takeover`. Порядок: (а) ядро узнаёт адрес активной вкладки бота до остановки (`GET /v1/bots/{id}/browser-tab` лаунчера: первая вкладка типа `page` по CDP `/json/list`; запасной вариант: адрес последнего `browser_step` с `navigate` из событий) и проверяет его `url_forbidden`; пустой или запрещённый адрес заменяется на `about:blank`, перехват из-за адреса не блокируется. Проверяет `human_url` (`core/bothub/browser_control.py`): всё, что отвергает `url_forbidden`, плюс невидимые и меняющие направление текста символы в любой части адреса (хост, путь, query, fragment; хост и в %-кодированном виде): U+00AD, U+034F, U+061C, U+115F, U+1160, U+17B4–17B5, U+180B–180F, U+200B–200F, U+2028–2029, U+202A–202E, U+2060–2064, U+2066–206F, U+3164, U+FE00–FE0F, U+FEFF, U+FFA0, U+FFF9–FFFB, U+1D173–1D17A, U+E0000–E0FFF (один список `HIDDEN_URL_CHARS` на пакет, копия в `launcher/bothub_launcher/validation.py`, тест сверяет оба); хост переводится в punycode (`xn--...`): подмена букв похожими (кириллическая «о» в google.com) видна в адресе. Хост, на котором IDNA 2003 (кодек Python) и UTS 46 (Chromium) расходятся, отклоняется (открывается `about:blank`, `url` в ответе `about:blank`): это `ß`, `ς`, U+200C, U+200D и любой хост, где кодек `idna` и ручная сборка меток через punycode дают разный результат (`faß.de` у Python это `fass.de`, у Chromium `xn--fa-hia.de`); (б) `freeze_bot`: лаунчер прекращает процессы бота под uid 1000 и блокирует новые exec; (в) `browser_mode human` с этим адресом: человек получает чистый Chromium (см. ниже); (г) только после успеха (б) и (в) ядро пишет `browser_control = human`, и ввод человека включается. Ответ содержит поле `url`: адрес, который открыт человеку (в событие `browser_control` он попадает в сокращённом виде `схема://хост/путь`). Сбой заморозки: 502 `freeze_failed`, состояние прежнее (`bot` или `returning`), прокси по-прежнему отбрасывает ввод, в последний тред пишется `browser_control` с `reason: "freeze_failed"` и `to`, равным текущему состоянию, процессы бота размораживаются. Сбой `browser_mode human`: откат (`browser_mode bot`, затем `unfreeze_bot`; если вернуть режим bot не вышло, бот остаётся замороженным), 502 `browser_mode_failed`, состояние прежнее, событие с `reason: "browser_mode_failed"`. При успехе ядро переводит браузерные `pending` и `approved` approvals в `expired`, сохраняет состояние и событие, затем останавливает активные turn бота. Экранный поток остаётся открытым: Xvfb, openbox и x11vnc не перезапускаются, человек, который смотрел экран, видит новый Chromium в том же потоке. Сбой остановки turn возвращает 502 `turn_stop_failed`. Остановка turn по другой причине (stop, таймаут) закрывает экранный поток кодом 4410.
- `human → returning`: `POST /api/bots/{id}/browser/return`. Порядок: (а) ядро записывает состояние `returning`: с этого момента ввод с экрана закрыт; (б) `browser_mode bot`: Chromium человека останавливается, cookies переносятся в профиль бота, каталог экземпляра человека удаляется целиком, буфер обмена X очищается, Chromium бота запускается с CDP; (в) `unfreeze_bot`. Пока режим не bot, бот не размораживается (лаунчер отказывает в `unfreeze_bot` в режиме human). Сбой (б) или (в): 502 `launcher_failed`, состояние остаётся `returning` (ввод закрыт, бот заморожен), повторный return (`retry_return`) идемпотентно выполняет (б) и (в) заново и доводит дело до конца, второе событие не пишется. Вернуться из `returning` в `human` можно только новым полным takeover, который снова замораживает бота. Если запись состояния (а) не удалась, лаунчера ядро не трогает: человек остаётся в `human`, бот заморожен. Таймауты: лаунчер ограничивает весь `browser_mode` (ожидание замка, запись режима, остановка и старт Chromium, ожидание готовности, отчёт о cookies) 45 секундами (`BROWSER_MODE_TOTAL_TIMEOUT` в `launcher/bothub_launcher/service.py`) и отвечает ошибкой; ядро ждёт ответ дольше (`BROWSER_MODE_TIMEOUT`, 60 секунд, `core/bothub/launcher_client.py`), поэтому всегда получает ошибку лаунчера, а не обрыв. Порядок констант проверяет `launcher/tests/test_wire_compat.py`. Ввод с экрана включён только в состоянии `human`, которое ядро записывает после успешных заморозки и `browser_mode human`.
- `returning → bot`: после успешного `browser_snapshot` или `browser_navigate` в активном turn (клик и ввод по старой странице до этого: 409 `browser_stale`). `/api/browser/authorize` выдаёт одноразовый `authorization_id`; `/api/browser/step` принимает его для этого же бота и turn. Отсутствующий, чужой, просроченный или повторно использованный id возвращает 409. Пока состояние `returning`, остальные браузерные действия возвращают `409 browser_stale`.
- `returning → human`: повторный `takeover`.
- Каждый переход пишет событие `browser_control` (`kind` из раздела 3 расширяется им; payload `{from, to, by: user_id, reason}`) в последний тред бота; если треда нет, ядро создаёт его. Состояние хранится в колонке `bots.browser_control`, время перехода и инициатор в памяти ядра. После рестарта `returning` получают только боты с `executor='container'` и `provider='claude'`: человек мог управлять их экраном, пока ядро лежало. Все остальные боты получают `bot`. Approvals для браузерных инструментов, выданные до рестарта, переводятся в `expired`. Метка заморозки в лаунчере переживает рестарт, поэтому при старте ядро для каждого контейнерного бота (после сброса состояний на старте `human` среди них нет) сначала вызывает `browser_mode bot`, затем `unfreeze_bot`, независимо от провайдера. Режим `human` лежит в томе браузера и переживает рестарт контейнера и лаунчера (супервизор возобновляет ту же сессию человека, если токен маркера совпадает с токеном файла режима), но не рестарт ядра: при старте ядро переводит ботов в `returning` (контейнерных Claude-ботов) или `bot` и вызывает `browser_mode bot`, поэтому Chromium человека останавливается, cookies переносятся, а каталог человека удаляется. `unfreeze_bot` вызывается независимо от исхода `browser_mode bot` (сбой режима пишется в журнал как `browser_startup_mode_failed`): остановленный контейнер режим сменить не может, но метка заморозки с него должна сняться, иначе пересозданный контейнер отказывает в каждом exec. Рядом с живым Chromium человека лаунчер бота не разморозит (`unfreeze_bot` отказывает в human), а при создании, пересоздании и старте контейнера режим human без метки заморозки (остался в томе от остановленного контейнера) переводится в bot. Сбой разморозки ядро не останавливает: он пишется в журнал (`browser_startup_unfreeze_failed`), бот остаётся замороженным, а его turn завершается с причиной `bot_frozen` и пояснением для владельца.
- `GET /api/bots/{id}/browser` → `{state, since, by}`.

Чистый браузер человека (`browser_mode`, лаунчер):

- `POST /v1/bots/{id}/browser-mode` `{mode: "human"|"bot", url?}` → `{bot_id, mode, changed, cookies}`, идемпотентна. `GET /v1/bots/{id}/browser-tab` → `{bot_id, mode, url}` (`url` равен `null` в human и если браузер не отвечает). Служебные поверхности Chromium (цели типа `page` с адресом `chrome://*`, `chrome-extension://`, `chrome-untrusted://`, `chrome-error://`, `devtools://`) вкладками не считаются и пропускаются; закрытая политикой новая вкладка (`chrome://newtab/`, `chrome://new-tab-page/`) отдаётся как `about:blank`. `POST /v1/networks/{owner_id}` → `{owner_id, network, core_connected}`: сеть пользователя и подключение к ней ядра без контейнера (повтор безопасен; ядро зовёт её фоном при создании пользователя). Лаунчер проверяет `url` сам: только `http`, `https` и `about:blank`, без пробелов, управляющих символов, невидимых и меняющих направление текста символов и обратной косой черты, до 2048 символов.
- Режим хранит файл `~/.browser-mode` (`bot` или `human`) в томе браузера под uid 1001, адрес для человека лежит в `~/.browser-human-url`. Лаунчер пишет их через `docker exec --user 1001` (адрес идёт через stdin, не в argv; сначала адрес, потом режим, оба через rename), читает `chromium-supervisor.sh`. Нет файла: bot. Любое другое содержимое: Chromium не стартует вовсе. Супервизор не поднимает Chromium бота с CDP в human никогда: ни после падения Chromium, ни после рестарта стека, ни после рестарта контейнера.
- human: супервизор останавливает Chromium (TERM, через 10 секунд KILL, затем добивает семейство процессов) и запускает новый без `--remote-debugging-port` и без `--remote-debugging-pipe`, с экземпляром в одном каталоге `~/.config/botstead-browser-human` (создаётся пустым) и ровно одной вкладкой с адресом от ядра (`-- <url>`). В каталоге всё, что пишет Chromium человека: `--user-data-dir` (сам каталог), `--disk-cache-dir=<каталог>/cache`, `--crash-dumps-dir=<каталог>/crash`, а `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME`, `TMPDIR` и `HOME` (там `~/.pki`) указывают на подкаталоги в нём, все 0700: HTTP-кэш, дампы, временные файлы и NSS-база не попадают в общие `~/.cache`, `/tmp`, `/dev/shm`. Маркер сессии `~/.browser-human-session` (вне каталога, обычный файл 0600, содержимое `session <токен>`) есть, пока сессия идёт. Токен (32 hex) лаунчер генерирует на каждый перехват и пишет в файл режима: `~/.browser-mode` держит `human <токен>`; повторная запись human при идущей сессии оставляет прежний токен. Каталог стирается перед входом в human всегда: при переключении с bot безусловно, в том числе когда Chromium бота перед этим упал (супервизор помнит предыдущий режим через паузу после падения); при старте супервизора и после падения Chromium человека каталог остаётся только если маркер несёт тот же токен, что файл режима. Такой каталог переживает рестарт контейнера, лаунчера и супервизора посреди активной сессии. Chromium бота (тот же uid 1001) может подложить и каталог, и маркер, но токен будущей сессии не знает: подложенный каталог стирается. Режим human без токена не возобновляется никогда. Каталог без подходящего маркера недоверенный: его стирают. При возврате в bot cookies переносятся, если маркер жив (токена в файле режима к этому моменту уже нет); подложенный маркер даёт боту только слияние в его собственный профиль. Не удалось стереть старый каталог: Chromium человека не стартует. Порт 9222 не слушается. Готов, когда процесс прожил не меньше двух секунд, в его командной строке нет `remote-debugging` и CDP не отвечает.
- bot: супервизор останавливает Chromium человека, переносит cookies (только при маркере сессии), очищает буфер обмена X (`xsel --clear` для PRIMARY и CLIPBOARD, `xprop -root -remove` для cut buffers CUT_BUFFER0–7 корневого окна, не дольше 3 секунд каждый; cut buffers отдельно, потому что `xsel --clear` их не трогает, а x11vnc кладёт в CUT_BUFFER0 текст из буфера клиента; `xprop` приходит из пакета `x11-utils`), удаляет каталог человека целиком и запускает Chromium бота с CDP как раньше. Готов, когда CDP отвечает. Если каталог удалить не удалось, Chromium бота не стартует (иначе бот получил бы доступ к данным человека): режим не становится готовым, лаунчер отвечает ошибкой, ядро остаётся в `returning`, супервизор повторяет попытку каждые 5 секунд. Итог переноса лежит в `~/.browser-merge-status`; лаунчер возвращает его в `cookies` (`{merged: N}` или `{error}`). Если каталог не удалился и возврат повторяется, повторное слияние находит уже перенесённые cookies и даёт `merged 0`: первый успешный итог остаётся до конца перехода, `failed` заменяется успешным повтором, файл стирается при следующем входе в human.
- Xvfb, openbox и x11vnc при смене режима не перезапускаются, меняется только Chromium. Оба экземпляра запускаются с одним `--password-store=basic`, иначе зашифрованные значения cookies не читались бы в другом профиле.
- Что переносится: из профиля бота в профиль человека ничего. Из профиля человека обратно только таблица `cookies` (`bot-image/cookie_merge.py`): строка человека заменяет строку бота с тем же ключом `(host_key, top_frame_site_key, name, path)`, остальные cookies бота остаются, слияние идёт одной транзакцией. Слияние запускается под `python3 -I` и не дольше 20 секунд (супервизор убивает зависший процесс, статус `failed`); профиль, каталоги по пути, база и её `-journal`, `-wal`, `-shm` обязаны быть обычными файлами и каталогами без ссылок (у базы одна жёсткая ссылка); соединение работает с `PRAGMA trusted_schema=OFF`; триггеры в любой из баз дают отказ до первой записи (в профиле бота код бота мог их заложить); если базы бота нет, база человека копируется через временный файл и ставится атомарно. Сбой или таймаут слияния не мешают ни удалению каталога человека, ни старту Chromium бота; итог в `~/.browser-merge-status`. Переносятся только persistent cookies: session cookies Chromium на диск не пишет. Cookie, которую человек удалил, в профиле бота остаётся. Не переносятся localStorage, IndexedDB, service workers, расширения, настройки, история и всё остальное. Сбой слияния не оставляет профиль человека: вход пропадает, `cookies.error` сообщает об этом.
- Закладки бота не видят ввод человека: скрипт, вкладка-перехватчик, service worker и изменённые настройки остались в профиле бота и в другом процессе Chromium, у которого нет порта отладки. Каталог человека недоступен uid 1000 по правам файлов. Пока `human`, лаунчер не принимает exec и отказывает в `unfreeze_bot`.
- Адрес для человека: ответ takeover содержит `url` (host в punycode; адреса с невидимыми символами и символами управления направлением текста отклоняются, открывается `about:blank`), тот же адрес открыт единственной вкладкой. PWA это поле пока не показывает: человек видит адрес только в адресной строке Chromium. Страницу входа выбрал бот, она может быть фишинговой: проверять адрес должен человек.
- Что переживает возврат: только cookies (слияние в профиль бота). Кэш страниц, история, автозаполнение, localStorage, временные файлы и отчёты о сбоях экземпляра человека лежат в одном каталоге и удаляются вместе с ним; буфер обмена X (PRIMARY, CLIPBOARD и cut buffers CUT_BUFFER0–7) очищается при входе в `human` и при выходе. Если каталог удалить не удалось, Chromium бота не запускается, состояние остаётся `returning`.

Контейнеры ботов создаются с `--security-opt seccomp=<профиль>`, профиль `deploy/seccomp/bot.json` генерирует `deploy/seccomp/build_profile.py` из профиля Moby: `clone` и `unshare` разрешены без условия по `CAP_SYS_ADMIN`, `setns`, `mount` и `clone3` (ENOSYS) закрыты, а `chroot` открыт: песочница Chromium вызывает его внутри своего user namespace и без него падает (проверено на стенде; флаг генератора `--no-chroot` закрывает его, Chromium тогда не стартует). `socket` ограничен `AF_UNIX`, `AF_INET`, `AF_INET6` и rtnetlink с uevent. `setsockopt` и `getsockopt` разрешены, кроме опций netfilter на уровнях `SOL_IP` (0) и `SOL_IPV6` (41): `setsockopt` с optname 64, 65, 96, 97, 128, 129 и `getsockopt` с 64–67 (на `SOL_IPV6` вместо 66 и 67, это `IPV6_RECVTCLASS` и `IPV6_TCLASS`, закрыты 68 и 69), 96–99, 128–131 дают `EPERM`; на двух этих уровнях закрыто и всё от 128 (нативных опций там нет). Правила построены масками по всем 64 битам аргумента: ядро берёт `level` и `optname` как `int`, и значение со старшими битами не должно проходить как «другой уровень». Путь профиля задаёт секция `[seccomp] profile` в `deploy/launcher.toml`; лаунчер не стартует без файла, который разбирается как JSON с `defaultAction`; через API профиль не меняется. Login-контейнеры идут на стандартном профиле. Коду бота user namespaces закрывает второй фильтр `bot-guard` (`unshare`, `setns` и `clone` с `CLONE_NEWUSER` дают `EPERM`, `clone3` даёт `ENOSYS`, чужая архитектура и x32 убивают процесс): лаунчер ставит `/usr/local/libexec/bot-guard` первым элементом команды перед каждым `docker exec` под uid 1000 (`exec`, терминал входа, `stop_exec`, заморозка и проверка процессов) и требует абсолютный путь исполняемого файла. Весь `entrypoint.sh` тоже стартует под `bot-guard` (`ENTRYPOINT ["/usr/local/libexec/bot-guard", "/usr/local/bin/entrypoint.sh"]` в образе; лаунчер не задаёт `--entrypoint` и команду для ботов), поэтому у bash и его детей второй фильтр есть с первой инструкции, а entrypoint читает из `/home/bot` только обычные файлы (`-f`, не FIFO) и с ограничением по времени. Браузерные команды uid 1001 идут без `bot-guard`. Если у каталога меток заморозки не удаётся выставить `chmod 0700`, лаунчер отвечает `503 state_error` с текстом «почините права каталога на сервере, бота пересоздавать не нужно».

Вызовы для одного бота выполняются последовательно: замок на бота (`asyncio.Lock` по id) общий с takeover, return и прокси ввода, поэтому клавиши двух вызовов не перемешиваются. Ответ 400 (`{error: "invalid", detail}`) не содержит введённого значения: `detail` называет поле и причину, исходное значение из ошибки валидации не попадает в ответ ни в этом, ни в других маршрутах, а для полей `secret`, `password`, `token`, `value`, `key`, `credential` причина заменяется на `invalid value`.

Маскирование делает одна функция, `mask_browser_args` в `core/bothub/browser_control.py`: `value` и `text` заменяются на `[redacted]`, `url` сводится к `схема://хост[:порт]/путь` (логин, query и fragment отбрасываются, адреса со схемой не http и не https не показываются). Функция применяется к `browser_step`, к `tool_call` и `tool_result` в парсерах Claude и Codex, вторым слоем в ядре при записи событий хода (`BrowserEventMasker`), в `POST /api/approvals` и в `approve` на стороне бота, так что значение до ядра не доходит. В approvals в `args`, `args_hash` и `op_hash` лежат замаскированные аргументы, а решение принимается по исходным. Результат вызова `fill` отбрасывается целиком, потому что Playwright печатает введённый текст в коде; в результатах остальных вызовов адреса сводятся так же, как в аргументах. Значения полей в тексте snapshot маскирует `mask_input_values` (`core/bothub/browser_control.py`): у строк с ролью `textbox`, `searchbox`, `combobox`, `spinbutton`, `slider` значение после `]:` или в кавычках заменяется на `[скрыто]`, роль, имя, атрибуты и `ref` сохраняются (`- textbox "Password" [ref=e5]: hunter2` становится `- textbox "Password" [ref=e5]: [скрыто]`). Разбор учитывает значения с `]:` и кавычками внутри и значения на нескольких строках (многострочным бывает только `textbox`; у остальных ролей строка `- ...` глубже по отступу это дочерний узел, а не продолжение значения); `option` не маскируется: `- option "Russia" [selected]` остаётся читаемым, выбор виден в замаскированной строке `combobox`; обычный текст страницы не меняется. Маскирование стоит в инструменте `browser` (`core/bothub/mcp_server.py`) до того, как текст уйдёт модели и попадёт в подписи approvals (`page_label`), и во втором слое `mask_browser_text` для событий.
- Адрес навигации (`url_forbidden`, `core/bothub/browser_control.py`). Разрешены `http`, `https` и `about:blank`. Запрещены: другие схемы (`file:`, `chrome:`, `chrome-extension:`, `devtools:`, `view-source:`, `javascript:`, `data:`, `blob:`), адрес без схемы, логин в адресе и обратная косая черта; адреса loopback, link-local (в том числе 169.254.169.254), частные сети RFC 1918, ULA, CGNAT и все остальные не глобальные адреса, включая числовые записи (`127.1`, `0x7f.1`, `2130706433`), IPv4 внутри IPv6, 6to4 и NAT64; имена `localhost`, имена без точки (`core`, `gateway`), `.local`, `.internal` и похожие суффиксы, домены вида `nip.io`, хосты из `BOTHUB_BROWSER_DENY_HOSTS` и хост из `BOTHUB_URL`. Хост с `%`-кодированием (`127.0.0.1%2e`, `10.0.0.%31`, `169.254.169.%32%35%34`) раскодируется и проверяется по правилам выше; если после раскодирования остаётся `%` (двойное кодирование), управляющие символы, `/`, `?`, `#`, `@` или `\`, адрес отклоняется как `url_invalid`. Хост приводится к виду, который увидит браузер: после раскодирования NFKC, ideographic, fullwidth и halfwidth точки (`。`, `．`, `｡`) становятся `.`, затем снимаются конечные точки, и так повторяется, пока значение не перестанет меняться (`127.0.0.1。`, `127.0.0.1..`, `127.0.0.1.。`, `%31%32%37.0.0.1%E3%80%82` проверяются как `127.0.0.1`). `%` в пути и query проверку не затрагивает. Проверка стоит в трёх местах: инструмент `browser` в контейнере до обращения к ядру, `POST /api/browser/authorize` (403 `url_forbidden`, в `detail` код причины) и `POST /api/approvals` (approval сразу получает `rejected`, в тред пишется `approval_dec` от `system` с `reason`; владельцу вопрос не приходит, одобрить такой адрес нельзя).
- Риск действий (`core/bothub/risk.py`). `snapshot` и `screenshot` одобряются без вопроса. `navigate` на разрешённый адрес спрашивает владельца. `fill` в поле, похожее на секретное (пароль, код, токен, номер и CVV карты), и `click` на оплату, удаление или вход получают метки `login`, `pay`, `delete`: они спрашивают каждый раз, правило и «запомнить» их не разрешают. Метка `pay` ставится по платёжным оборотам и глаголам: карта (`Привязать карту`, `Добавить карту`, `Сохранить карту`, `Add card`, `Save card`, `Номер карты`), деньги (`Оплатить картой`, `Подтвердить платёж`, `Пополнить баланс`, `Перевести`, `Перевод средств`, `Вывести средства`, `Продлить подписку`, `Transfer`, `Top up`, `Withdraw`, `Renew subscription`) и покупка (`Pay now`, `Place order`, `Checkout`, `Оформить заказ`, `Купить`); корни слов целиком не берутся, поэтому «Картинки», «Яндекс Карты», «Карта сайта», «Карточка товара», «Sort by order date», «Payload size», «Перевод текста», «Переводчик», «Transfer-Encoding» и одинокое «Renew» оплатой не считаются. Метка считается по описанию элемента (`element`, `target`) и по подписи элемента со страницы (`page_label`): `mcp_server` берёт её из snapshot по ref, поэтому кнопку оплаты, названную моделью иначе, ядро всё равно узнаёт. Остальные `navigate`, `click` и `fill` запоминаются по паре (действие, origin) правилом `{tool, scope: "browser_origin", match: {action, origin}}`. Origin навигации берётся из адреса; origin для `click` и `fill` берётся из поля `origin`, которое `mcp_server` ставит по строке `Page URL` в ответе Playwright. Вызов с одним ref без описания и без известного origin запомнить нельзя. Неизвестное действие и лишние ключи в аргументах требуют ручного подтверждения.

### Что гарантируется теперь

- Пока состояние `human`, инструменты браузера бота отключены (`409 human_in_control`), процессы бота под uid 1000 остановлены, новые exec заблокированы, а человек работает в чистом Chromium без порта отладки и с пустым профилем. Ввод человека проходит в браузер только после успешной заморозки; при сбое заморозки (`502 freeze_failed`) управление остаётся у бота, ввод отбрасывается, событие записано.
- Перехват не рвёт экран человека: turn останавливается, сокет и сессия лаунчера остаются.
- После рестарта ядра только контейнерные Claude-боты получают `returning` и должны перечитать страницу; остальные остаются в `bot`.
- Значение, введённое человеком через экран или `secret-input`, не попадает в события, approvals, логи и ответы ядра, в том числе в ответ 400. Модель получает snapshot страницы, в котором значения полей ввода заменены на `[скрыто]`.
- Текст, который бот вводит инструментом `fill`, не сохраняется ни в событиях, ни в approvals, ни в их хэшах; адреса в событиях сведены к схеме, хосту и пути.
- Бот не открывает инструментом браузера адреса вне политики: проверка стоит в контейнере, в ядре и в approvals, одобрение владельца такой адрес не открывает.
- Оплата, удаление, вход и ввод в секретные поля всегда проходят через владельца и не запоминаются.
- Пределы длины (2026-10-05): элементы `mcp_allow` строки 1–200 символов, у правил `auto_allow` поле `tool`, если есть, строка 1–200 символов, в обоих списках до 200 элементов; `client` в `POST /api/threads/{id}/turns` и `POST /api/approvals/{id}/decide` до 64; `timezone` расписания (`POST /api/schedules` и `schedule` у `POST /api/bots`) 1–64 символа и имя из `zoneinfo`; `device` в `POST /api/push/subscribe` до 200. Превышение и неизвестная зона: 422 `{"error":"invalid","detail":"..."}` (detail называет поле, значение в него не попадает). Остальные ошибки схемы по-прежнему 400; если в запросе есть и ошибка предела, и обычная ошибка схемы, ответ 400.
- Текст на входе (2026-10-05, правки Opus 2, 3, 5). Любая строка тела и любой ключ на любой глубине: без NUL и кодируется в UTF-8 (непарный суррогат из JSON). Проверка общая: базовый класс всех моделей запроса (`Body`) и тип `JsonObject` у маршрутов с телом-словарём; нарушение: 422 `{"error":"invalid","detail":"<верхнее поле> contains a NUL or an invalid character"}`, значения в ответе нет; вложенность JSON глубже 64: 422. Исключения: `POST /api/invites/accept` (токен с NUL или суррогатом даёт 410 `invite_invalid`, как неизвестный токен) и `/hooks/{id}` (тело уходит в prompt как есть, `\u0000` в нём проходит). Токены, cookie, заголовок Authorization и код setup с NUL: 401 без обращения к базе; `token_hash`, `token_equals` и `csrf_token` на непарном суррогате не бросают исключение. Идентификатор с NUL в пути `DELETE /api/invites/{id}` и `DELETE /api/sessions/{id}`: 404. Для остальных путей запасной вариант: `CharacterNotInRepertoireError` и `UntranslatableCharacterError` из базы отвечают 400 `invalid`, не 500. Правила `auto_allow`: `pattern` до 500 символов, `op_hash` до 128, `scope` до 64, `match` объект до 64 ключей (ключ до 200 символов, значение до 4096; не строка считается по каноническому JSON), нарушение: 422 (не строка там, где ждут строку, и `match` не объект: 400). Общий предел тела запроса 1 МиБ (`BODY_MAX`, чистый ASGI-слой: по `Content-Length` сразу, без него по принятым байтам): 413 в формате `{error, detail}`. `multipart/form-data` (`POST /api/files`) и прокси шлюза `/gateway/…` (промпты CLI, свой предел 32 МиБ) этим пределом не ограничены.
- Ошибки схемы не несут значений (2026-10-05). `PATCH /api/bots/{id}` отвечает как `POST /api/bots`: 422 на предел длины, иначе 400, `detail` строится из `validation_detail` (поле и причина; текст самой `pydantic.ValidationError`, где лежат введённые значения, наружу не уходит). Лишнее поле в теле: `detail` `"<путь>: unknown field"` без имени ключа (имя пришло от клиента и может быть непечатным). Место ошибки в `detail` обрезается до 100 символов и приводится к кодируемому виду.

### Старт ядра при недоступном лаунчере

Ядро стартует всегда: недоступный лаунчер не роняет lifespan. Часть старта, которой нужен лаунчер, выполняет фоновая задача (`launcher_startup_sync`): повторы с паузой 1 с, вдвое больше после каждой неудачи, до 30 с (`LAUNCHER_SYNC_DELAY_START`, `LAUNCHER_SYNC_DELAY_MAX`), без предела числа попыток, отмена при остановке приложения. Lifespan ждёт только первую попытку и не дольше 3 с (`LAUNCHER_SYNC_FIRST_WAIT`): при живом лаунчере сверка кончается до первого запроса.

- Сверка идемпотентна. Шаг 1: проверка `list_bots` (режим docker) и разморозка всех контейнерных ботов вне `human` (замок строки бота, как раньше). После него `app.state.launcher_ready` становится истинным. Шаг 2: `recover_stale_turns` (процесс останавливается раньше, чем turn помечается `error`, поэтому повтор после сбоя лаунчера остановит его снова) и пересоздание ботов с `need_restart`. После шага 2 запускается worker. Scheduler и outbox_sender от лаунчера не зависят и стартуют сразу. Сброс `browser_control` при старте (`human` и всё прочее в `returning` для контейнерных ботов Claude, остальные в `bot`) делается до этого в БД и от лаунчера не зависит.
- `GET /api/health` поле `launcher`: `ok` только после шага 2 (`app.state.launcher_synced`), между шагами `syncing`, до шага 1 `unavailable`. Каждая неудачная попытка даёт одну запись `launcher_startup_sync_failed`: warning для попыток 1–4, с пятой (`LAUNCHER_SYNC_ERROR_AFTER`) error с трассировкой; текст исключения в поле `error`.
- Пока `launcher_ready` ложен, маршруты, которым нужен лаунчер, отвечают 503 `{"error":"launcher_unavailable"}`: takeover, return, secret-input, `POST /api/browser/authorize` и `/api/browser/step` (бот не получает ни разрешения на шаг, ни доступа к браузеру: после рестарта лаунчер ещё мог держать бота замороженным под человеком), `POST /api/bots/{id}/recreate`, `DELETE /api/bots/{id}`, `POST /api/bots/draft`, `POST /api/bots` с запуском контейнера в режиме docker. WebSocket экрана и входа по подписке закрываются с кодом 1013 `launcher_unavailable`. Проверка подписочного провайдера отвечает как при отсутствии лаунчера (статус `error`). `GET /api/bots/{id}/browser` и список ботов отдают состояние из БД: это только показ, прав оно не даёт. Остальное API работает.
- Порядок проверок во всех этих маршрутах: аутентификация, CSRF, владелец и существование ресурса (чужой бот: 404), разбор тела (ошибка схемы: 400 или 422), и только потом 503 `launcher_unavailable`. Так 503 не показывает чужому, что бот существует и что запрос дошёл до обработки. Для маршрутов бота (`/api/browser/*`) то же: сначала токен бота и принадлежность turn боту (404), состояния 409, затем 503. У WebSocket экрана сначала Origin, сессия, владелец (4401, 4404) и конфликт сессии (4409), потом 1013. Если лаунчер не настроен вообще (`launcher=None`), порядок и коды те же, что до введения сверки: 503 стоит там, где проверка на `None` была раньше.
- Без настроенного лаунчера (режим local) фоновой задачи нет, `launcher_ready` истинен с первого запроса.

### Что остаётся

- Пока управление у бота, его процессы (uid 1000) могут обратиться по loopback к CDP (9222), у которого нет пароля, и оставить в профиле бота скрипт, service worker или изменённые настройки. Во время `human` эти закладки не видят ввод: человек в другом процессе Chromium с другим профилем и без CDP. После `return` Chromium бота снова их исполняет, и они видят всё, что делает бот, включая перенесённые cookies человека. Код с правами uid 1001 (скомпрометированный браузер) этой гарантией не закрыт. Экран (x11vnc) отдаётся только через unix-сокет в каталоге uid 1001 (0700), TCP-порта нет; openbox запущен с конфигом образа без привязок клавиш, Execute и меню, политики Chromium (root, read-only) закрывают расширения, native messaging и загрузки. В интерфейсе писать только: «Модель не получает экран и не действует, пока управляете вы».
- Адрес проверяется по тексту. DNS не разрешается: публичное имя, указывающее на частный адрес, редирект с публичного сайта на внутренний адрес и подресурсы страницы проверка не видит. Здесь работает только сетевая изоляция бота (`docs/isolation.md`); исключения `[[allow]]` и `[[host_allow]]` в `deploy/launcher.toml` расширяют доступ и для браузера.
- Подпись элемента берёт страница. Кнопка оплаты с подписью «Далее» классифицируется как обычная, а запомненное для origin правило разрешит клик по ней. Формат строк snapshot и строки `Page URL` разобран по образцу вывода Playwright MCP и на живом стенде не проверен.
- Одноразовый `authorization_id` связывает вызовы authorize и step, но успешность `browser_snapshot` сообщает MCP-клиент. Ядро не подтверждает чтение страницы независимо.
- Маскируются известные поля (`value`, `text`, `url`), результат `fill` и значения полей ввода в snapshot (роли `textbox`, `searchbox`, `combobox`, `spinbutton`, `slider`). Остальной текст snapshot и скриншоты, которые видит модель, содержат то, что есть на странице, в том числе значения в полях, чьи роли сюда не входят, и пароль, показанный на скриншоте; сводка результата в событиях ограничена 500 символами, адреса в ней сведены к пути. Gemini не отдаёт событий инструментов, при их появлении маппинг нужно пропустить через `BrowserEventMasker`.
- Скомпрометированный браузер (uid 1001) создаёт user namespaces и внутри них получает capabilities над своими namespace. Закрыто профилем: `mount`, `bpf`, `io_uring`, `userfaultfd`, `setns`, `clone3`, семейства сокетов кроме `AF_UNIX`, `AF_INET`, `AF_INET6` и `AF_NETLINK` с `NETLINK_ROUTE` и uevent (то есть нет `AF_PACKET` и netfilter через netlink), опции netfilter, arp_tables и ebtables через `setsockopt` и `getsockopt` на `SOL_IP` и `SOL_IPV6` (класс CVE-2021-22555). Открыто: сами user namespaces и `chroot` в них, обычные сокеты и rtnetlink в собственном сетевом namespace, остальные опции сокетов и вся поверхность ядра, которую профиль Docker оставляет любому контейнеру. Данным бота (uid 1000) uid 1001 мешают только права файлов. Остаточный риск описан в `docs/isolation.md`, для недоверенных ботов рекомендован `runtime = "runsc"`.
- Не проверено на живом Docker: смена режима браузера (`browser_mode`) против настоящего Chromium (в тестах Chromium, X и openbox заменены заглушками; проверки для стенда: `deploy/tests/isolation_check.sh`, секция «Режим human», пункт 11 в шапке), формат записей `/json/list` и порядок вкладок в нём (берётся первая вкладка типа `page`), сброс cookies Chromium при TERM, заморозка при takeover против реального лаунчера, поведение Playwright MCP на запрещённых адресах и формат его ответа, число фильтров `Seccomp_filters` у PID 1 после перевода entrypoint под `bot-guard` (ожидается 3), профиль `bot.json` с правилами `setsockopt` (Docker принимает профиль и не упирается в лимит 4096 инструкций BPF), `x11vnc -inetd` под `socat UNIX-LISTEN` и noVNC против него, openbox с `/etc/bothub/openbox-rc.xml`, применение политик Chromium (`chrome://policy`), noexec-tmpfs `/home/browser/Downloads`. Команды и ожидаемый результат: `deploy/tests/isolation_check.sh`.

## 14. Процедуры (записанные действия)

Владелец: core (таблицы и воспроизведение), PWA (список, правка, запуск). Процедура = последовательность структурированных шагов браузера. Источники: вызовы Playwright MCP самим ботом (`source='bot'`), показ человека через рекордер (`human`), файл (`import`).

```sql
procedures     (id uuid pk, owner_id → users not null, bot_id → bots on delete set null, name, description,
                params jsonb array, steps jsonb array, source 'bot'|'human'|'import', status 'draft'|'active'|'archived',
                version int, created_at, updated_at, unique (owner_id, name))
procedure_runs (id uuid pk, procedure_id → procedures on delete cascade, procedure_version, bot_id, thread_id, turn_id,
                status 'queued'|'running'|'waiting_approval'|'waiting_model'|'waiting_human'|'done'|'failed'|'stopped',
                params jsonb object, steps jsonb array not null default '[]' (снимок, миграция 018), next_step int, step_log jsonb array,
                error, started_at, finished_at, created_at,
                reason, approval_id → approvals on delete set null, attempt int not null default 0, in_flight bool not null default false,
                secret_params jsonb array not null default '[]' (миграция 019, «Воспроизведение»))
```

**Шаг** (элемент `steps`):

```json
{"id": "s3", "action": "fill", "target": {"role": "textbox", "name": "Email"},
 "value": "{{email}}", "secret_ref": null,
 "precondition": {"url_matches": "^https://example\\.com/login"},
 "expect": {"visible": {"role": "button", "name": "Войти"}},
 "safe_to_retry": true, "risk": "none"}
```

| Поле | Значение |
|---|---|
| `id` | строка, уникальна в процедуре |
| `action` | `navigate`, `click`, `fill`, `press`, `select`, `wait`, `assert` |
| `target` | `{"url": …}` для `navigate`; иначе `{"role": …, "name": …}` (основной способ), запасной `{"selector": css}` (только CSS, см. «Селектор»); для `press`/`wait` может быть null |
| `value` | строка, допускает `{{param}}` из `params`; значения секретов сюда не попадают |
| `secret_ref` | `vault:<имя>` вместо `value` для паролей и токенов; взаимоисключающе с `value`. `<имя>` это `secrets.name` (раздел 11): ядро ищет сначала секрет бота запуска (`owner_id` = владелец процедуры, `bot_id` = бот запуска), затем общий (`bot_id is null`); нет ни того ни другого: шаг проваливается, запуск `failed` с `error='secret_not_found'`. Значение расшифровывается при выполнении шага и в `step_log`, события, `procedure_runs.params` и контекст модели не пишется |
| `precondition` | что должно быть верно до шага: `url_matches` (regex), `visible` (target). Не выполнено: запуск переходит в `waiting_human` с `reason: precondition_failed` (`waiting_model` исполнитель этапа 7Б не ставит, см. «Воспроизведение») |
| `expect` | что должно быть верно после шага: `url_matches`, `visible`, `text`, `timeout_ms` (по умолчанию 5000). Не выполнено: шаг считается проваленным |
| `safe_to_retry` | можно ли повторить шаг без побочных эффектов (чтение, навигация, переключатель в известное состояние) |
| `risk` | `none`, `pay`, `send`, `delete`, `login`, `push`, `exec`, `other` (значения `approvals.risk` плюс `none`); вычисляет ядро, клиент может только повысить |
| `flags` | необязательно: жёсткие метки, которые не поместились в `risk` (`["login"]` у шага с `risk: "pay"`); считает ядро, присланное игнорируется, ключ есть только когда массив не пуст |

Правила воспроизведения (без модели, через Playwright):

- Запуск (routine): `POST /api/procedures/{id}/run`, тело `{bot_id, thread_id, params}`. Запуск всегда привязан к боту и треду: `bot_id` берётся из тела, иначе из `procedures.bot_id`; бот должен принадлежать пользователю, тред боту (иначе 400 `invalid`); без `thread_id` ядро заводит новый тред бота. Нет бота ни в теле, ни в процедуре: запись `procedure_runs` создаётся сразу в статусе `failed`, `error='no_bot'`, шаги не выполняются (запуск остаётся в истории и виден расписаниям). Все approvals запуска создаются в этом треде (`approvals.thread_id` = `thread_id`, `bot_id` = бот запуска, `turn_id` = `procedure_runs.turn_id`, если он есть): владелец решает их на том же экране, что и обычные.
- Подстановка параметров и проверка условий при запуске: `procedures.resolve_step` и `procedures.match_url` (ниже, «Подстановка параметров при запуске» и «Regex»). Условие `url_matches`, которое не совпало или вышло за 200 мс, считается невыполненным.
- Параметры: `params` процедуры описывает `[{name, type, required, default, secret}]`; запуск задаёт значения в `procedure_runs.params`; неописанный параметр в `value` отклоняется при сохранении. Параметр с `secret: true` (по умолчанию `false`) принимает только ссылку `vault:<имя>` (само значение отклоняется) и без `default`: в `procedure_runs.params`, `step_log` и событиях лежит ссылка, значение подставляется из `secrets` в момент шага (ссылка, которой нет в `secrets`, отклоняется при запуске, 400 `invalid`).
- Запуск продолжается с `next_step`; после падения ядра или паузы идёт с него, а не сначала. `next_step` увеличивается только после проверки `expect`.
- Шаг с `risk` не `none`, любой `login` и любой ввод секрета (`secret_ref`, секретный параметр) проходят через approvals (раздел 4) на каждом запуске; `args_hash` считается от шага с подставленными параметрами и origin страницы. Статус запуска `waiting_approval`. Неотключаемый список рисков (раздел 4) правилом `remember` не снимается.
- Элемент не найден или `precondition` не выполнено: задумка контракта это статус `waiting_model` (ядро ставит turn боту с контекстом шага и текущей страницей, правка шага применяется после подтверждения владельцем, процедура получает новую `version`, запущенные до правки `procedure_runs` сохраняют свою `procedure_version`). Исполнитель этапа 7Б (`bothub/procedure_runner.py`) модельный разбор не делает: запуск идёт в `waiting_human`, причина в поле `reason` (`element_not_found`, `element_ambiguous`, `precondition_failed`, ...), решает владелец через `decide`. Статус `waiting_model` остаётся допустимым в схеме и в PWA, исполнитель его не ставит.
- Провал `expect`: при `safe_to_retry` до 2 повторов, иначе запуск `failed`. Шаг с неизвестным исходом (обрыв посреди действия) и `safe_to_retry=false` автоматически не повторяется: статус `waiting_human`, человек решает. Запуски в `running` на момент рестарта ядра ведут себя так же: шаг с `safe_to_retry=true` повторяется с `next_step`, остальные уходят в `waiting_human`.
- Состояние браузера `human` (раздел 13) приостанавливает запуск (`waiting_human`); после `returning → bot` запуск продолжается с шага, который не успел завершиться, с повторной проверкой `precondition`. После рестарта ядра браузер в состоянии `returning`, а `waiting_human` остаётся статусом запуска: он переживает рестарт (хранится в БД) и снимается тем же переходом `returning → bot`.
- `step_log`: массив `{step_id, status: 'ok'|'failed'|'skipped', at, duration_ms, error?}`; без значений параметров, помеченных секретными, и без снимков страницы.
- API: `GET/POST /api/procedures`, `GET/PATCH/DELETE /api/procedures/{id}`, `POST /api/procedures/{id}/run`, `GET /api/procedure-runs/{id}`, `POST /api/procedure-runs/{id}/stop`, `POST /api/procedure-runs/{id}/decide`, `GET /api/secrets`; все выборки по `owner_id` пользователя. Ниже добавлены `POST /api/procedures/from-turn`, `POST /api/procedures/import`, `GET /api/procedures/{id}/export`, `GET /api/procedures/{id}/runs`.

### Уточнения (этап 7, часть А: сохранение, импорт, запись из действий бота; миграция 017)

Код проверки: `core/bothub/procedures.py`, маршруты в `core/bothub/main.py`. Воспроизведение запусков (`run`, `stop`, `decide`) описано ниже, в «Воспроизведение (этап 7, часть Б)».

**Статус `draft`.** Миграция `017_procedure_draft.sql` добавляет `draft` в check `procedures.status`, остальная схема не меняется. `draft` значит: в процедуре есть шаг `fill` без значения (`needs_value: true`), запуск запрещён. Статус вычисляет ядро: пока такой шаг есть, `draft`; когда все заполнены, `active`; `archived` задаёт только владелец через `PATCH {"status": "archived"}`, он сохраняется, пока владелец сам не вернёт `active`. `PATCH {"status": "active"}` при незаполненных шагах: 422. Клиент `draft` не задаёт. `POST /api/procedures/{id}/run` для `draft` и `archived`: 409 `not_runnable`.

**Шаг, уточнения.** Допустимые ключи шага: `id`, `action`, `target`, `value`, `secret_ref`, `precondition`, `expect`, `safe_to_retry`, `risk`, `needs_value`, `needs_secret`, а также `flags` и `computed_risk`, которые ядро считает само: присланные игнорируются, чтобы клиент мог вернуть шаги в том виде, в каком получил; другие ключи отклоняются (422 `unknown_field`). В ответе у каждого шага есть все ключи контракта (`null`, `false` или вычисленное значение); `needs_value`, `needs_secret` и `flags` только когда `true` или не пусто; `computed_risk` есть в ответах API у каждого шага, но не хранится и в экспорт не попадает.
- `id`: `[A-Za-z0-9_-]{1,64}`, уникален. `role`: `[a-z][a-z0-9-]{0,63}`. Цель `{role, name}` (`name` может быть пустой строкой) или `{selector}`, не вместе. Параметр `{{имя}}` допустим в `name` и в адресе `navigate`, в `selector` нет (422 `param_in_selector`: по селектору риск не определить). `navigate`: `target` только `{url}`, `value` и `secret_ref` не допускаются. `click`: цель обязательна, `value` и `secret_ref` нет. `fill`: цель обязательна, ровно одно из `value` (непустая строка) и `secret_ref`, либо `needs_value`. `select`: цель и `value` обязательны. `press`: `value` (клавиша) обязательно, цель по желанию. `wait`: нужна цель или `value`, `value` это миллисекунды строкой до 60000. `assert`: цель обязательна, `value` по желанию. `secret_ref` только у `fill`, формат `vault:<имя>`, имя `[A-Za-z][A-Za-z0-9_-]{0,63}` (как `secret-input.save_as`); существование секрета при сохранении не проверяется, его ищет запуск (см. выше).
- **Селектор** `{selector}` только обычный CSS: отклоняются `>>`, префиксы движков Playwright (`xpath=`, `text=`, `css=`, `id=`, `data-testid=` и любое `имя=` в начале, `internal:`), `//`, `..`, ведущая `/`, текст в кавычках и любые псевдоклассы и псевдоэлементы (`:has-text`, `:text`, `:visible`, `:light`, `:hover`, `:nth-child`, `::before`), а также незакрытая кавычка или скобка (422 `selector_not_css`, путь `…selector`, значение в ответ не возвращается). Строки в кавычках и содержимое `[…]` не проверяются, поэтому `a[href^="https://x"]` и `input[value=".."]` принимаются; экранированное `\:` (класс `md\:flex`) тоже. Проверка одна и та же в `procedures.css_selector_ok` и в `cssSelectorOk` исполнителя. Исполнитель проверяет то же самое и ищет по `page.locator('css=' + селектор)`: движок задан явно.
- **Секрет только в приведённую страницу.** `fill` из хранилища (`secret_ref` или единственная подстановка секретного параметра) сохраняется, если раньше в процедуре есть `navigate` или у шага задан `precondition.url_matches` (иначе 422 `secret_no_context`, путь `steps[i].precondition`). У такого шага `safe_to_retry` всегда `false`: ввод секрета автоматически не повторяется.
- `precondition`: `url_matches`, `visible`. `expect`: `url_matches`, `visible`, `text`, `timeout_ms` (целое от 100 до 60000, по умолчанию 5000 при воспроизведении). Пустой объект сохраняется как `null`.
- Пределы: шагов до 200, `params` до 50, `name` до 120 (после `strip`, не пусто), `description` до 2000, любая строка шага до 2000 символов, regex до 300. Превышение: 422. Лишнее поле в теле запроса: 400, как у остальных маршрутов.
- Параметры: `{name, type, required, default, secret}`; `name` `[A-Za-z_][A-Za-z0-9_]{0,63}`, уникально; `type` `string|number|boolean` (по умолчанию `string`); `required` по умолчанию `true`; `secret` по умолчанию `false`. Секретный параметр: тип `string`, `default` только `null` (любое значение 422).
- Подстановки `{{имя}}` (пробелы внутри скобок допустимы, имя регистрозависимо) разбираются в `value`, `target.url`, `target.name`, `expect.text`, `expect.visible`, `precondition.visible` (имя). В `target.selector` подстановок нет. Не объявленное в `params` имя, а также одиночные `{{` и `}}`: 422. В `url_matches` подстановок нет, `{{` там 422. Секретный параметр допустим только в `value` шага `fill`, в любом другом месте 422.
- Адрес `navigate` без подстановки проверяется `url_forbidden` при сохранении (запрещённый адрес 422, в тексте ошибки только код причины). Адрес с `{{param}}` при сохранении не проверяется: проверка откладывается до запуска, и запуск обязан применить `url_forbidden` к адресу после подстановки перед каждым `navigate`, как к живому действию.

**Regex (`url_matches`).** Строка до 300 символов (`regex_too_long`), компилируется (`re`), иначе 422 `regex_invalid`. `url_matches: null` это то же, что поле не задано (как у `visible`). Защита от катастрофического перебора двойная.

(а) Статическое правило при сохранении. Повтор с `high - low > 10` (`*`, `+`, `{n,}`, `{0,200}`) считается неограниченным. Неограниченный повтор в шаблоне не больше одного (`regex_unbounded`) и не внутри группы с повтором. Сумма верхних границ ограниченных повторов не больше 200 (`?` это 1, `{3}` это 3; `regex_budget`). Запрещены: любой повтор внутри группы, которая может повториться больше одного раза (`(a+)+`, `(a{2}){3}`, `(?:/[^/]+)*`; `regex_nested`), альтернатива внутри такой группы (`(a|aa)+`, `(ab|cd)*`; `regex_alternation`), обратные ссылки и условные группы (`regex_backreference`), lookahead и lookbehind (`regex_lookaround`). Допустимы `(www\.)?`, `(en|ru)`, `(a+)?`, один `.*`, ограниченные повторы вроде `\d{1,3}`.

(б) Сопоставление при воспроизведении: `procedures.match_url(pattern, url)` (async, возвращает `(совпало, таймаут)`). Адрес режется до 2048 символов (`MATCH_URL_MAX`), поиск (`re.search`) идёт в отдельном процессе: `ProcessPoolExecutor` с одним воркером (запуск `spawn`, воркер прогрет заранее, чтобы старт процесса не съедал предел). Дольше 200 мс (`MATCH_URL_TIMEOUT`): воркер убивается, результат `(False, True)` («не совпало» плюс признак таймаута), следующий вызов поднимает новый. Параллельные вызовы идут по очереди (один воркер), event loop не блокируется. Процесс не запустился (нет семафоров в песочнице): тоже `(False, True)`. Битый шаблон: `(False, False)`.

**Риск шага.** При сохранении (создание, `PATCH` шагов или параметров, импорт, запись из turn) ядро вычисляет риск шага и хранит в `risk` строгую метку. Порядок: `none < other < send < push < exec < delete < login < pay`. Метки по шагу:

- `click`, `select` (как click) и `fill`: классификатор живых действий браузера (`risk.classify`, инструмент `mcp__bothub__browser`) по роли, имени и селектору цели; `risk.browser_labels` отдаёт все подходящие метки, а не первую. Подпись перед классификацией проходит свёртку омоглифов (`risk.homoglyph_variants`: кириллица и греческий, похожие на латиницу, и обратно; «Pаy» с кириллической «а» это pay), так же для списка слов секретного поля. `other` классификатора это `none` шага. `other` ставится не ниже, если в `target.name` есть параметр, если `fill` идёт в безымянное поле (имя пусто после очистки) или в поле по селектору. `fill` в секретное поле получает ещё `login`.
- `navigate`: адрес с параметром даёт `other` (итог проверит `resolve_step`); иначе `pay`, если адрес (host, путь, query) содержит как отдельное слово `checkout`, `payment`, `payments`, `pay`, `oplata`, `оплата` или `billing` (слова режутся по всему, что не буква и не цифра, перед этим снимается %-кодирование; `paypal`, `prepaid`, `payload` не считаются); иначе `none`.
- `press` с целью как click. `press` клавишами Enter, NumpadEnter, Space (без учёта регистра) без цели отправляет форму и наследует метки всего, что шло в страницу с последнего `navigate`: `fill`, `select`, `click` и `press` с целью; значение с параметром считается отправкой. Клик без риска («Далее» между вводом карты и Enter) наследование не сбрасывает: где кончается форма, по записи не видно, лишнее подтверждение безопасно. Сбрасывает его только `navigate` (новая страница). Остальные клавиши, `wait`, `assert`: `none`.
- Когда шагу подходят несколько меток, `risk` равен строжайшей, остальные жёсткие метки и `send` лежат в `flags` по убыванию строгости: шаг, которому нужны оплата и вход, хранит `risk: "pay"`, `flags: ["login"]`.

Клиент присылает `risk` необязательно. Не прислал: ставится вычисленный. Прислал выше: сохраняется он, вычисленная метка уходит в `flags`. Прислал ниже вычисленного: 422 `steps[i].risk: risk_below_computed`. Не из списка: 422 `risk_invalid`. Импорт и `from-turn` не жалуются, риск там просто пересчитывается. `computed_risk` (вычисленный без повышения клиентом, с наследованием у `press`) ядро добавляет к каждому шагу в ответах `GET/POST/PATCH /api/procedures*`; PWA берёт его нижней границей выбора риска и не отправляет `risk`, пока выбор не тронут.

**Поле как секрет.** `fill` в секретное поле не принимает `value`: нужен `secret_ref` (422 `steps[i].value: secret_required`, значение в ответ не возвращается). Секретное поле это поле, у которого классификатор даёт `login` (пароль, токен, код, ключ API, одноразовый код и т. п.) или чьё название после очистки от управляющих и невидимых символов, NFKC, удаления пробелов, дефисов и подчёркиваний и приведения к нижнему регистру содержит одно из: `cvv`, `cvc`, `card number`, `номер карты`, `срок действия`, `security code`, `код подтверждения`, `одноразовый код`, `otp`, `2fa`, `passwort`, `kennwort`, `contraseña`, `mot de passe`, `senha`, `пароль` (слова приведены к той же форме: `cardnumber`). Совпадение по подстроке, поэтому лишнее срабатывание (`footprint` содержит `otp`) безопасно: поле просто потребует секрет. Исключение: `value` из одной подстановки `{{p}}` параметра с `secret: true`; в запуск придёт ссылка `vault:<имя>`, не значение.

Безымянное поле и поле по селектору определить нельзя (селектор проходит те же проверки, что имя). При ручном сохранении литерал в них допустим, но риск шага не ниже `other`. Запись из действий бота (`from-turn`) ставит такому `fill`, как и любому, `needs_value: true`, а безымянному и секретному ещё `needs_secret: true`: человек сам решит, нужен ли секрет. Запуск не доверяет сохранённому: `resolve_step` отклоняет литерал в поле, которое стало секретным после подстановки параметра в имя.

**Управляющие и невидимые символы.** `target.role` и `target.name` (в том числе в `precondition.visible` и `expect.visible`) отклоняют управляющие (Cc) и невидимые форматирующие (Cf: bidi U+202A–U+202E и U+2066–U+2069, нулевой ширины U+200B–U+200F, U+2060, BOM U+FEFF, мягкий перенос U+00AD) символы, кроме обычного пробела: 422 `control_chars` (роль: `invalid`). Неразрывный пробел допустим. События бота (`POST /api/browser/authorize` и `/step`) не отклоняются: `role` и `name` в теле вычищаются от таких символов до проверки формата и до `secret_field`, поэтому bidi не прячет слово «пароль» от классификатора. `from-turn` чистит имя так же (события, записанные раньше). `mcp_server._remember_page` берёт имя только из кавычек строки snapshot: экранированная кавычка и обратная косая разбираются, `\n` и `\t` становятся управляющими символами (ядро их вычистит). У строки без кавычек имя пустое: текст после двоеточия это значение поля или содержимое страницы, не имя (он остаётся только в подписи для approvals, `page_label`).

**Запись из действий бота.** `POST /api/procedures/from-turn` `{thread_id, turn_id?, name}`: тред свой (иначе 404), `turn_id` принадлежит треду (иначе 404). Берутся события `browser_step` этого turn (без `turn_id` всего треда) по `seq`, не больше 5000 (больше: 422). Правила: `snapshot`, `screenshot` и события с `result` не `ok` отбрасываются; подряд идущие `navigate` на один адрес (после отбрасывания) схлопываются; `navigate.url` берётся из события, то есть без query и fragment (маскирование раздела 13). `click` и `fill` получают цель `{role, name}` из события; нет роли или имени: 422 (шаг без цели не воспроизвести). `fill` получает `value: null`, `secret_ref: null`, `needs_value: true`, а для секретного (`secret` в событии или `secret_field`: классификатор и список слов выше) и безымянного поля ещё `needs_secret: true`. `safe_to_retry`: `true` у `navigate`, `false` у остальных. Идентификаторы шагов `s1..sN`. Результат: `source='bot'`, `bot_id` бота треда, `description=''`, `status` по правилу выше (`draft`, если есть `fill`), риск вычислен (`press` в записи нет: бот его не вызывает). Нет ни одного шага: 422. Шагов больше 200: 422. Имя занято: 409. Ответ 201.

**Импорт и экспорт.** `GET /api/procedures/{id}/export`: `{format: "bothub-procedure/1", name, description, params, steps}`, без `owner_id`, `bot_id`, идентификаторов, `version`, `source`, `status`, `last_run` и без `computed_risk` у шагов (шаги отданы как хранятся: с `flags` и `needs_value`). Мок PWA и e2e отдают и ждут тот же формат. `POST /api/procedures/import`: тот же объект (`format` по желанию, иначе должен совпасть; `description`, `params`, `steps` по желанию); любое другое поле (`owner_id`, `bot_id`, `id`, `version` и т. д.): 400. Проверка полная, как при создании; `risk` пересчитывается без ошибки (меньше вычисленного заменяется вычисленным, больше сохраняется); `source='import'`, `bot_id=null`, `version=1`, `status` по шагам. Имя занято: 409. Ответ 201.

**CRUD.** `GET /api/procedures?bot_id=&status=` (свои; `status` один из `draft|active|archived`, иначе 400; сортировка по `updated_at` по убыванию). `POST /api/procedures` `{name, description?, bot_id?, params?, steps?}` отвечает 201 (`source='human'`, `version=1`; `bot_id` чужой или несуществующий: 404; `source` и `status` из тела не принимаются). `PATCH` принимает `name`, `description`, `bot_id` (`null` отвязывает), `params`, `steps`, `status`; `version` растёт на 1, только если нормализованные `params` или `steps` отличаются от сохранённых; при смене `params` или `steps` проверяются оба вместе (подстановки против новых параметров); пустое тело и `null` в `name`, `description`, `params`, `steps`, `status`: 400. `name` уникально на владельца: 409 `conflict` при `POST`, `PATCH` и импорте. `DELETE` удаляет строку и каскадом `procedure_runs`; 409 `conflict`, если есть запуск в `queued`, `running`, `waiting_approval`, `waiting_model` или `waiting_human`; ответ `{"ok": true}`. Воспроизведение, которое создаёт запуск, обязано взять блокировку строки процедуры (`for share` или `for update`) перед проверкой статуса, иначе оно разойдётся с `DELETE`.

**Запуски (чтение).** `GET /api/procedures/{id}/runs` (последние 100, новые сверху) и `GET /api/procedure-runs/{id}` отдают строки `procedure_runs` целиком (с `steps`), доступ через владельца процедуры, чужие 404. Запуск, остановка и решение: «Воспроизведение (этап 7, часть Б)».

**`last_run` и `computed_risk` в ответах.** Процедура в ответах `GET /api/procedures`, `GET /api/procedures/{id}`, `POST`, `PATCH`, `from-turn` и `import` содержит `last_run`: `{id, status, started_at, finished_at, error}` последнего запуска (по `created_at`) или `null`, и у каждого шага `computed_risk` (см. «Риск шага»). Экспорт их не содержит.

**Снимок шагов запуска (миграция 018).** `018_procedure_run_steps.sql` добавляет `procedure_runs.steps jsonb not null default '[]'` с проверкой «массив». Создание запуска копирует в него `steps` процедуры версии `procedure_version` в нормальном виде (секретов в шагах нет, только `secret_ref`). Воспроизведение идёт по снимку, а не по нынешним шагам процедуры: правка процедуры после запуска не меняет шаги запуска и смысл `next_step` и `step_log`. `GET /api/procedure-runs/{id}` и `GET /api/procedures/{id}/runs` отдают `steps` с остальными полями; PWA рисует экран запуска по снимку (у записей без снимка, `steps` пуст, берутся нынешние шаги процедуры с пометкой о версии). Запуск создаёт `POST /api/procedures/{id}/run` (часть Б).

**Решение по запуску (`decide`).** `POST /api/procedure-runs/{id}/decide` `{"action": "retry" | "skip" | "stop"}`: решение владельца для запуска в `waiting_human` (шаг с неизвестным исходом и `safe_to_retry=false`, рестарт ядра, возврат браузера). `retry` повторяет шаг с `next_step`, `skip` пропускает его (запись `step_log` со статусом `skipped`, `next_step` растёт на 1) и продолжает, `stop` останавливает запуск. Порядок проверок: доступ (404 чужому и несуществующему), тело (`action` не из списка, лишнее поле, не строка: 400), затем 409 `conflict` для запуска не в `waiting_human`; успех отвечает строкой запуска (200). Маршрут в матрице `test_stage4_route_matrix.py` и `test_stage4_route_matrix_db.py` как `resource`. PWA показывает на экране запуска в `waiting_human` три действия, каждое с подтверждением: «Повторить шаг», «Пропустить шаг», «Остановить запуск» (пока браузером управляет человек, повтор и пропуск скрыты: сначала «Вернуть управление боту»).

**Список секретов.** `GET /api/secrets` (владелец, сессия): `[{name, bot_id}]`, имена сохранённых секретов текущего пользователя (`secrets.owner_id`): сначала общие (`bot_id` null), затем по боту, внутри по имени. Значений и шифртекста в ответе нет, чужие секреты не видны. PWA показывает выбор из этого списка для `secret_ref` вместо ручного ввода имени; если список недоступен, имя вводится вручную. Токен бота 403, без входа 401. Маршрут в обеих матрицах (`secret_list` в БД-матрице: чужое имя в ответе не появляется).

**Формат ошибок проверки.** Любая ошибка проверки процедуры (кроме 400 схемы тела, 404, 409, 501): 422 `{"error": "invalid", "detail": "<путь>: <код>: <короткий текст>"}`, например `steps[1].value: secret_required: a secret field requires secret_ref`. Путь называет место в теле (`steps[2].target.name`, `params[0].name`, `name`, `format`, `steps`, `status`, `events[0].target`). Код причины стабилен, по нему PWA переводит ошибку на русский; текст короткий, английский и не содержит значений клиента (имена параметров, слова клиента, адреса и шаблоны в нём не повторяются). Коды: `type`, `too_long`, `too_many`, `empty`, `unknown_field`, `invalid`, `duplicate`, `required`, `not_allowed`, `mutually_exclusive`, `placeholder_invalid`, `param_undeclared`, `param_in_selector`, `param_in_regex`, `param_missing`, `secret_param_misplaced`, `secret_required`, `secret_not_found`, `control_chars`, `url_forbidden`, `risk_invalid`, `risk_below_computed`, `regex_invalid`, `regex_too_long`, `regex_unbounded`, `regex_budget`, `regex_nested`, `regex_alternation`, `regex_backreference`, `regex_lookaround`, `unsupported`, `target_missing`, `steps_need_values`, `selector_not_css`, `secret_no_context`. 409 при занятом имени: `name is already used`.

**Подстановка параметров при запуске.** `procedures.resolve_step(step, params, secrets_lookup=None, *, secret_params=())` возвращает `(шаг, значения_не_журналировать)`. `params`: значения запуска по имени (у секретного параметра там `vault:<имя>`, какие параметры секретные, говорит `secret_params`); `secrets_lookup(имя)` достаёт значение секрета в порядке из таблицы полей. Подстановка идёт в один проход: значение параметра вставляется как есть и повторно не разбирается (`{{other}}` в значении остаётся текстом). Подставляются `target.name`, `target.url`, `value`, `expect.text` и `visible` условий. Адрес `navigate` после подстановки проходит `url_forbidden` (`step.target.url: url_forbidden`), `wait` после подстановки проверяется снова. Риск пересчитывается по итоговой цели, результат `max(сохранённый, пересчитанный)`: «Оплатить» в имени кнопки даёт `pay`, адрес с `pay` в host даёт `pay`. Литерал в поле, ставшее секретным после подстановки, отклоняется (`secret_required`); секрет, которого нет в хранилище: `secret_not_found` (запуск `failed` с `error='secret_not_found'`). В набор «не журналировать» попадают значения секретов (из `secret_ref` и секретных параметров) и значение `press` из одного печатного символа (клавиши могли набирать пароль). Запуск не пишет эти значения в `step_log`, события, approvals, логи и контекст модели. Ошибки `resolve_step` несут путь `step...` (запуск ставит свой путь через параметр `path`).

### Воспроизведение (этап 7, часть Б)

Код: `core/bothub/procedure_runner.py` (исполнитель `ProcedureRunner`, хранилище `PgStore`), операция лаунчера `procedure_step` (раздел 13 и `docs/isolation.md`), исполнитель в контейнере `bot-image/procedure-step.mjs`. Миграция `019_procedure_runner.sql` добавляет к `procedure_runs` поля `reason`, `approval_id`, `attempt`, `in_flight`, `secret_params`; миграция `020_procedure_wait_since.sql` поле `waiting_since` (см. «Ожидание человека»).

**Запуск (`POST /api/procedures/{id}/run`, 201).** Тело `{bot_id?, thread_id?, params?}`, ответ строка запуска в статусе `queued` (у запуска без бота `failed`). Порядок проверок: доступ (чужая процедура 404), тело (400), `draft` и `archived` (409 `not_runnable`), лаунчер не настроен или не сверен (503 `launcher_unavailable`, раздел 13; запуск без бота лаунчера не требует), затем 400 `invalid`: параметр обязательный без значения и без `default`, неописанный, не того типа, строка длиннее 2000; секретный параметр не в виде `vault:<имя>` или секрета нет ни у бота запуска, ни среди общих (`params.<имя>: secret not found`); бот чужой или несуществующий; бот не контейнерный (`executor='mac'`, у него нет браузера в контейнере); тред не этого бота. `detail` в формате ошибок проверки, `путь: код: текст` (`params.<имя>: required`, `type`, `too_long`, `invalid`, `secret_not_found`; `bot_id: invalid` и `not_allowed`; `thread_id: invalid`; неописанный параметр `params: unknown_field`): PWA по коду показывает русский текст. Имя в пути это параметр процедуры, значений клиента в тексте нет. Бот берётся из тела, иначе из `procedures.bot_id`; нет ни того ни другого: запуск сразу `failed` с `error='no_bot'`. Тред: переданный или новый тред `routine` с именем процедуры (в него идут approvals и короткие события запуска `system`, по ним PWA обновляет экран). Строка процедуры читается `for share`, шаги копируются в `procedure_runs.steps`, имена секретных параметров в `secret_params` (в `params` у них лежит `vault:<имя>`).

**Цикл.** Фоновая задача `procedure_runner` (интервал `BOTHUB_PROCEDURE_INTERVAL`, по умолчанию 1 с) стартует после стартовой сверки с лаунчером, как worker, и только при настроенном лаунчере. Один неконечный запуск на бота (у бота один браузер): второй `POST /api/procedures/{id}/run` для бота с запуском в `queued`, `running`, `waiting_approval`, `waiting_model` или `waiting_human` отвечает 409 `conflict` (после проверок тела и ресурсов, до создания треда; бот блокируется строкой `for update`, два запуска одновременно проходят по очереди). Запуски разных ботов идут параллельно. Не больше 20 запусков в час на пользователя: 21-й это 429 `rate_limited`, запуск не создаётся (лимит считает попытки, `no_bot` тоже). Запуск и turn делят браузер и взаимно исключаются: worker не берёт turn бота, у которого есть неконечный запуск (turn остаётся `queued`, а не теряется, пока запуск не завершён или не остановлен: владельцем или по сроку ожидания человека, см. «Ожидание человека»), а исполнитель не начинает шаг (и не переводит `queued` в `running`), пока у бота есть turn в `running`, `waiting_approval` или `waiting_mac`: проход повторяется по интервалу. Первым проходом выполняется восстановление (ниже). Каждый переход статуса условен (`update ... where status=...`): остановка владельцем не затирается результатом шага, пришедшим позже.

**Один шаг.** (1) `procedures.resolve_step`: параметры и секреты подставляются, `url_forbidden` проверяет адрес `navigate`, риск пересчитывается; ошибка даёт `failed` с кодом ошибки подстановки. (2) Чтение страницы: `launcher.procedure_step(..., dry_run=True)` возвращает адрес, видимость `precondition.visible`, число совпадений цели и её живую подпись, ничего не нажимая (значения шага в такой вызов не кладутся). `precondition.url_matches` считает ядро через `procedures.match_url`. Бот в состоянии `human` или лаунчер отвечает `frozen`: запуск не трогает браузер. (3) Риск по живой подписи (`procedures.risk_with_live`): строжайший из сохранённого `risk` с `flags` и меток, которые классификатор даёт живому имени и роли элемента. Не `none`: подтверждение. Литерал, который вводится в поле, оказавшееся секретным по живой подписи, не вводится: `failed`, `secret_required`. (4) Действие: `launcher.procedure_step(..., dry_run=False)` с `payload.expected = {origin, url, role, name}` (адрес вкладки и подпись цели из последнего чтения, origin страницы, которую одобрил владелец). `expected` может нести `url_sha256` (SHA-256 полного адреса из чтения: показ `url` обрезан до 2048 символов, `expected.url` принимается до 8192): тогда вкладка ищется по хэшу, иначе по точному адресу. Исполнитель в этом же вызове находит вкладку, сверяет её origin и подпись цели, проверяет `precondition.visible` и что цель одна, получает `ElementHandle` и действует только через него (повторного поиска по локатору нет). Нет вкладки с таким адресом, origin или подпись другие: код `changed`, действия не было (запуск `waiting_human`, `reason: page_changed`). Две вкладки с одним адресом: код `ambiguous`, действия не было (`reason: page_ambiguous`; его же отдаёт чтение, если у первой вкладки есть двойник; `navigate` вкладку не сверяет). Действие без `expected` исполнитель принимает только для `navigate` (первая навигация, когда у чтения нет адреса), для остального это `invalid_input`; ядро без адреса страницы шаг не начинает (`no_page`). Сверка у каждого действия с целью (`click`, `fill`, `select`, `press` с целью, `assert`) и у `press` без цели: подписка на `framenavigated` главного фрейма на время действия; перед действием адрес (origin), `handle.ownerFrame() === page.mainFrame()`, `isConnected` и доступность (`isVisible`, `isEnabled`, для `fill` ещё `isEditable`; для `assert` только видимость). Недоступный элемент: код `stat_not_actionable`, действия не было (`reason: element_not_actionable`); ожидания доступности нет. Само действие идёт через handle с таймаутом не более 2000 мс, `noWaitAfter: true`, без `force`. Origin сменился до действия: `changed`, `acted: false`. После действия адрес читается заново: переход на другую страницу, в том числе на другой origin, это обычный результат клика, нажатия, выбора и ввода без секрета (правило в «Переход после действия» ниже). Ограничение: переход, который страница начала сама уже после проверки (например по таймеру), виден только если успел сменить адрес или прислать `framenavigated` до выхода. Поле `payload.secret_input` ядро шлёт у ввода секрета: при нём смена origin после действия это код `changed_after`. Признак `in_flight` ядро ставит до отправки действия и снимает только записью `next_step` и `step_log` (одним `update`): любой проход, который застал `in_flight` включённым (сбой ядра между действием и записью результата), ставит `waiting_human` с `unknown_outcome` и ничего не повторяет, даже при `safe_to_retry`. (5) `expect`: ядро повторяет чтение (`dry_run`, `check_expect`) каждые 0,4 с, пока `url_matches` (ядро), `visible` и `text` (исполнитель) не выполнятся или не выйдет `timeout_ms` (по умолчанию 5000). Только после этого `next_step` растёт, в `step_log` пишется `ok`.

**Статусы и причины.** `queued → running → done | failed | stopped`, по пути `waiting_approval` и `waiting_human`. `waiting_human` всегда с полем `reason`:

| `reason` | Когда | Что дальше |
|---|---|---|
| `precondition_failed` | не совпал `url_matches` (в том числе за 200 мс) или не виден `precondition.visible` | решает владелец |
| `element_not_found`, `element_ambiguous` | цель не найдена или найдено больше одной (поиск по роли точный, `exact`) | решает владелец |
| `no_page`, `browser_unavailable` | у браузера нет вкладки; CDP не отвечает или в образе нет `playwright-core` (`runtime_missing`) | решает владелец |
| `page_changed` | в вызове действия страница оказалась не той, которую одобрил владелец (адрес, origin, подпись); действия не было | решает владелец (повтор просит подтверждение заново) |
| `page_ambiguous` | две вкладки с одним адресом, одобренную не определить (код `ambiguous`); действия не было | решает владелец |
| `element_not_actionable` | в момент сверки элемент невидим, недоступен или не редактируется (код `stat_not_actionable`); действия не было | решает владелец |
| `executor_crashed` | исполнитель дважды подряд упал до действия (`internal_error`, `before_action`) | решает владелец |
| `page_changed_after_action` | ввод секрета выполнен, а вкладка после него на другом origin (код `changed_after`, при секрете и `origin_changed: true`); шаг не повторяется даже при `safe_to_retry` | решает владелец |
| `unknown_outcome` | действие запущено, исход неизвестен только при обрыве связи, таймауте, сбое исполнителя или рестарте ядра, шаг не `safe_to_retry` или повторы кончились. Переход на другую страницу сам по себе сюда не ведёт | решает владелец |
| `browser_human` | браузером управляет человек (`browser_control` `human`) | запуск возобновляется сам, когда состояние стало `bot` или `returning` |
| `bot_frozen` | лаунчер держит бота замороженным, а в базе управляет бот (5 отказов подряд) | решает владелец |
| `launcher_unavailable` | лаунчер недоступен или контейнер бота не запущен 5 проходов подряд | решает владелец |

Запуск бота на паузе (раздел 16, «Пауза бота») остаётся в `queued` или `running` с `reason = "bot_paused"`. Это не причина `waiting_human`: статус не меняется, причина снимается после `resume`.

Решение владельца (`decide`): `retry` повторяет шаг с `next_step` (счётчик повторов обнуляется, подтверждение просится заново), `skip` пишет в `step_log` запись `skipped` и идёт дальше (последний шаг закрывает запуск `done`), `stop` останавливает. Остановка (`stop`, `decide stop`) закрывает подтверждение запуска (`expired`), останавливает исполнителя шага в полёте операцией лаунчера `procedure_step_cancel` (`proc-<id запуска>`, процесс под uid 1001) и пишет `stopped`; если действие шло (`in_flight`), в `step_log` добавляется запись шага со статусом `failed` и `error: unknown_outcome`. Ошибка отмены остановку не отменяет. `decide` принимается только в `waiting_human` (иначе 409 `conflict`), `stop` в любом незавершённом статусе (завершённому 409 `conflict`).

**Ожидание человека.** Запуск не ждёт владельца бесконечно. Если он стоит в `waiting_human` или `waiting_approval` дольше `BOTHUB_PROCEDURE_WAIT_HOURS` часов (по умолчанию 24; допустимо дробное значение; пустое, не число, `nan`, `inf`, не больше нуля и больше 87600 (десять лет) считаются невалидными и дают 24; значение читается при каждом проходе цикла), следующий проход цикла переводит его в `stopped` с `error: wait_expired` (`reason` пустой, `finished_at` проставлен, `in_flight` снят, подтверждение запуска закрыто `expired`). Срок считается от последнего перехода в ожидание: поле `procedure_runs.waiting_since` ставят `pause()` и восстановление после рестарта (`unknown_outcome`), поэтому решение владельца `retry` и новая пауза начинают отсчёт заново; запуски, которые ждали на момент миграции 020, получили `now()`. Для `waiting_approval` действует и срок подтверждения (`APPROVAL_TTL_MINUTES`, 60 мин): кто короче, тот и сработает (истёкшее подтверждение даёт `failed`, `approval_expired`; `wait_expired` бывает у `waiting_approval`, только если `BOTHUB_PROCEDURE_WAIT_HOURS` короче TTL или TTL настроен длиннее). Переход условный (`update ... where status in ('waiting_approval','waiting_human') and waiting_since < срок`): решение или остановка владельца, пришедшие раньше, не затираются, а повторный проход запуск не трогает. После остановки: (а) бот свободен, потому что неконечного запуска больше нет: `queued`-turn'ы бота, которые всё это время ждали (они не теряются и не отбрасываются), берёт worker, а `POST /api/procedures/{id}/run` для бота снова принимается; шаги ждущего запуска никогда не шли, поэтому останавливать в браузере и в лаунчере нечего. Заморозка бота: при `reason: bot_frozen` (в базе управляет бот, а лаунчер держит его замороженным) ядро по сроку вызывает `unfreeze_bot`, сбой разморозки остановку не отменяет; при `browser_human` браузер у человека не отбирается (`browser_control` остаётся `human`, лаунчер заморожен как после обычного перехвата, вернуть управление может только владелец); (б) в тред запуска пишется одно событие `system` с `payload.text` и `payload.run_id` (идентификатор запуска; `run_id` теперь есть у всех коротких событий запуска): «Запуск <run_id>: процедура «имя» остановлена на шаге N, ожидание человека дольше 24 ч (wait_expired). Бот свободен для сообщений и расписаний.»; (в) расписания (раздел 9) не дублируются и не теряются: `run_due_schedules` не выбирает расписание, у бота которого есть неконечный запуск (`queued`, `running`, `waiting_approval`, `waiting_model`, `waiting_human`), `next_run_at` остаётся в прошлом, и расписание срабатывает одним turn'ом на первом проходе после освобождения бота (после `done`, `failed`, `stopped`, в том числе по сроку), затем `next_run_at` считается от текущего момента. Пропущенные за время ожидания сроки cron не накапливаются. До этой правки планировщик создавал turn на каждый срок, а `claim_turn` держал их `queued` до конца запуска: за сутки ожидания копилась очередь одинаковых turn'ов. `POST /api/schedules/{id}/run` (ручной запуск владельцем) этим не ограничен: turn встаёт в очередь и ждёт бота.

**Повторы.** `expect` не выполнился и неизвестный исход: шаг с `safe_to_retry` повторяется до двух раз (с паузой 0,4 с), иначе `failed` с `expect_failed` (для `assert` с `assert_failed`) или `waiting_human` с `unknown_outcome`. Сбой самого исполнителя до действия (`internal_error`, `phase: before_action`, `acted: false`, в том числе при чтении) шаг повторяет сам до двух раз независимо от `safe_to_retry` (ничего не сделано; у шага с подтверждением повтор просит подтверждение заново), потом `waiting_human` с `reason: executor_crashed` и решением владельца; `internal_error` после начала действия остаётся `unknown_outcome`. Недоступный лаунчер сам запуск не роняет: проход повторяется, на пятом подряд `waiting_human`.

**Коды ошибок** (`procedure_runs.error` и `step_log[].error`, только коды, ни текста страницы, ни значений): `no_bot`, `no_thread`, `bot_unavailable`, `secret_not_found`, `secret_required`, `url_forbidden` (адрес `navigate` или адрес, на который ушла вкладка после действия), `param_missing` и остальные коды `resolve_step`, `step_incomplete` (у `fill`, `select`, `press` нет значения), `approval_rejected`, `approval_expired`, `wait_expired` (запуск `stopped`, а не `failed`: ожидание человека дольше `BOTHUB_PROCEDURE_WAIT_HOURS`), `expect_failed`, `assert_failed`, `executor_error` (исполнитель вернул неизвестный код, в том числе `internal_error` до действия, или лаунчер отверг вызов как неверный), `internal_error` (три неожиданных исключения подряд в ядре).

**Подтверждения (`approvals`).** Шаг с итоговым риском не `none` (в том числе любой `login`) создаёт approval: `tool='procedure_step'`, `risk` строжайший, `thread_id` и `bot_id` запуска, `turn_id` равен `procedure_runs.turn_id` (у воспроизведения без модели он `null`), TTL как у остальных (`APPROVAL_TTL_MINUTES`). `title`: «Процедура «имя», шаг N из M: действие «живое имя» на схема://хост[:порт]» (origin в punycode, поэтому подмену букв в адресе видно: `xn--…`; для ввода секрета: «… ввести секрет «имя» на origin. Значение секрета получит код бота: он сможет его прочитать.»; обрезается имя элемента, а не origin и не фраза). `args`: `{run_id, step_id, index, action, target, value, risk, flags?, live, origin, secret_input?}`, где `origin` это `схема://хост[:порт]` страницы шага (`procedures.page_origin`, хост в punycode, порт по умолчанию опущен, не http(s) это `null`), `secret_input: true` у ввода секрета (его `risk` не ниже `login`, подтверждение просится на каждом запуске, даже если поле выглядит безобидно), где `target.url` сведён к `схема://хост/путь`, `value` для `fill` и для всего, что подставлено из секретов, это `[redacted]`, `live` это `{role, name}` найденного элемента (имя до 80 символов через `mask_browser_text`). `args_hash` считается от этих `args`, `op_hash` от `tool` и `args`. Запись `approval_req` и push идут тем же путём, что у обычных approvals (`outbox`), решение владельца принимает `POST /api/approvals/{id}/decide`. «Запомнить» не работает: `remember_rule('procedure_step', ...)` возвращает `None`, ответ `remember: false`, правила в `bots.auto_allow` не создаются. Одобрение расходуется (`used_at`) перед действием; после одобрения страница читается заново, и если живая подпись (роль или имя), origin, риск, признак секрета или шаг изменились, одобрение недействительно (`expired`) и просится новое. Одобрение, записанное без `origin`, не принимается так же. Каждая попытка шага (повтор после `expect_failed` или неизвестного исхода) просит подтверждение заново. Отклонено: `failed`, `approval_rejected`; истекло: `failed`, `approval_expired`. Переходы `takeover` и `return` браузерные approvals гасят по префиксам инструментов; approval шага процедуры (`procedure_step`) они не трогают, его защищает перепроверка живой подписи.

**Человек в браузере и возврат управления.** Бот в `human`: запуск `waiting_human` с `browser_human`, браузер не трогается. Состояние `returning` (человек вернул управление): исполнитель читает страницу шага (проверяет `precondition` заново), и после этого сам переводит `returning → bot` (`browser_transition` с действием `snapshot` и причиной `procedure_run`, событие `browser_control` от имени бота). Это отступление от раздела 13 («после успешного `browser_snapshot` в активном turn»): у воспроизведения нет модели, чью картину страницы нужно обновлять, а чтение с проверкой условий шага выполняет ту же роль. Сбой перехода запуск не останавливает, состояние остаётся `returning`, следующий проход повторит.

**Рестарт ядра.** Первым проходом: запуск `running` с `in_flight` (действие было запущено, исход не записан) и шагом `safe_to_retry` продолжается с `next_step`, остальные уходят в `waiting_human` с `unknown_outcome`. Запуски `running` без `in_flight` продолжаются. `waiting_approval` и `waiting_human` остаются как были (хранятся в БД); approval шага процедуры рестарт не гасит.

**Безопасность.** Значения секретов расшифровываются на один шаг (`secrets`, ключ `BOTHUB_SECRET_KEYS`, секрет бота раньше общего; не расшифровался: `secret_not_found`) и уходят только в stdin исполнителя. Их нет в `step_log`, `error`, `reason`, событиях, approvals и их хэшах, ответах API, журнале ядра и лаунчера, argv и окружении процесса. Исключения в журнал ядра попадают классом и местом в коде, без текста. Ответ исполнителя ядро не принимает на веру: берутся только известные поля известных типов и длин (`clean_result`), неразбираемый ответ считается потерянным. Адрес `navigate` проверяется после подстановки `url_forbidden` в ядре и ещё раз по схеме в исполнителе.

**Граница секрета (раздел 14, правка по ревью Opus).** (а) Значение секрета, введённое в страницу, доступно коду бота: Chromium, CDP и экран того же uid 1001 доступны коду в контейнере (раздел 13, «Граница этой гарантии»). Хранилище защищает секрет от журналов, событий, approvals, контекста модели и ответов API, но не от враждебного кода бота в том же браузере. (б) Поэтому ввод секрета подтверждается на каждом запуске, а подтверждение показывает origin страницы и фразу о боте (см. «Подтверждения»). (в) Условия адреса (origin, адрес вкладки, подпись цели) проверяются не в чтении, а в самом вызове действия, одним вызовом исполнителя; после ввода секрета адрес читается ещё раз. (г) Секрет сохраняется только в процедуру, которая привела на страницу (`navigate` раньше или `precondition.url_matches`, `secret_no_context`). (д) Скрипт грузит `playwright-core` только по абсолютному пути из образа (HOME, `NODE_PATH`, `NODE_OPTIONS`, cwd не влияют), необработанные исключения не печатают текст ошибки.

**Лаунчер: `procedure_step`.** `POST /v1/bots/{id}/procedure-step` `{payload_json, dry_run?, timeout?, exec_id?}` → `{bot_id, exec_id, exit_code, reason, result}`. `payload_json` строка с JSON-объектом до 256 КиБ (лаунчер содержимое не разбирает и не журналирует), `timeout` от 5 до 180 с (по умолчанию 30; исполнитель сам укладывается на 3 с раньше). Лаунчер запускает `docker exec -i --user 1001:1001 -e HOME=/nonexistent --workdir /` с `setsid -w bash -c ... env -i HOME=/nonexistent PATH=/usr/bin:/bin node --no-warnings /usr/local/libexec/procedure-step.mjs` (чистое окружение: ни `NODE_PATH`, ни `NODE_OPTIONS`, ни `HOME` с `.node_modules`, cwd `/`); в argv и окружении только константы и `exec_id`, данные шага идут одним конвертом `{dry_run, deadline_ms, payload}` в stdin. Допуск как у `exec` (метка лаунчера, контейнер запущен, `frozen` для заморозки и режима `human`), один шаг на бота за раз (`429 busy`). Заморозка при перехвате останавливает исполнителя вместе с остальными exec бота; сигналы идут под uid 1001 (`kill_procedure_step`, PID в `/home/browser/.procedure-step.pid`), потому что `kill` под uid 1000 до процесса uid 1001 не дотянулся бы. Операция `procedure_step_cancel`: `POST /v1/bots/{id}/procedure-step/cancel` `{exec_id}` → `{bot_id, exec_id, stopped, was_running}` завершает исполнитель шага (TERM, через `kill_grace` KILL группе процессов под uid 1001): шаг в реестре лаунчера завершается с `reason: stopped`, после перезапуска лаунчера (реестра нет) идут сигналы по PID-файлу и метке. Шаг чужого бота и обычный exec этой операцией не гасятся (404), бота нет: 404. Ядро зовёт её при остановке запуска с шагом в полёте. `result` это разобранная последняя строка stdout (до 64 КиБ) или `null`; stderr отбрасывается.

**Исполнитель в контейнере.** `procedure-step.mjs` подключается к CDP на `127.0.0.1:9222` (`playwright-core` грузится по абсолютному пути из образа, список `RUNTIME_PATHS` в скрипте, файл вне `/usr/` и симлинк наружу не принимаются), ищет цель по `getByRole(role, {name, exact: true})` или по `page.locator('css=' + selector)`; страницу выбирает по `expected.url_sha256` или `expected.url` (чтение и первая навигация берут первую страницу браузера, `navigate` без страницы открывает новую; две вкладки с одним адресом это `ambiguous`). Результат: `{v: 1, ok, code, acted, url, url_sha256, precondition_visible, found: {count, role, name}, expect: {visible, text}, navigated, origin_changed}` (`navigated` и `origin_changed` булевы, у чтения, ошибок и `navigate` `false`; старый исполнитель их не шлёт, ядро читает это как `false`). `acted`: `false` значит действия не было, `true` выполнено, `null` исход неизвестен (ошибка Playwright уже после начала действия, срок). Код `changed_after` бывает только у ввода секрета (`payload.secret_input`) при сменившемся origin: `acted: true`, если действие вернулось, `acted: null`, если оно оборвалось. Коды: `invalid_input`, `url_forbidden`, `runtime_missing` (нет `playwright-core` по абсолютному пути), `cdp_unavailable`, `no_page`, `changed`, `changed_after`, `ambiguous`, `stat_not_actionable`, `precondition_failed`, `element_not_found`, `element_ambiguous`, `assert_failed`, `action_failed`, `timeout`, `internal_error`. `internal_error` приходит из обработчиков `uncaughtException` и `unhandledRejection`: одна строка JSON с полем `phase` (`before_action`: `acted: false`, `after_action`: `acted: null`), текст ошибки нигде не печатается (stderr пуст), код выхода 70. Ни значений шага, ни текста страницы, ни текстов ошибок Playwright в результате нет, только коды и подпись найденного элемента.

**Не проверено на живом Docker.** `procedure-step.mjs` против настоящего Chromium и `playwright-core` из образа (в тестах Playwright заменён моделью страницы), `ariaSnapshot` для цели по селектору (версия `playwright-core` в образе), `docker exec` под uid 1001 с `setsid -w` и остановка группы, SQL `PgStore` на живой схеме (`core/tests/test_procedure_runner_db.py` написан, но без Postgres не запускался), формат подписи `getByRole(..., exact)` против имён из snapshot Playwright MCP (имена там могут быть нормализованы иначе, и точный поиск не найдёт элемент: запуск тогда ждёт владельца с `element_not_found`).

**Доступ.** Все маршруты только для пользователя (сессия, CSRF на изменяющих): токен бота 403, токен Mac 403, без входа 401. Отключённый пользователь теряет сессии и токены (401), его процедуры остаются в БД. Удаление бота процедуры и запуски не удаляет (`bot_id` становится `null`), `DELETE /api/bots/{id}` процедурами не блокируется. Ядро пользователей не удаляет, только отключает; из БД пользователя с процедурами удалить нельзя (`owner_id` без каскада).

### Вкладка по адресу цели CDP (2026-10-06)

Исполнитель определяет вкладку по адресу **цели** CDP (`Target.getTargetInfo` через `context.newCDPSession(page)`, сессия закрывается после чтения), а не по `page.url()`: политика закрывает `chrome://*`, и у служебных страниц Chromium и заблокированной новой вкладки `page.url()` один и тот же (`chrome-error://chromewebdata/`), отчего на свежем боте любой первый `navigate` останавливался с `page_ambiguous`. Выбран запрос по сессии самой страницы, а не `Target.getTargets` браузера: он напрямую привязан к странице Playwright, сопоставлять `targetId` не нужно.

- Вкладкой считается обычная страница, новая вкладка (`chrome://newtab/`, `chrome://new-tab-page/`) и `about:blank`. Служебные `chrome://*`, `chrome-extension://`, `chrome-untrusted://`, `devtools://*` и `chrome-error://` вкладками не считаются. Новая вкладка в результате выглядит как `about:blank` (адрес и хэш считаются от `about:blank`), поэтому `expected` из чтения находит эту же вкладку.
- Адрес результата и `url_sha256` берутся из одного значения, прочитанного один раз; после действия читаются заново тоже одним значением.
- Цель не прочиталась: берётся адрес фрейма, а `chrome-error://` вкладкой не считается (нет вкладки: `no_page`, для `navigate` открывается новая).
- Страница ошибки у настоящей вкладки (адрес цели обычный, фрейм `chrome-error://`): чтение и действие на ней, кроме `navigate`, дают код `page_error` (`acted=false`). `navigate` такую вкладку читает спокойно (из неё и выходят). Если после действия вкладка оказалась на странице ошибки, это `page_error` с `acted=true` и адресом, который просили открыть, не молчаливый успех. Ядро пока относит `page_error` к общему отказу `executor_error` (отдельной причины паузы нет).
- Две настоящие вкладки с одним адресом по-прежнему `ambiguous`.

### Переход после действия (2026-10-06)

Живой прогон показал ошибку: после клика по ссылке на другой origin исполнитель отвечал `changed_after`, а ядро ставило `waiting_human` с `unknown_outcome`. Для `click`, `press`, `select` и `fill` без секрета переход на другую страницу, в том числе на другой origin, обычный результат. Правила:

1. **До действия** без изменений: исполнитель сверяет адрес, origin и подпись цели (`expected`), при расхождении действия нет (`changed`, `acted: false`).
2. **После действия** (`click`, `press`, `select`, `fill` без `secret_input`) адрес читается заново. Вкладка ушла на другую страницу: `ok: true`, `acted: true`, `url` и `url_sha256` новой страницы, `navigated: true`; сменился origin: ещё и `origin_changed: true`. Переход виден по `framenavigated` главного фрейма за время действия или по другому адресу вкладки после него. Ядро по такому ответу сначала проверяет новый адрес `url_forbidden` (запрещён: запуск `failed`, `error: url_forbidden`, следующие шаги не идут), затем проверяет `expect` обычным порядком, то есть повторными чтениями по новому адресу, и только потом растёт `next_step`. Без `expect` шаг закрывается `ok`.
3. **`fill` с секретом** (`payload.secret_input`): origin после ввода сменился, значение могло уйти не туда. Исполнитель отвечает `changed_after` (`acted: true`, `acted: null` при обрыве), ядро ставит `waiting_human` с `reason: page_changed_after_action`, шаг не повторяется даже при `safe_to_retry`. Ядро ставит ту же паузу, если исполнитель по секрету вернул `ok` с `origin_changed: true`, и при любом `changed_after` (старый исполнитель слал его и для клика).
4. **Ожидание только в чтении.** Действие само ничего не ждёт: таймаут handle до 2000 мс, `noWaitAfter: true`, `settle_ms` в вызове действия `0`. Читающий вызов (`dry_run`) с `settle_ms` (0..5000, задаёт ядро) ждёт `domcontentloaded` и появления цели одним общим пределом `settle_ms`, затем перечитывает адрес вкладки и отдаёт его уже после ожидания. Обычное чтение перед шагом идёт с `SETTLE_MS` (1500 мс); чтение шага, следующего за шагом с `navigated: true`, с `SETTLE_AFTER_NAV_MS` (5000 мс, предел исполнителя). Чтения проверки `expect` опрашивает само ядро каждые 0,4 с до `timeout_ms`, их `settle_ms` равен 0.
5. **Неизвестный исход** (`waiting_human`, `reason: unknown_outcome`) бывает только при обрыве связи с лаунчером, таймауте, падении исполнителя после начала действия (`internal_error` с `phase: after_action`), ошибке Playwright во время действия (`action_failed`, `acted: null`), недоступной проверке `expect` и сбое ядра между действием и записью результата (`in_flight`). Переход страницы сам по себе исходом неизвестным не считается. Выполненное действие (`acted: true`) с проваленным `expect` повторяется только при `safe_to_retry` (до двух раз), иначе `failed` с `expect_failed`.

## 15. Заполнение контекста и сжатие треда (этап 8, миграция `022_context_compaction.sql`)

Раннер продолжает сессию CLI по `threads.cli_session_id`, поэтому контекст модели растёт с каждым ходом. Ядро измеряет заполнение, показывает его клиенту и умеет сжимать тред: сводка вместо истории для модели, при этом лента владельца остаётся полной. Чистая логика (процент, оценка, решение об автосжатии, преамбула, обрезка сводки) в `core/bothub/context.py`, без БД и сети.

### Измерение

Поле `usage` у раннера получает три необязательных ключа: `context_tokens` (размер контекста сессии после хода: промпт последнего вызова модели плюс его ответ), `context_estimated` (цифра приблизительная), `context_window` (окно модели, если CLI его сообщил). В событие `usage` ленты эти ключи не попадают.

| Раннер | Откуда берётся `context_tokens` | Почему |
| --- | --- | --- |
| `claude` | `result.usage.iterations[-1]`: `input_tokens + cache_creation_input_tokens + cache_read_input_tokens + output_tokens`; без `iterations` те же поля из `usage` последнего assistant-сообщения; без них (приблизительно) итоги `result.usage` | `result.usage.input_tokens` не считает кэш (в снятом потоке 18 при реальных 46 тысячах) и суммирует вызовы хода; последний вызов даёт настоящий размер промпта |
| `codex` | `turn.completed.usage`: `input_tokens + output_tokens`, всегда `context_estimated=true` | `input_tokens` включает `cached_input_tokens`; в снятом потоке 62 тысячи на ход с одним вызовом инструмента при базовом промпте около 21 тысячи, то есть, вероятно, сумма по вызовам хода (не проверено на живом CLI): это верхняя оценка |
| `gemini` (agy) | `step_update.usage` последнего шага: `input_tokens + output_tokens`; без шагов с usage `result.usage` приблизительно | `result.usage` может суммировать шаги, usage шага это промпт одного вызова |
| `fake` | не сообщает | ядро считает оценку по событиям |

`context_window` сообщает только `claude`: `modelUsage[модель].contextWindow` (при нескольких моделях берётся самая загруженная). Окно треда для `threads.context_window`: окно раннера, иначе `models.context_window` модели бота (`bots.model_id`), иначе значение по умолчанию для провайдера (`claude` 200 000, `codex` 400 000, `gemini` 1 000 000, модель с `[1m]` или `-1m` в имени 1 000 000), иначе `null`. Окно меньше 1000 токенов (от раннера или `models.context_window`) считается неизвестным: берётся следующий источник, процент и автосжатие по нему не считаются (окно 1 при 50 токенах давало бы 5000 процентов и сжатие на каждом ходу). Верхняя граница окна 10^9. Нулевой или отрицательный `context_tokens` не принимается: ядро считает оценку по событиям (`tokens = context_base_tokens + ceil(байты / 3,5)` по `user_msg`, `assistant_msg`, `tool_call.args`, `tool_result.summary` с `seq > context_base_seq`) и ставит `estimated=true`.

Колонки `threads`: `context_tokens bigint`, `context_window integer`, `context_estimated boolean`, `compacted_at timestamptz`, `compactions integer`, `context_base_tokens bigint`, `context_base_seq bigint`, `turns_since_compact integer default 3`, `auto_compact_disabled boolean`. `turns.turn_type` и `usage.turn_type`: `normal` | `compact`. `bots.auto_compact_percent integer default 80` (50..95 или `null`). Обновление идёт на каждом событии `usage` обычного хода. Смена модели или провайдера бота сбрасывает `cli_session_id`, `context_tokens` и `context_window` его тредов.

`GET /api/threads/{id}` (owner; чужой тред 404) отдаёт строку треда и `context: {tokens, window, percent, estimated, compacted_at, compactions}`. `percent = floor(tokens * 100 / window)`, от 0 до 100, `null` без окна или без `tokens`. Тот же `context` есть у каждого элемента `GET /api/threads`. Текущая сводка лежит в поле `summary` строки треда.

### Сжатие

`POST /api/threads/{id}/compact` (owner, без тела; тело, если есть, наследует `Body` и не принимает лишних полей) создаёт turn `turn_type=compact`, `client=api`, `prompt` равен фиксированной инструкции `COMPACT_INSTRUCTION` (английский текст, обязательные разделы Goals, Decisions, Tasks, Facts, Browser and files, без секретов и без вызова инструментов). Ответ: Turn со статусом `queued`. Ошибки: 404 чужой или несуществующий тред; 409 `conflict` если тред архивный, у треда есть `queued`, `running`, `waiting_approval` или `waiting_mac` turn, либо сжимать нечего (`cli_session_id` пуст); 409 `no_model`/`bot_computer_failed` как у обычного хода. Проверка и вставка идут под `pg_advisory_xact_lock(hashtext('bothub-claim-turn'))`.

Ход сжатия невидим: события `user_msg` нет, ответ бота, план и вызовы инструментов в ленту не пишутся, `usage` пишется в таблицу с `turn_type=compact` (бюджет считает его), события `usage` нет. Остаются события `status`. `claim_turn` ставит compact перед обычными turn'ами. Раннер продолжает текущую сессию, текст `assistant_msg` склеивается в сводку (для `gemini` без `final=true`: там текст ошибки).

Ход сжатия не исполняет инструменты, в два слоя. Раннер получает `TurnContext.turn_type = "compact"` и запускает CLI без инструментов, насколько это умеет CLI. `claude`: `--tools ""` и `--strict-mcp-config` без `--mcp-config` (ни встроенных инструментов, ни MCP-сервера, ни `approve`). `codex`: `-s read-only` (у `resume` флага нет, там `-c sandbox_mode="read-only"`) и `--disable shell_tool --disable unified_exec`. `agy`: `--mode plan` без `--dangerously-skip-permissions`. Полного запрета инструментов у `codex` и `agy` нет, поэтому держит ядро: первый же `tool_call` хода сжатия и запрос подтверждения (`POST /api/approvals` с `turn_id` такого хода отвечает 409 `conflict`, `detail` равен `tool_call_refused`, подтверждение не создаётся) сразу останавливают ход тем же путём, что `POST /api/turns/{id}/stop`: раннер остановлен, turn в `stopped`. Пишется событие `compact_failed` с `detail` и `reason` равными `tool_call_refused` и `tool` (имя инструмента, одна строка до 100 символов, без аргументов). Вызов, результат и дальнейший текст в тред не попадают, сессия CLI не сбрасывается, сводка не сохраняется, `turns_since_compact=0`. Три одинаковые ошибки инструмента подряд (`guard` с `repeat_error`) останавливают ход сжатия так же, как обычный; результаты инструментов этого хода в тред по-прежнему не пишутся. В ленте активности ход сжатия идёт под своими кодами `compact_started`, `compact_done`, `compact_failed` (раздел 16), а не `turn_*`.

Успех (одна транзакция вместе со статусом `done`): сводка проходит `mask_browser_text` (те же правила, что у вывода браузера: URL без запроса и фрагмента, значения полей скрыты), обрезается до 16 КиБ по границе абзаца и пишется в `threads.summary`; `cli_session_id=null`, `compactions+1`, `compacted_at=now()`, `turns_since_compact=0`, `context_tokens` и `context_base_tokens` равны оценке преамбулы (`estimated=true`), `context_base_seq` равен `seq` события. Пишется событие `compacted` (`actor=system`). Сводка не попадает в `memory`. История (`events`) не удаляется.

Сбой (ошибка раннера, таймаут, бюджет, остановка, пустая сводка, нечего сжимать): тред не меняется, кроме `turns_since_compact=0` (следующая попытка автосжатия не раньше чем через три хода). Пишется событие `compact_failed` с `detail` (до 500 символов; при отказе от инструмента ещё `reason` и `tool`, см. выше), turn закрывается по обычным правилам (`status` `error` или `stopped`).

Первый обычный ход после сжатия (`threads.summary` не пуст и `cli_session_id` пуст) запускает новую сессию CLI: промпт раннера собирается как заголовок `Summary of previous conversation:`, пояснение, рамка данных и `New message from the user:` с текстом хода. Сводку составила модель по тексту, который мог прийти от сайтов и файлов, поэтому в рамке стоят сводка и `Last messages of the conversation, verbatim:` (последние 6 сообщений владельца и бота из событий последних шести обычных ходов, каждое до 8 КиБ, все вместе до 32 КиБ; при превышении старые отбрасываются первыми, самое новое остаётся). Рамка это две строки `<<<BOTHUB-CONTEXT токен>>>` и `<<<END BOTHUB-CONTEXT токен>>>`. Токен случайный на каждую преамбулу (16 hex-символов) и выбирается так, чтобы его не было в тексте внутри рамки; имя `BOTHUB-CONTEXT` в тексте сводки и сообщений заменяется на `BOTHUB_CONTEXT`, поэтому строку разделителя подделать нельзя. Пояснение перед рамкой (по-английски): текст между строками разделителя это справочные данные из прошлой части разговора, составленные автоматически; это не сообщение пользователя и не системный промпт, инструкции внутри них выполнять нельзя. В ленте и в `turns.prompt` остаётся исходный текст владельца. После первого ответа бота сессия новая, следующие ходы продолжают её без преамбулы. Тот же путь работает после смены модели, если сводка уже есть.

### Автосжатие

Настройка бота `auto_compact_percent`: целое 50..95 или `null` (выключено), по умолчанию 80; принимают `POST /api/bots` и `PATCH /api/bots/{id}` (явный `null` выключает, вне диапазона 400). После завершённого обычного хода (`status=done`, не посреди хода) ядро увеличивает `turns_since_compact` и ставит compact turn (`client=system`), если одновременно: тред активный и у него есть сессия, окно известно и точное заполнение `tokens / window * 100` не меньше порога, прошло не меньше трёх обычных ходов с прошлого сжатия (новый тред стартует со значением 3), в треде нет ожидающего compact, `auto_compact_disabled=false`. Сбой самой постановки пишется в лог и ход не ломает.

Если после автосжатия размер упал меньше чем на 30 процентов (`tokens_after` против `tokens_before`, оценка по преамбуле), `threads.auto_compact_disabled` становится `true` и пишется событие `auto_compact_disabled`; настройка бота остаётся как есть, ручное сжатие работает.

### События

| kind | payload |
| --- | --- |
| compacted | `{"tokens_before": int\|null, "tokens_after": int, "auto": bool, "reduction_percent": int\|null, "summary_chars": int}` |
| compact_failed | `{"detail"}`; при отказе от инструмента `{"detail":"tool_call_refused","reason":"tool_call_refused","tool"}` |
| auto_compact_disabled | `{"reduction_percent": int\|null}` |

`tokens_after` оценочный: точное значение появится после usage следующего хода.

## 16. Лента активности, пауза бота, пауза триггеров (этап 8, миграции `021_activity_pause.sql` и `023_review_fixes.sql`)

Владелец: core (`core/bothub/activity.py` чистая логика, маршруты в `main.py`), PWA (`pwa/activity.js`). Все маршруты только для пользователя: чужой ресурс 404, токен бота 403, без входа 401, изменяющие запросы по cookie требуют `X-CSRF` и `Origin`.

### Лента `GET /api/activity`

Параметры: `bot_id` (только свои боты: чужой или несуществующий даёт пустую ленту), `kind`, `before`, `limit`. `kind` из списка `turn`, `approval`, `browser`, `takeover`, `schedule`, `procedure`, `memory`, `pause`; можно несколько через запятую (`kind=turn,approval`), без параметра все. `limit` от 1 до 100, по умолчанию 50. `before` непрозрачный курсор из прошлого ответа. Неизвестный `kind`, плохой `limit`, `before` или длинный `bot_id`: 422 `{"error":"invalid","detail":"kind|limit|before|bot_id"}` (значение в ответ не возвращается). Курсор со временем, которое не помещается в UTC (`0001-01-01T00:00:00+14:00`, `9999-12-31T23:59:59-14:00`), это неверный `before` (422), а не ошибка сервера. Так же отклоняется `expires_at` памяти вне диапазона UTC: `POST /api/memory` и `PATCH /api/memory/{id}` отвечают 400, значение без пояса считается UTC.

Ответ `{"items":[...],"next":"<курсор>"|null}`: события по всем своим ботам, новые сверху; `next` равен `null` на последней странице. Порядок полный: `(at, id)` по убыванию, `id` сравнивается как строка по кодовым точкам (в SQL `collate "C"`), поэтому на одинаковом времени страницы не пересекаются и ничего не теряют. Курсор кодирует время (UTC, микросекунды) и id последнего элемента страницы.

Элемент: `{id, at, bot_id, thread_id, turn_id?, kind, title, detail?, risk?, status?}`.

- `id`: строка вида `turn:<uuid>:start`, `approval:<uuid>:dec`, `event:<thread>:<seq>`, `run:<uuid>`, `procedure:<uuid>:end`, `memory:<uuid>`, `log:<n>`. Уникальна в ленте и со временем не меняется.
- `at`: ISO 8601 UTC с микросекундами и `Z`. `bot_id` и `thread_id` могут быть `null` (процедура без бота, пауза не привязана к треду).
- `title`: `{"code": "...", "params": {...}}`. Ядро отдаёт короткий код и параметры, человекочитаемую строку собирает PWA (так лента переводима). Параметры только скаляры: строки (до 120–300 символов), числа, булевы.
- `detail`: свободный текст пользователя или бота (заголовок подтверждения, текст предложенной записи памяти), до 200 символов. PWA помечает его `data-i18n-skip`.
- `risk`: только у подтверждений (`pay|send|delete|login|push|other`). `status`: статус turn, подтверждения, запуска процедуры или записи памяти; у `browser_step` результат `ok|error`.

| kind | Источник | codes (`title.code`) и params |
| --- | --- | --- |
| `turn` | `turns` | `turn_started`, `turn_done`, `turn_error`, `turn_stopped`; `client`. Служебный ход сжатия (`turn_type=compact`, раздел 15) даёт `compact_started`, `compact_done`, `compact_failed` (`auto`: сжатие поставило ядро), кодов `turn_*` у него нет |
| `approval` | `approvals` | `approval_requested`, `approval_approved`, `approval_rejected`, `checker_denied` (раздел 19), `approval_expired`; `tool`; в `detail` заголовок |
| `browser` | `events.kind='browser_step'` | `browser_step`; `action`, `target`, `url` (схема://хост/путь, без query и логина) |
| `takeover` | `events.kind='browser_control'` | `takeover_started` (на `human`), `takeover_returned` (на `returning`), `takeover_bot`; `from`, `to` |
| `schedule` | `turns.client in ('schedule','hook')`, `activity_log` | `schedule_run`, `hook_run` (`name`, `schedule_id`), `schedule_skipped` (`reason`, `count`, `paused`, `schedule_id`, `name`), `schedule_resumed`, `wakeup_scheduled`, `wakeup_fired`, `wakeup_skipped` (`wakeup_id`, `scheduled_at`, у пропуска `reason`; в `detail` причина, которую назвал бот; раздел 17), `delegation_sent`, `delegation_done` (`from_bot`, `to_bot`, `to_bot_id`, `turn_id`, у завершения `outcome`; в `detail` текст задачи; раздел 19) |
| `procedure` | `procedure_runs` | `procedure_started`, `procedure_finished`; `name`, `procedure_id`, `run_id` |
| `memory` | `memory` с `source like 'bot:%'` | `memory_proposed`; `memory_id`, в `detail` текст |
| `pause` | `activity_log` | `bot_paused` (`reason?`, `by_all?`), `bot_resumed` |

Что в ленту не попадает: `approvals.args` (отдаются только заголовок и имя инструмента), `events.payload.value` и любые введённые значения, `procedure_runs.params` и `step_log`, текст ошибки turn. Заголовок подтверждения и цель браузерного шага дополнительно проходят `mask_browser_text`, адрес `mask_url`. Выборка по каждому источнику идёт отдельным запросом (не больше девяти на страницу, без N+1): каждый возвращает до `limit + 1` своих самых новых строк после курсора, ядро сливает их по `(at, id)`. Выборка идёт от владельца (миграция 023). Для `turns`, `approvals`, `events` и `procedure_runs` сначала берутся свои треды (`threads.owner_id`, индекс `threads(owner_id, bot_id)`) или процедуры (`procedures.owner_id`), затем `lateral` по каждому из них отдаёт до `limit + 1` самых новых строк по индексу, начинающемуся с `thread_id` или `procedure_id`: `turns(thread_id, started_at desc)`, `turns(thread_id, finished_at desc)`, `turns(thread_id, created_at desc)` для расписаний и hooks, `approvals(thread_id, created_at desc)`, `approvals(thread_id, coalesce(decided_at, expires_at) desc)`, `events(thread_id, ts desc)` для `browser_step` и `browser_control`, `procedure_runs(procedure_id, created_at desc)`, `procedure_runs(procedure_id, finished_at desc)`. `memory` и `activity_log` идут по индексам, которые начинаются с `owner_id` (`memory_proposed_idx`, `activity_log(owner_id, at desc, id desc)`, миграция 021). Чужие строки не читаются: индексы 021 шли по времени всей системы, и на 100 тысячах чужих событий выборка отбрасывала их все фильтром соединения (`Rows Removed by Join Filter: 100000`). Курсор отсекает строки внутри `lateral` (`время <= время курсора`), порядок внутри него тот же, что у слияния, поэтому на равных временах ничего не теряется; `schedule_id` у `schedule_run` ищется уже по строкам страницы. Миграция 023 удаляет прежние индексы 021 по времени всей системы. **Миграция 023 строит индексы обычным `create index`** (раннер миграций исполняет файл в одной транзакции, `create index concurrently` в ней невозможен), и на время сборки запись в `turns`, `approvals`, `events` и `procedure_runs` блокируется: на большой базе запускать в окно обслуживания.

`activity_log` (`id bigserial, owner_id, bot_id, thread_id, kind in ('pause','schedule'), code, params jsonb, at`) хранит события, которым не принадлежит тред: пауза и возобновление бота, пропуск и возобновление расписания. `bot_id` и `thread_id` без внешних ключей: запись переживает удаление бота и треда.

### Пауза бота

Колонки `bots.paused boolean not null default false`, `paused_at`, `paused_reason` (приходят в `GET /api/bots`).

- `POST /api/bots/{id}/pause` `{"reason"?: строка до 200 символов}` и `POST /api/bots/{id}/resume`: идемпотентны (повтор состояние и событие не меняет). Ответ `{"bot_id","paused","paused_at","paused_reason","running_turn"}`; `running_turn` это id turn в `running`, `waiting_approval` или `waiting_mac` либо `null`. Пауза идущий turn не прерывает: клиент может предложить «Остановить текущую задачу» через `POST /api/turns/{id}/stop`.
- `POST /api/bots/pause-all` (`{"reason"?}`) и `POST /api/bots/resume-all`: все свои боты, ответ `{"bots":[…как выше…]}`. Чужие боты не затрагиваются.
- На паузе: `claim_turn` не берёт `queued` turn этого бота (они остаются в очереди и выполняются после возобновления; продолжение уже идущего turn и перехват брошенного `running` не затронуты); расписания и hooks пропускают запуск (`bot_paused`); `POST /api/schedules/{id}/run` и `POST /api/procedures/{id}/run` отвечают 409 `{"error":"bot_paused"}` (проверка запуска процедуры стоит внутри транзакции создания запуска, ниже). Сообщение владельца в тред бота на паузе принимается (`POST /api/threads/{id}/turns` как раньше) и ждёт; в тред пишется событие `system` с `payload.code = "bot_paused"`, по одному на turn. Каждая смена состояния пишет `bot_paused` или `bot_resumed` в ленту.

**Очередь процедур на паузе.** Движок процедур (`procedure_runner`) не начинает и не продолжает шаги запусков бота на паузе. Пауза проверяется перед каждым шагом и перед началом запуска (`queued` в `running` переводит условный `update`, который сам смотрит `bots.paused`, поэтому запуск, выбранный проходом цикла до паузы, всё равно не начнётся). Идущий шаг доводится до конца, следующий не начинается. Запуск остаётся в своём статусе (`queued` или `running`) с причиной ожидания `reason = "bot_paused"`: её отдают `GET /api/procedure-runs/{id}` и список запусков процедуры. После `resume` причина снимается, и запуск идёт с шага, который не начался. Запуски в `waiting_approval` и `waiting_human` пауза не трогает: решения владельца (подтверждение, `decide`, возврат браузера) принимаются, но следующий шаг после них ждёт возобновления.

**Срок ожидания человека на паузе не тикает.** `BOTHUB_PROCEDURE_WAIT_HOURS` (раздел 14) отсчитывается без времени паузы: пока бот на паузе, запуск не останавливается с `wait_expired`, а `resume` в той же транзакции сдвигает `waiting_since` запусков бота вперёд на длину паузы (для ожидания, начавшегося во время паузы, на её часть после начала). Так владелец, который поставил бота на паузу на выходные, не теряет ожидающий запуск. Подтверждения (`approvals`) живут по своему сроку и на паузе истекают как обычно.

**Запуск процедуры на паузе.** `POST /api/procedures/{id}/run` отвечает 409 `bot_paused`. Проверка стоит внутри транзакции создания запуска (`PgStore.create_run`) после блокировки строки бота (`for update`), ту же строку блокирует смена паузы: пауза, поставленная между проверкой и вставкой, не проскакивает. Запуск не создаёт ни строки, ни треда. Запуск процедуры без бота паузой не затрагивается. Проверка стоит после `require_launcher`, поэтому без лаунчера ответ 503 `launcher_unavailable`.

### Пауза триггеров при недоступном исполнителе

Перед созданием turn по расписанию (`kind='cron'`) и по hook ядро вызывает `trigger_block(bot)`. Причина (в порядке проверки):

1. `bot_paused`: `bots.paused`.
2. `provider_unavailable`: бот привязан к провайдеру, чей статус не `ok` (`error`, `pending_admin`, `disabled`, `new`), бот без модели (`no_model`, привязка к реестру без провайдера).
3. `executor_unavailable`: `bots.status='error_starting'`; для `executor='mac'` Mac владельца не `online` (нет сокета агента, нет heartbeat 90 с, `locked`); для контейнерного бота в `BOTHUB_RUNNER_EXEC=docker` лаунчер не завершил сверку, недоступен (`LauncherError`, таймаут) или `status(bot_id).running` ложно. Без лаунчера и вне docker-режима контейнер не проверяется.

Причина найдена: turn не создаётся, срабатывание считается пропущенным.

Если сама проверка бросила исключение (сбой БД, лаунчера), срабатывание тоже считается пропущенным с причиной `check_failed`: расписание сдвигается на следующий срок, а не остаётся в прошлом и не пишет ошибку в журнал каждые 30 секунд; hook отвечает тем же 202. `check_failed` входит в `schedules.last_skip_reason` (миграция 023), счётчик и пауза по пяти пропускам подряд действуют как у остальных причин.

- Поля расписания (миграция 021): `skipped_count` (пропусков подряд с последнего успешного запуска), `last_skipped_at`, `last_skip_reason`, `paused_by_unavailable`, `catch_up boolean default false` (в `ScheduleIn` и `PATCH`), служебное `last_skip_event_at`. Все приходят в `GET /api/schedules`.
- Событие `schedule_skipped` пишется в ленту (`activity_log`, со счётчиком `count`) и системным событием `{"text","code":"schedule_skipped","reason","count"}` в тред расписания (тред последнего запуска, если он активен): не чаще одного раза в час на расписание. Счётчик растёт на каждом пропуске.
- Cron-расписание после пропуска сдвигается на следующий срок (не крутится каждые 30 с). После 5 пропусков подряд `paused_by_unavailable=true`, и расписание проверяется не чаще раза в 15 минут (`next_run_at = max(следующий cron, сейчас + 15 мин)`).
- Исполнитель снова доступен: если были пропуски или пауза, пишется `schedule_resumed` (лента и тред), счётчик и флаг сбрасываются. Расписание вне паузы запускается как обычно (его срок настал). Расписание в `paused_by_unavailable` проверялось не по cron, поэтому запускает turn один раз только при `catch_up=true`, иначе ждёт своего cron. Пропущенные запуски пачкой не догоняются. Для hook `catch_up` не действует: любой следующий принятый hook запускает turn.
- Hook: ответ всегда `202 {"status":"accepted"}`, и при созданном turn, и при пропуске (пауза, исполнитель, провайдер, сбой проверки). Идентификатора turn в ответе нет, поэтому внешний отправитель по коду, телу и заголовкам не узнаёт состояние бота. Порядок действий один: проверка и постановка в очередь (или запись пропуска) идут до ответа в обоих случаях, так что и по времени ответа разница небольшая (создание turn пишет чуть больше строк, чем запись пропуска). Созданный turn владелец видит в треде расписания (событие `user_msg` с промптом). Идентификатор turn из ответа hook в продукте не использовался (PWA, Mac-агент, e2e его не читают); если понадобится, отдавать его можно только маршруту, который аутентифицирован владельцем. Бот, который сломался между проверкой и постановкой (`require_available_bot`, 409), тоже даёт пропуск и тот же 202. Неверный токен по-прежнему 403 и пропуском не считается. Пять пропусков подряд помечают расписание `paused_by_unavailable` (для отображения), первый принятый hook после возвращения исполнителя пишет `schedule_resumed`.
- Решения (причина, счётчик, троттлинг, возобновление) это чистые функции `activity.skip_reason`, `plan_skip`, `plan_resume`; ядро только выполняет их.

## 17. Самопробуждение бота (миграция `025_wakeups.sql`)

Бот сам просит ядро разбудить его позже: MCP-инструмент `schedule_wakeup` кладёт строку в `bothub.wakeups`, планировщик расписаний в нужный момент создаёт turn. Владелец видит запланированное в настройках бота, отменяет его и находит срабатывания в ленте. Чистая логика в `core/bothub/wakeups.py`, маршруты и исполнение в `main.py`, инструмент в `mcp_server.py`.

### Таблица `bothub.wakeups`

`id uuid`, `bot_id` (внешний ключ на `bots`, `on delete cascade`), `scheduled_at timestamptz`, `status` (`active|fired|skipped`), `prompt` (1–2000 символов), `reason` (до 200, по умолчанию пусто), `created_at`, `fired_at`. Сверх обязательных колонок две служебные: `thread_id` (тред, из которого бот попросил пробуждение; внешний ключ `on delete set null`) и `skip_reason` (`executor_unavailable|bot_paused|provider_unavailable|check_failed`, как у пауз триггеров, раздел 16). Отдельного `owner_id` нет: владелец определяется через `bots.owner_id`, как у `turns` и `approvals`. Индексы: `wakeups_due_idx(scheduled_at) where status='active'` для планировщика и `wakeups_bot_idx(bot_id, scheduled_at desc)` для списка бота. Миграция расширяет и `activity_log_code_check` тремя кодами событий.

### MCP-инструмент `schedule_wakeup`

Вызов не требует одобрения владельца (как `remember`): он только ставит будущий ход этому же боту, пробуждения видны в ленте и отменяются в настройках бота. Пробуждение, которое не удалось запустить в течение 15 минут, закрывается пропуском с причиной `fire_failed`.


`schedule_wakeup(prompt, reason?, at?, in_minutes?)`: ровно одно из `at` (ISO 8601; без пояса считается UTC, как остальные даты от клиента) и `in_minutes` (целое). Инструмент шлёт `POST /api/bots/wakeups` с токеном бота и `thread_id` текущего треда (`BOTHUB_THREAD_ID`). Ответ ядра возвращается как `{"ok": true, ...Wakeup, "deduplicated": bool}`; отказ ядра как `{"ok": false, "error": "<код>"}`, чтобы модель видела причину и могла исправить вызов. `prompt` и `reason` инструмент проверяет сам, до запроса. По `risk.classify` инструмент не из списка «только чтение»: без правила `auto_allow` он просит подтверждение владельца, как любое другое действие, меняющее состояние.

### `POST /api/bots/wakeups`

Только токен бота (владелец, Mac-агент: 403; без входа 401). Тело (`extra=forbid`): `at`, `in_minutes`, `prompt`, `reason`, `thread_id` (свой тред бота, иначе 404 или 403 как у других маршрутов бота).

| Правило | Значение | Отказ |
| --- | --- | --- |
| Срок | не раньше чем через 1 минуту и не позже чем через 30 дней от момента запроса, границы включены (`in_minutes` от 1 до 43200) | 400 `invalid`, detail `too_soon` или `too_far` |
| Способ задать срок | ровно одно из `at` и `in_minutes` | 400, detail `time_required` или `time_conflict` |
| Формат | `at` разбирается как ISO 8601, `in_minutes` целое (не строка, не булево) | 400, detail `at_invalid` или 400 `invalid` на схеме тела |
| `prompt` | непустой (пробелы не считаются), до 2000 символов | 400 `prompt_empty`, 422 `prompt_too_long` |
| `reason` | до 200 символов | 422 `reason_too_long` |
| Активные | не больше 20 на бота | 409 `{"error":"conflict","detail":"wakeup_limit"}` |
| Идемпотентность | активное пробуждение этого бота с тем же `prompt` и сроком в пределах ±1 минуты возвращается как есть | 200 вместо 201, `deduplicated: true` |

Повтор проверяется раньше предела: бот с 20 активными пробуждениями, повторивший свой вызов, получает то же пробуждение, а не отказ. Разные `prompt` в ту же минуту это разные пробуждения. Строка бота берётся `for update`, поэтому два параллельных вызова не обходят предел и не плодят дубли. Ответ 201: `{id, bot_id, thread_id, scheduled_at, status, prompt, reason, skip_reason, created_at, fired_at, deduplicated}`. При создании пишется `wakeup_scheduled` в ленту и системное событие `{"text","code":"wakeup_scheduled","wakeup_id"}` в тред (если он передан).

### Исполнение

Тот же цикл `scheduler` (интервал `BOTHUB_SCHEDULER_INTERVAL`, 30 с): `scheduler_tick` сначала вызывает `run_due_schedules`, затем `run_due_wakeups`; сбой первого не отменяет второй. `run_due_wakeups` выбирает активные строки со сроком не позже `now()` у активных пользователей (`for update of w skip locked`) и, как расписание, откладывает бота с неконечным запуском процедуры (строка остаётся `active` и срабатывает на первом проходе после освобождения). Исполнитель проверяет та же `trigger_block` (раздел 16), решение принимает чистая `wakeups.decide(block, scheduled_at, now)`:

- причины нет: `fire`. Тред: тред бота, из которого пришёл запрос, если он ещё `active`; иначе новый тред `kind=routine` с названием «Пробуждение: <причина>» (до 80 символов). В тред ставится turn `client='wakeup'` (событие `user_msg` с `actor = "bot:<bot_id>"`: сообщение от самого бота, не от владельца) с текстом «Самопробуждение: ты сам запланировал этот запуск. Причина: <reason>» и `prompt` через пустую строку. Строка получает `status='fired'`, `fired_at`, `thread_id`; в ленту идёт `wakeup_fired`. Опоздание не ограничено: если ядро лежало, пробуждение срабатывает при первом проходе, пока исполнитель доступен;
- `bot_paused`: `skip` сразу (пауза это явное решение владельца): `status='skipped'`, `skip_reason`, событие `wakeup_skipped` в ленту и системное событие `{"text","code":"wakeup_skipped","reason"}` в тред;
- остальные причины (`executor_unavailable`, `provider_unavailable`, `check_failed`): `wait` (строка остаётся `active`, проверка на следующем проходе), а через 15 минут после срока (`wakeups.GRACE`) `skip` с той же записью. Так перезапуск контейнера на минуту пробуждения не съедает, а исполнитель, который не вернулся, не держит его бесконечно.

Сбой одного пробуждения (исключение внутри savepoint) пишется в журнал и не откатывает остальные; строка остаётся `active` и пробуется снова.

### Маршруты владельца

- `GET /api/bots/{id}/wakeups?status=active|fired|skipped`: только свой бот (чужой или несуществующий 404; токен бота 403; неизвестный `status` 422 `invalid`, detail `status`). Ответ: массив `Wakeup`, не больше 100: активные по возрастанию `scheduled_at`, за ними история от новых к старым.
- `DELETE /api/wakeups/{id}`: отмена удаляет строку. Чужое и несуществующее 404, токен бота 403. Уже сработавшее или пропущенное не удаляется: 409 `{"error":"conflict","detail":"wakeup_not_active"}`. Гонка с планировщиком решается условным `delete ... where status='active'`. Отдельного события отмены нет.

Изменяющие запросы по cookie требуют `X-CSRF` и `Origin`, как везде.

### События активности

Журнал `activity_log` вида `schedule` (фильтр `kind=schedule` в `GET /api/activity` их показывает): `wakeup_scheduled`, `wakeup_fired`, `wakeup_skipped`. Параметры: `wakeup_id`, `scheduled_at` (ISO, UTC), у пропуска `reason` (код причины); текст, который бот назвал в `reason`, лента отдаёт полем `detail` (до 200 символов, PWA помечает его `data-i18n-skip`). Срабатывание ещё и обычный turn в ленте (`turn_started`, `client: "wakeup"`).

### PWA

В настройках бота (`#/bots/<id>`, телефон и Mac) карточка «Пробуждения бота» (`[data-wakeups]`): активные пробуждения со сроком, причиной и кнопкой «Отменить» (`DELETE /api/wakeups/{id}`), пустое состояние, ошибка загрузки с кнопкой «Повторить». Мок-режим: `?mock=1`, `&wakeups=fail` ломает загрузку.

## 18. Адаптеры вебхуков GitHub и Slack (этап 10, 2026-10-06)

Для расписаний типа `hook` (`schedules.kind = 'hook'`) поверх универсального вызова `POST /hooks/{id}` добавлены два специализированных адаптера:

- `POST /hooks/{id}/github`: адаптер вебхуков GitHub.
- `POST /hooks/{id}/slack`: адаптер Events API Slack.

Оба адаптера сохраняют общий предел тела запроса 64 КиБ (при превышении 413 `invalid`), проверку активности пользователя и включённого состояния расписания (иначе 404), а также правило ответа 202 `{"status":"accepted"}` для принятых в очередь и пропущенных событий. При неверной или отсутствующей подписи возвращается 403 `forbidden`. Подпись сырого тела проверяется до разбора JSON (невалидный JSON с неверной подписью даёт 403, с верной 400 `invalid`); предел 64 КиБ применяется по `Content-Length` и по ходу чтения потока; сравнение подписи идёт по байтам, не-ASCII в заголовке даёт 403.

#### Адаптер GitHub (`POST /hooks/{id}/github`)

1. **Заголовки и проверка подписи.**
   - `X-Hub-Signature-256`: заголовок подписи в формате `sha256=<hex>` (HMAC-SHA256 сырого тела запроса с секретом `hook_token` расписания). Сравнение выполняется за постоянное время (`hmac.compare_digest`). Неверная или отсутствующая подпись даёт 403.
   - `X-GitHub-Event`: тип события GitHub.
2. **Обработка событий.**
   - Событие `ping`: отвечает 202 `{"status":"accepted"}` без постановки turn в очередь.
   - Поддерживаемые события: `issues`, `issue_comment`, `pull_request`, `pull_request_review`, `push`, `workflow_run`. Для них формируется короткий русскоязычный текст промпта с полями: событие, репозиторий (`full_name`), действие (`action`), заголовок и номер задачи или PR (либо ref для push), логин автора, ссылка (`html_url`) и первые 2000 символов описания, комментария или сообщений коммитов. Этот текст добавляется к базовому `schedule.prompt` и ставится в очередь turn бота через общую логику ядра.
   - Остальные события: отвечают 202 `{"status":"accepted"}` и пропускаются без создания turn.
3. **Настройка в GitHub.**
   - В настройках репозитория или организации открыть раздел Webhooks и нажать «Add webhook».
   - Payload URL: `https://<домен>/bots/hooks/<schedule_id>/github`.
   - Content type: `application/json`.
   - Secret: скопировать значение `hook_token` из параметров расписания в Bothub.
   - Which events would you like to trigger this webhook: выбрать «Let me select individual events» и отметить нужные события (Issues, Issue comments, Pull requests, Pull request reviews, Pushes, Workflow runs).
   - Нажать «Add webhook». GitHub отправит пинг, ядро ответит 202.

#### Адаптер Slack (`POST /hooks/{id}/slack`)

1. **Заголовки и проверка подписи.**
   - `X-Slack-Request-Timestamp`: unix-время отправки запроса в секундах. Если разница с текущим временем сервера превышает 5 минут (300 секунд), запрос отклоняется с 403.
   - `X-Slack-Signature`: сигнатура в формате `v0=<hex>`, вычисляемая как HMAC-SHA256 от строки `v0:{X-Slack-Request-Timestamp}:{сырое тело}` с Signing Secret приложения Slack, сохранённым в расписании (`schedules.slack_signing_secret`, миграция `028_slack_signing_secret.sql`). `hook_token` для Slack не используется: Slack подписывает своим секретом, который владелец выбрать не может. Если секрет не задан, адаптер отвечает 403. Сравнение выполняется за постоянное время.
2. **Обработка событий.**
   - Подтверждение адреса (`url_verification`): если тело запроса содержит `{"type": "url_verification", "challenge": "..."}`, ядро возвращает `{"challenge": "..."}` со статусом HTTP 200.
   - Обратные вызовы (`event_callback`): для событий `app_mention` и `message` (без `bot_id` и без `subtype`, чтобы игнорировать сообщения ботов и системные события) формируется промпт с каналом, пользователем и текстом сообщения (до 2000 символов). Промпт ставится в очередь turn бота через общую логику ядра.
   - Другие события и типы вызовов: отвечают 202 `{"status":"accepted"}` без постановки задачи в очередь.
3. **Настройка в Slack.**
   - В консоли управления приложением Slack (api.slack.com/apps) открыть раздел «Event Subscriptions» и включить переключатель «Enable Events».
   - В поле «Request URL» ввести адрес `https://<домен>/bots/hooks/<schedule_id>/slack`.
   - В разделе «Basic Information -> App Credentials» скопировать «Signing Secret» и вставить его в поле «Секрет подписи Slack» расписания Bothub (`PATCH /api/schedules/{id}` с `{"slack_signing_secret": "..."}`; `null` очищает). Секрет хранится зашифрованным (AES-GCM, AAD = id расписания), только на запись: API возвращает лишь `has_slack_signing_secret: true|false`. Без заданного секрета подписанные запросы Slack, включая `url_verification`, получают 403.
   - Slack автоматически отправит запрос `url_verification`. Ядро ответит вызовом challenge (200 OK), и статус адреса сменится на «Verified».
   - В подразделе «Subscribe to bot events» добавить необходимые события: `app_mention` и `message.channels`.
   - Сохранить изменения и выполнить установку приложения в нужное рабочее пространство Slack.


## 19. Поручения бота боту (этап 11, миграция `027_delegation.sql`)

Бот передаёт задачу другому боту того же владельца: MCP-инструмент `delegate_to_bot` ставит turn получателю и сразу возвращает его id, результат бот читает позже инструментом `delegation_result`. Чистая логика (пределы, выбор получателя, текст результата) в `core/bothub/delegation.py`, маршруты в `core/bothub/main.py` рядом с самопробуждением.

### Колонки `bothub.turns`

`delegated_from_turn uuid` (turn бота-отправителя, внешний ключ на `turns`, `on delete set null`) и `delegated_by_bot text` (id бота-отправителя, без внешнего ключа: запись переживает удаление бота). У обычных turn'ов обе колонки `null`. Индекс `turns_delegated_by_idx (delegated_by_bot, status)` обслуживает счётчик активных поручений. Та же миграция расширяет CHECK `activity_log_code_check` кодами `delegation_sent` и `delegation_done`.

### MCP-инструменты

- `delegate_to_bot(bot, task)`: `bot` имя (без учёта регистра) или id бота того же владельца, `task` от 1 до 4000 символов. Шлёт `POST /api/bots/delegations` с токеном бота и `turn_id` текущего хода (`BOTHUB_TURN_ID`). Возвращает `{"ok": true, "turn_id", "thread_id"}` сразу, не дожидаясь выполнения; отказ приходит данными: `{"ok": false, "error": <код>}`. Длину `task` и пустой `bot` инструмент проверяет до запроса теми же функциями `delegation.clean_*`.
- `delegation_result(turn_id)`: `GET /api/bots/delegations/{turn_id}`. Возвращает `{"ok": true, "turn_id", "thread_id", "to_bot", "status", "result", "error"}`.

Одобрение. `delegate_to_bot` не входит в `READ_ONLY_TOOLS`: `risk.classify` даёт ему метку `other`, `permission_class` равен `unknown`, поэтому `decide` разрешает вызов без владельца только по точному правилу `auto_allow` (имя инструмента без glob, непустой `match`, закреплённый `op_hash`, как у правила после «запомнить»). Без такого правила вызов уходит владельцу на одобрение, как другие записи. `delegation_result` только читает и входит в `READ_ONLY_TOOLS` (`mcp__bothub__delegation_result`), но у ядра есть своя проверка: результат видит лишь бот, который поручил.

### `POST /api/bots/delegations`

Только токен бота (владелец, Mac-агент: 403; без входа 401). Тело (`extra=forbid`): `bot`, `task`, `turn_id` (turn этого бота, иначе 404 `turn_not_found`). Ответ 201: `{"turn_id", "thread_id"}`.

| Правило | Значение | Отказ |
| --- | --- | --- |
| `task` | непустой (пробелы не считаются), до 4000 символов | 422 `invalid`, detail `task_empty` или `task_too_long` |
| `bot` | строка до 200 символов: id, иначе имя без учёта регистра среди ботов того же владельца | 422 `bot_invalid`; не найден (в том числе бот чужого владельца) 404 `bot_not_found`; два бота с одним именем 409 `bot_ambiguous` |
| Себе | отправитель и получатель разные боты | 409 `conflict`, detail `self_delegation` |
| Получатель | не на паузе, не `no_model`, не `error_starting` | 409 `target_paused`, `target_no_model`, `target_error_starting` |
| Глубина | turn, созданный поручением (`delegated_by_bot is not null`, `delegated_from_turn is not null` или `client='delegate'`), поручать дальше не может | 409 `delegation_depth` |
| Активные | не больше 5 turn'ов с `delegated_by_bot = отправитель` в статусах `queued`, `running`, `waiting_approval`, `waiting_mac` | 409 `delegation_limit` |

Строка бота-отправителя берётся `for update`, поэтому параллельные вызовы не обходят предел. Всё делается одной транзакцией.

Тред получателя: самый свежий (по последнему событию, иначе по созданию) активный тред `kind='direct'` без `dry_run`; если такого нет, создаётся новый `direct` с названием «Поручения от <имя отправителя>». В нём создаётся turn `client='delegate'` с `delegated_from_turn` и `delegated_by_bot` и событие `user_msg`: `actor = "bot:<id отправителя>"`, `client='delegate'`, `payload = {"text": "Поручение от бота <имя>:\n\n<task>", "delegated_from": {"bot_id", "name"}}`. Событие уходит подписчикам треда после коммита. Дальше turn идёт обычной очередью: если в треде уже идёт другой turn, поручение ждёт.

### `GET /api/bots/delegations/{turn_id}`

Только токен бота. Читает бот, который поручил: чужой, несуществующий и обычный turn дают 404 (получатель тоже читать не может). Ответ: `{"turn_id", "thread_id", "to_bot", "status", "result", "error"}`. `status` это статус turn'а (`queued|running|waiting_approval|waiting_mac|done|stopped|error`). `result` непустое только при `done`: текст `assistant_msg` после последнего вызова инструмента этого turn'а (промежуточные реплики перед инструментами не берутся; если после инструментов текста нет, берётся весь текст), склеенный как ответ бота (`context.join_assistant`), не больше 8000 символов. `error` заполнено при `status='error'`.

### События активности

Журнал `activity_log` вида `schedule` (фильтр `kind=schedule` в `GET /api/activity`), строки пишутся на имя бота-отправителя (`bot_id`), `thread_id` это тред получателя:

- `delegation_sent`: при постановке. Параметры `from_bot`, `to_bot` (имена), `to_bot_id`, `turn_id`; текст задачи (до 200 символов) лента отдаёт полем `detail`.
- `delegation_done`: когда turn поручения закончился. Те же параметры и `outcome` (`done`, `error` или `stopped`). Событие пишет `append_event` при записи события `status` с конечным статусом, поэтому оно одно на turn и не зависит от того, как turn закрылся (штатно, остановка, ошибка, перезапуск ядра).

### PWA

В треде получателя сообщение с `payload.delegated_from` рисуется в обёртке `.msg-user-wrap` с меткой `[data-delegated-from]` «От бота <имя>» над пузырём `.msg-user`; имя бота и текст поручения это данные (`data-i18n-skip`), слово «От бота» переводится. В ленте активности строки «Бот передал задачу другому боту» и «Поручение выполнено» (у ошибки и остановки свои подписи) с подписью «<от> → <кому>». Мок-режим `?mock=1`: Скаут поручил Архиву разложить скан договора (тред `t-archive`).

## 20. Проверяющая модель действий (этап 11, миграция `029_action_checker.sql`)

Вторая оценка рискованного действия бота до того, как его увидит владелец. Необязательна: без настройки ничего не меняется.

**Настройка.** `bots.checker_model_id` (uuid, nullable, внешний ключ на `models(id)`, `on delete set null`): модель из реестра владельца (раздел 11). Задаётся в `POST /api/bots` и `PATCH /api/bots/{id}` (`null` выключает). Модель должна быть включённой моделью провайдера того же владельца и не подписки (`cli_subscription`): у подписки нет ключа для прямого запроса. Иначе 400 `invalid`, `detail: "checker model unavailable"`. В шаблон бота (раздел 9) поле не экспортируется. В PWA: настройки бота, поле «Проверяющая модель» (выбор из включённых моделей API-провайдеров, пустое значение «Не задана»).

**Когда проверяется.** В `POST /api/approvals`, если после `decide_permission` approval остаётся `pending`, у бота задана проверяющая модель и риск один из `pay`, `send`, `delete`, `login`, `push`, `exec` (всё, кроме `other`: чтение и прочее не проверяются). Approval с отказом по `forbidden_reason`/`mcp_allow` и авторазрешённые модель не видит. Запросы процедур (раздел 14) идут мимо этого маршрута и не проверяются.

**Запрос.** Один прямой HTTP-запрос к API провайдера модели (`bothub/checker.py`) на закреплённый проверенный IP: та же проверка адреса, `host` и SNI исходного имени, одобренные администратором приватные IP, запрет редиректов, что у пробного запроса списка моделей (раздел 11). Ключ провайдера идёт только в заголовок аутентификации. Не больше одного запроса на approval, таймаут 20 с (вместе с DNS), ответ не больше 256 КиБ, выход до 300 токенов. Формат запроса по типу провайдера: `anthropic_api` `POST /v1/messages`, `openai_api` и `openai_compatible` `POST /v1/chat/completions`, `google_api` `POST /v1beta/models/<модель>:generateContent`.

Фиксированный системный промпт (английский, в `checker.SYSTEM_PROMPT`) требует ответ строго одним JSON `{"verdict":"allow|deny|ask","reason":"<=200 chars"}` и объявляет всё внутри тегов `<role>`, `<request>`, `<action>` недоверенными данными. Сообщение пользователя: `<role>` роль бота (до 512 символов), `<request>` последнее сообщение владельца в ходе (`user_msg` этого `turn_id`, при его отсутствии последнее в треде; первые 2000 символов), `<action>` имя инструмента и аргументы. Аргументы берутся из approval уже после маскирования браузера (`mask_browser_args`), затем ещё раз: значения полей с именами `password`, `secret`, `token`, `api_key`, `authorization`, `cookie` и подобных заменяются на `[скрыто]`, строки, похожие на ключи и токены (`sk-…`, `Bearer …`, `ghp_…`, `xox…`, `AKIA…`), тоже, управляющие и невидимые символы убираются, JSON обрезается до 4000 символов.

**Разбор ответа.** Берётся первый JSON-объект в тексте (допускается обёртка в markdown). `verdict` без учёта регистра и пробелов; причина обрезается до 200 символов, переводы строк склеиваются. Неизвестный или отсутствующий `verdict`, не JSON, пустой ответ, сетевая ошибка, ответ не 200, редирект, превышение размера, недоступный адрес, нет модели или ключа, таймаут: `verdict: "ask"` с причиной «проверяющая модель не ответила вовремя», «проверяющая модель недоступна» или «проверяющая модель ответила не по формату». Сбой проверки никогда не отклоняет и не разрешает действие.

**Эффект.**
- `deny`: approval создаётся сразу в `rejected` (`decided_from='checker'`, `decided_at` заполнен), ответ `POST /api/approvals` несёт `reason: "checker_denied"`, `checker_verdict`, `checker_reason`. Владельцу вопрос не приходит (в `GET /api/approvals?status=pending` его нет). В тред пишутся события `approval_req` (с полем `checker`, чтобы в ленте была карточка), `approval_dec` от `system` с `decision: "rejected"`, `reason: "checker_denied"`, `checker`, и `checker_denied`. Бот получает отказ как обычно: `approve` в `mcp_server.py` возвращает `{"behavior":"deny","message":"checker_denied: <причина>"}`, ход продолжается.
- `allow` и `ask`: approval остаётся `pending` и ждёт владельца. `allow` ничего не разрешает сам. Вердикт и причина лежат в `approvals.checker_verdict` и `checker_reason` (видны в `GET /api/approvals`) и в `approval_req.payload.checker`.

**Данные.** `approvals.checker_verdict` (`allow|deny|ask`, null: проверки не было), `approvals.checker_reason` (до 200 символов).

**События.** `approval_req.payload.checker` = `{"verdict","reason"}` (необязательное поле), `approval_dec.payload.reason = "checker_denied"` и `checker`, новый вид `checker_denied` с `payload` `{"approval_id","tool","reason"}`. Лента активности (раздел 16): запись вида `approval` с кодом `checker_denied` вместо `approval_rejected`, если approval закрыла проверяющая модель.

**PWA.** Карточка подтверждения (тред, экран «Решения»): строка «Проверка: <вердикт> · <причина>» под заголовком; автоотказ показывается как «Отклонено проверяющей моделью» без кнопок. Мок `?mock=1`: `ap2` несёт подсказку `ask`.
